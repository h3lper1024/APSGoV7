**核心方向：搜索与计算使用按字段分列的 NumPy 原生数值数组；每个业务字段只有一份权威计算值，规则、排序、评分、结果与审核遵守同一个数值标准。**

**数据表示迁移不等于算法修改。**在输入、规则和数值标准相同的前提下，将 Python 对象、元组、列表或字典改成 NumPy 数值数组，必须保持求解阶段、动作集合、候选的有效顺序、重点/常规轮转、候选额度含义、首个改善接受和最终结果不变。若结果发生变化，必须证明它来自另行确认的数值标准变化或独立登记的算法缺陷修复，不能笼统归因于“改成 NumPy”。

**候选按结构归属直接唯一生成。**动作、链、区间和目标位置共同确定一个结构候选；每个候选在当前方案代次中只有一个自然生成入口。订单优先级只决定候选顺序和所属搜索通道，不允许以链中每个订单为入口重复展开链级或区间级动作，也不允许先批量生成重复候选再依赖 `set` 或字典过滤。

**数据保存为 NumPy 数组，不等于完整评价已经成为数值内核。**完整候选评价只有在候选、链、节点和规则的高频计算全部只读写原生数值数组与标量，不逐候选创建规则结果、违规、指标、字典、列表或元组，并可由 Numba 编译时，才算完成数值化。Python 可以继续负责批次编排、额度、取消、按序接受及最终对象映射；这些低频边界不属于需要消除的计算内核。

用户已明确：可以调整旧数值计算口径，不为兼容浮点、Decimal 的历史差异维护双份字段、双套求解或精确回落路径；设计不受 Ponytail Lite 的最小修改偏好限制。该授权只适用于第 4、8、9、15 节明确列出的数值标准变化，不授权借数据结构迁移修改搜索控制。排除这些已确认数值差异后，Python 对象路径与 NumPy 路径必须对同一规范候选流作出相同判断和接受结果。

## 2. 背景、目标和非目标

### 2.1 阶段 7 实施前的问题及当前解决边界

以下问题表与三层诊断冻结于 `8cf80f1`，描述阶段 7 实施前，不再作为阶段 7.4 完成后的现状。现在边/链/方案规则、资源、时钟、九级评分和未变链复用均在 `_numeric_kernel.py` 中实际编译执行；普通拒绝候选不构造规则/违规/指标/完整评价对象，接受及审核使用同原语明细模式。Python 仍负责候选生成与覆盖准备、额度、取消及首改善发布；批次扁平化和候选并行归阶段 8，不能宣称整个搜索流程已编译。

实施前已经有数值数组，但尚未形成统一的数值搜索基础：

| 当前位置 | 已有能力 | 本次要解决的缺口 |
|---|---|---|
| `_numeric_state.py` | `NumericNodeColumns`、`NumericPlan` 已保存分列数组、连续节点行和链偏移 | `NumericPlanOverlay.chains` 仍以“每链一个 NumPy 数组”的 Python 元组组织，并通过 Python 列表建立覆盖布局 |
| `_numeric_rules.py` | 规则参数已编译，边快速判定及部分规则计算使用数值列 | 完整规则评价仍循环 `CompiledNumericRule` 对象，并创建 `NumericRuleResult`、`NumericViolation`、`NumericMetric` 等 Python 对象 |
| `_numeric_evaluation.py` | 交期已有向量化和未变链评价复用，九级评分使用整数语义 | `_chain_facts()`、`_assemble_evaluation()`、`_evaluate_numeric_candidate()` 仍使用字典、元组、生成器和逐链 Python 循环组装完整结果 |
| `_numeric_refinement.py` | 候选按结构唯一生成，支持有界有序描述批次和覆盖评价 | `_scan_family()` 只批量预取描述，随后仍逐条调用 Python `_try_recipe()` 和完整评价；不是批量数值评价 |
| `_delivery_parallel.py` | 已有一个受限的 Numba 并行内核 | 只覆盖旧交期上下界，不是本文要求的完整规则、资源、交期和九级评分内核 |

阶段 6.2 从冻结真实请求截取 256 组 `evaluate_numeric_overlay_candidate()` 实际输入，对 1/2/4/8 个 Python 工作线程分别测量。全部结果一致，但经过时间中位数为 0.369328/0.376141/0.382813/0.396968 秒，线程越多反而越慢。该结果证明的是：**普通 Python 完整评价器加线程没有收益**。它同时暴露出完整评价器尚不是可由 Numba 在候选维度并行调度的编译内核；不能把这一结果泛化为“Numba 候选并行无效”，也不能将该离线探测描述为生产并行接入。

当前数值化进度必须分成三层记录，不能再合并表述：

1. **数值存储层已建立**：节点字段、方案主结构、规则参数及主要评分使用 NumPy 数组或原生整数。
2. **向量与增量计算部分完成**：交期时钟、边判定、未变链复用等已有实际收益，但仍由 Python 编排并组装大量对象。
3. **完整数值评价内核未完成**：候选、链、规则、资源、交期和九级评分尚未形成一个只处理数值缓冲区的权威内核；因此生产并行的必要前提尚不具备。

阶段 5 预检进一步发现，目标态与当前实现之间仍有一处结构性缺口：`NumericPlan` 已按 `node_rows + chain_offsets` 保存连续 NumPy 结构，但候选编辑继续通过 `_layout()` 把全部链恢复为 Python 元组/列表。该适配最初在首轮候选构造中用于复用切片、拼接、`pop`、`insert` 和 `list.index` 逻辑，随后又被后置精修用于每个尚未正式计费的原始组合过滤。切链和片段交换会产生大量组合；被重点/常规通道过滤掉的组合发生在逻辑候选额度扣除之前，因此 40 万次额度没有约束这部分实际工作。这个问题属于数值迁移未闭合和候选边界错误，不是 NumPy 的必然成本。

步骤 5.3 又暴露出更直接的生成职责错误：候选生成以原订单为外层入口，但切链、整链调序和部分区间动作实际属于链或结构区间。一条链含 6 个原订单时，5 个切分点和 2 种新旧链位置本应只生成 10 个切链候选，当前入口却生成 60 个，再过滤其中 50 个重复候选。生成后去重虽然减少了重复评价，却改变了额度消费与后续候选轨迹，并使寻找下一个“未见候选”的扫描工作游离在 40 万次额度之外。正确修复不是扩大去重集合，而是按结构归属直接生成 10 个候选。

### 2.2 目标

1. 订单属性、链结构、候选描述、规则参数、评价及搜索辅助状态使用原生数值数组。
2. 从候选生成到规则判定、交期计算及接受判断，直接操作数组，不在每个候选中恢复整份领域对象。
3. 统一单位、缺值、分类、比较、舍入、溢出与身份语义；不保留旧数值兼容分支。
4. 继续使用现有求解流程和结构调整能力，保持规则配置、多产线边界及可追溯结果。
5. 在同一数值语义下，使全量、增量、串行、后续并行评价得到相同结果。
6. 为一分钟完整求解目标建立可测量的基础；一分钟不是已经达标，也不是强行截断搜索。
7. 候选按节点、区间、链或结构对的自然归属唯一生成；规范候选流保持原有首见顺序、轮转、额度含义和确定性。
8. 建立唯一的完整数值评价内核；拒绝候选只产生固定长度的数值汇总，只有被接受候选、阶段快照和最终方案才生成明细及领域对象。

### 2.3 非目标

- 不改成另一套 ALNS/VNS/局部搜索框架，不调整九级目标优先级，不增加新的资源范围或业务目标。
- 不把全部内容塞入一个二维浮点表；不用 DataFrame、字符串数组或 `dtype=object` 充当搜索主结构。
- 不建设通用规则语言、动态代码生成平台、多精度数值库或分布式调度平台。
- 不为了并行另写一套“快速近似评分器”；串行、批量和并行必须调用同一权威数值事实与评分内核。
- 不建立“先生成重复候选、再用全局集合过滤”的生产路径；测试中的重复检测只作为断言，不作为运行时正确性机制。
- 不以增加候选额度、放宽禁止规则、删减审核或损失来源重量换取速度。
- 不在本次文档任务升级依赖、切换分支、接前端、打包 exe、启停服务或部署。

## 3. 统一计算边界与运行流程

### 3.1 边界内外的职责

| 范围 | 允许的数据和工作 | 禁止的回流 |
|---|---|---|
| 输入准备 | 原有请求对象、JSON、规则对象、字典；解析 Decimal/日期、校验、编码、编译数值参数 | 未校验输入直接进入数值内核 |
| 搜索与计算 | `int64`、`int8`、`bool` 等 NumPy 数组及原生数值标量；Numba 编译计算 | 查询业务字典、恢复原订单对象、调用旧 Decimal 评分作兜底 |
| 主控制逻辑 | 阶段、额度、取消、数组生命周期、串行接受；可用轻量 Python 函数或封装数组的类 | 把每节点/每候选循环留在 Python 对象路径，却称为数值搜索 |
| 输出与诊断 | 从权威数值和身份映射生成原有结果对象、中文说明、CSV/JSON | 输出阶段重新采用旧规则口径计算或静默重排 |
| 独立审核 | 从冻结输入和最终候选重新构造数值事实、无搜索缓存重算 | 直接相信搜索保存的分数、合法标记、缓存或派生台账 |

“统一 NumPy”约束的是搜索使用的数据及算法运算，不禁止在输入/输出边界使用字典、日期或 Decimal 进行解析与单位换算。边界保留原始文本用于追溯，不意味着保留另一份参与评分的原值。

### 3.2 各运行节点

| 顺序 | 节点 | 数值化后的职责 |
|---|---|---|
| 1 | 请求与规则冻结 | 沿用输入验证、软硬钢数据准备、任务期序和规则绑定；确定数值标准身份 |
| 2 | 数值准备 | 选择精确单位、检查范围、建立节点/原单/原型数组、规则参数和派生分类 |
| 3 | 连接与初始构造 | 数值连接查询、稳定排序、有序邻接表、最大匹配/路径覆盖及初始链编号序列 |
| 4 | 首轮局部搜索 | 整链调整、真实节点移动、虚拟填充、适用的整链调序；直接评价数值候选 |
| 5 | 受控拆单与重放 | 数值拆分、重量与工时分配、分隔/桥接及原有重放入口；不增加一套重放逻辑 |
| 6 | 后置结构与交期精修 | 保留节点、片段、切链、调序、普通连接材回收及重点/常规搜索策略 |
| 7 | 最终审核与释放 | 无缓存重算规则、来源、期锁、谱系、时钟、九级评分；通过后才构造可发布结果 |

数据表示迁移必须保持动作集合、阶段先后、直接位置优先、原单 4 提案轮转、重点/常规 64 提案轮转、候选额度及“首个改善接受”的算法原则。在同一数值标准下，规范候选序列、接受轨迹和最终结果必须一致。只有第 4、8、9、15 节另行确认的新数值标准允许造成临界评价差异；该差异必须在固定候选上单独证明，不能与数据结构改造混报。

### 3.3 完整数值化的完成定义

搜索热路径按以下边界判断是否完成，不能以类名包含 `Numeric`、字段使用 `np.ndarray` 或局部函数完成向量化代替验收：

| 层次 | 完成条件 | Python 允许范围 |
|---|---|---|
| 数值存储 | 搜索所需字段、方案、规则参数和候选结构可由原生数值数组完整表达，无 `dtype=object` | 任务准备和静态容器可组织数组 |
| 单候选权威评价 | 链规则、方案规则、资源、交期和九级评分全部在同一数值事实内核中完成 | 调用内核、检查状态码、按序比较评分 |
| 批量候选评价 | 多个候选使用扁平数组和偏移批量输入，输出固定形状汇总；拒绝候选不创建 Python 明细对象 | 生成有界批次、额度与取消控制 |
| 候选并行 | 单候选内核可由 Numba 编译；候选维度可用 `prange`，工作缓冲互不共享写入 | 主线程按原顺序消费、接受和提交资源 |
| 明细与发布 | 只对接受候选、阶段快照和最终方案，从同一数值事实生成违规、指标和结果对象 | 中文消息、API 模型、CSV/JSON 和诊断落盘 |

Numba 编译后的循环仍属于数值内核；需要消除的是高频 Python 解释器循环及其对象分配，而不是机械地消灭所有 `for`。独立最终审核仍保留，但必须使用同一数值标准重新构造输入并无缓存执行，不能读取搜索缓存或把搜索结果直接回传。

## 4. 统一数值标准

本章四项数值约定已获用户确认，记录见第 15 节。统一数值标准应绑定任务身份，任务运行中不可切换；已确认不代表已经实现或验证。

### 4.1 静态物理量：精确定点整数

定点数是“物理值 × 固定倍率后保存为整数”。同一任务、同一字段只确定一个倍率；输入、规则阈值、虚拟原型及派生节点共用。

| 字段 | 原单位 | 确定倍率的范围 | 权威数组类型 |
|---|---|---|---|
| 宽度 | mm | 全部订单/原型宽度、逆宽/窄钢等宽度阈值 | `int64` |
| 厚度 | mm | 全部订单/原型厚度、区间边界、绝对跳跃阈值 | `int64` |
| 温区上下限 | ℃ | 全部有效上下限、最小重叠量 | `int64`；上下限共用倍率 |
| 重量 | 吨 | 原订单、原型、链重/连续重量/填充/拆单阈值；至少能表达 0.01 吨评分单位 | `int64` |
| 比例 | 无量纲 | 比例参数及相对厚度系数 | 约分后的 `int64` 分子、分母；分母严格为正 |

准备时从十进制原值取得所需最大有效小数位，选择对应的 10 的幂作为倍率。删除末尾无意义零不改变数值；不得先转 `float` 再推算位数，也不按每条订单选择不同倍率。固定倍率在任务中冻结，不随候选变细。

因此，宽度只有一列：连接、逆宽、窄钢分类、同规格、初始排序、链间宽差全部读取该列。重量也只有一列，不再额外保留“排序浮点重量”。比例的分子/分母是一个数的表示，不是两种口径。

所有同量纲比较直接进行整数比较；相对厚度判断使用约分后的交叉乘法，避免生成一列舍入后的允许厚差。例：相对上限为 `p/q` 时，判断 `abs(t2-t1) * q <= basis * p`。中间乘积必须事前证明不溢出。

### 4.3 生产时钟：统一整数毫秒

生产时间刻度确定为 **1 毫秒**，数组存相对排产开始时间的 `int64`。业务展示可以到秒，但计算过程不通过字符串日期，也不通过小时浮点数。

1. 排产开始时间沿用 `Asia/Shanghai` 时区，交期取当天 24 点；形成相对起排的毫秒差。起排输入若精细于毫秒，明确按四舍五入到毫秒并记录转换，不静默截断。
2. 原订单总工时在准备阶段一次转换：`D = round_half_up(duration_hours × 3_600_000)`。
3. 原型单位工时在准备阶段一次转换：`D_proto = round_half_up(unit_weight × virtual_hours_per_tonne × 3_600_000)`；仍使用当前显式传入/准备的速度和工时，不另改速度。
4. 搜索中只累加节点整数毫秒。最终完成时间、晚交判断、候选排序和审核均从这个时钟取得，不再回到 28 位 Decimal 时钟。
5. 原始工时为正但量化后为零时，准备失败并报告该字段；不能偷偷提升为一毫秒，也不能切换到旧精算。

上述舍入是新业务数值标准，不是“与旧时钟误差为零”。未拆原单和原型每次量化误差不超过 0.5 毫秒；总偏移需按实际节点及原型使用次数给出上界。仅 531 个未拆原单的量化上界是 265.5 毫秒，不包含新增虚拟材，也不包含起排时间量化。临近交期边界的晚交名单可能变化，必须在对照报告单列。

### 4.4 拆单重量与工时必须守恒

- 片段重量使用父单相同重量单位；沿用当前最大片重构造和最小片重判定，末片保存整数余量，所有片段重量精确等于父单重量。
- 原订单总工时在拆前已经固定，不在每次排入不同位置时重新计算。
- 设父单重量 `W`、总毫秒 `D`，按稳定的 `piece_index` 排列片重 `w_j`，定义累计分配 `A_j = round_half_up(D × sum(w_1..w_j) / W)`，`A_0=0`；片段工时为 `A_j-A_(j-1)`。
- 各片工时之和严格为 `D`；片段换位不会重新分配工时。分配只在准备拆分候选时执行一次，不在普通评分时做除法。
- 单片相对比例分配可能有毫秒级差异；重排后生产前缀可能只包含部分片段，误差报告应把这种分配差异与原单总工时量化分别计算，不能只引用未拆原单的总误差上界。
- 极小片段可能分配为零毫秒；它是总工时守恒下的量化结果，允许并记录，不可删除该片段或当作原订单完成。原订单完成取最后实际片段的位置。
- 虚拟节点仍按原型单位重量生成，使用原型单位毫秒；不引入原实现没有的任意重量虚拟单。分隔材同样占用工时。

### 4.5 舍入、比较和派生评分

统一四舍五入：小于半单位舍去，大于或等于半单位进一；恰好中点时远离零，例如 `2.5→3`、`3.5→4`、`-2.5→-3`。十进制准备阶段对应 `ROUND_HALF_UP`；它不代表把全部输入先截成固定小数位，只作用于本文明确规定的量化点。[Python 舍入定义](https://docs.python.org/3.10/library/decimal.html#decimal.ROUND_HALF_UP)

数值内核使用整数商与余数实现：对待舍入整数比值取绝对值，除以正分母得到商 `q` 与余数 `r`；当 `r >= 分母-r` 时令商加一，最后恢复符号。该判断避免直接计算 `2*r` 的额外溢出风险，符号、绝对值和加一仍受第 4.6 节范围检查。不使用依赖默认舍入方式的 Python `round()` 或 `np.round()`，也不先转浮点再比较中点。

- 物理值和重量：可精确表示才进入数组，不做输入舍入。
- 工时：仅按第 4.3～4.4 节在转换或拆分时量化；普通累计只做整数加法。
- 欠重评分：每链缺口换成 0.01 吨单位后四舍五入，再求和；欠重数量按权威链重判断，不能按舍入后的缺口是否为零判断。
- 交期评分：完成/等待毫秒派生为整秒再评分；这是已确认的评分粒度，不是第二条生产时钟。原始完成明细和晚交判断用同一毫秒时钟。
- 禁止严重度：每条违规的规则严重度转换成 `10^-6` 严重度单位并四舍五入，之后整数求和；不继续兼容旧“浮点按序加总后保留六位”的结果。
- 显示单位换算只发生在输出，不反向参与接受判断。

**移除仅为旧浮点/Decimal 判定保留的隐式 `1e-9`、`1e-6` 比较余量，直接按数值化后的配置边界判断。**真正的工艺容差仍由宽度、厚度、温度等现有规则参数表达。此项包含重量及虚拟比例临界判定的变化，已获第 15 节确认，不能假装只是内部格式替换。

### 4.6 范围、溢出与错误

NumPy/Numba 的原生整数是固定宽度，不具有 Python 整数的任意精度；Numba 默认也不保证数组越界会得到普通 Python 异常。[NumPy 整数范围](https://numpy.org/doc/2.2/user/basics.types.html#overflow-errors)、[Numba 数值与边界语义](https://numba.readthedocs.io/en/stable/reference/pysemantics.html)

设计要求：

1. 准备时可以用 Python 任意精度整数/Decimal 完成解析、倍率选择及上界证明；只把已证明安全的值送入数组。
2. 检查范围不仅包含单值，还包含重量总量、差值、绝对值、比例交叉乘积、片重工时分配、最长时钟、重量乘时间、严重度和评分总量。
3. 候选使用私有空间时仍检查新增规模；不能以历史样本峰值当成最大节点数，也不能把候选额度直接当成最终虚拟节点数量。
4. 全局上界难以证明的中间乘法使用运行前检查或约分后计算；必须在运算前判断，不能溢出后再检查正负号。范围失败不是“规则违规”或“候选不改善”。
5. 超范围或不能支持的输入明确结束本次数值求解并返回可定位诊断；不饱和截断、不降精度、不回到对象求解。该收紧适用范围的策略已获用户确认，实际范围证明仍须在实施时验证。
6. 索引检查包括负数、容量、有效行数、片段区间及方案代次；`-1` 仅可表示无身份，使用前判断，禁止意外索引数组末项。

### 5.4 规则参数表

保留现有规则基类、具体规则及规则集作为配置和说明入口，将已启用、已验证的参数编译为计算函数所需数组。参数包括整数阈值、比例分子分母、厚度区间及开闭标记、角色开关、连续规则分组码、规则身份和目标位置。

当前 `tuple[CompiledNumericRule, ...]` 适合作为准备边界的可读结果，但不作为候选热路径的内核输入。规则冻结后一次性编译成固定数值表，至少包括：

- `rule_kind`、`rule_scope`、`rule_index`、`rule_enabled` 等一维整数/布尔列；
- 通用参数的 `parameter_offsets + parameter_values`；
- 厚度分档等变长参数的区间偏移、上下界、开闭标记、计算基准及回退值；
- 规则原因编号、指标编号、允许偏差标记和九级目标顺序；
- 规则程序、任务字段单位及数值语义身份。

串行评分、批量评分、并行评分和明细投影必须读取同一组编译数值表。禁止让串行使用 `CompiledNumericRule` 对象分派、并行再用另一套 `if`/参数常量，因为那会形成两套权威规则实现。

不新增第三层规则抽象、通用表达式解释器或另一份 GQGA4 配置。数值计算器直接返回规则编号、原因编号、主体位置和数值结果；中文消息由边界格式化。

启用但未提供数值实现的规则/参数在准备阶段明确拒绝，不能跳过，也不按候选回退到旧对象规则。停用规则继续校验配置结构，不贡献判断和分数。其他产线须逐条登记覆盖情况，不因 GQGA4 通过而宣称全部支持。

## 6. 方案、候选与搜索工作空间

### 6.1 列式节点目录

所有静态节点按稳定行号保存，第 5 节每个字段各有一条连续数组。只读数组可由一个轻量对象组织，但内核参数必须最终是原生数组和标量，不能依赖逐节点 Python 方法调用。

- 原订单行的物理数据不可被搜索改写。
- 动态拆片和虚拟节点采用同样的列布局；不是另外一套规则对象。
- 拒绝候选产生的临时行留在该候选私有空间，不增长正式目录、不消耗正式编号。
- 接受时才登记正式动态行；回收后的业务编号不重用。容量增长、必要的物理行整理只能在主线程没有计算批次读取时发生；整理必须重建全部位置索引并提升代次。
- 字符串原编号、授权文字和规则名称只保留一份边界映射，不进入数值数组的 `object` 元素。

### 6.2 当前方案布局

建议用“连续节点序列＋链起止偏移”表达完整方案，避免每条链对应一个 Python 节点列表。

| 数组 | 长度 / 内容 | 用途 |
|---|---|---|
| `node_rows` | 全部当前节点数；各链节点依生产顺序相接 | 生产序列与链内扫描 |
| `chain_offsets` | 链数＋1；第一项 0、末项等于节点数 | 第 i 链是 `node_rows[offsets[i]:offsets[i+1]]` |
| `chain_ids` | 链数；稳定内部身份 | 身份与生产位置解耦 |
| `chain_periods` | 链数；实际安排期序 | 期锁、生产分组与延后检查 |
| `row_to_chain`、`row_to_position` | 节点目录容量；不存在为显式无位置 | 常数次读取找到节点当前位置 |
| `source_piece_offsets`、`source_piece_rows` | 原单数＋1，以及全部真实片段行号 | 完整覆盖拆单，不能只保存一个片段 |
| `source_last_position` | 原单数 | 取得每个原单最后实际片段完成位置 |
| 链摘要、方案指标 | 按链和规则编号排列的原生数值数组 | 复用未变链、增量与评分 |

空链不进入当前方案；链内必须至少有一个真实节点，真实过渡材属于真实节点。链 ID 不是数组下标，原单 ID 也不是节点行号。结构编辑后可能需要重建一部分位置数组，这属于正常数值维护成本，不能为追求“零复制”引入复杂可变链表。

`_layout()` 一类“完整方案转为每链 Python 元组/列表”的适配只能留在低频边界工具中，不得进入候选枚举、通道归属、快速过滤或完整评价的高频路径。搜索读取单链时直接使用 `node_rows[chain_offsets[i]:chain_offsets[i+1]]` 的只读 NumPy 视图；链标识定位、节点位置和原单片段优先使用本节已有索引，不逐候选扫描或转换完整方案。

### 6.3 轻量候选

候选描述保存：动作枚举、当前方案代次、候选序号、源/目标链身份、源/目标节点或区间、插入位置、期锁信息，以及新增/删除/拆分资源的明确清单。

纯移动/交换描述通过数值索引读取共享属性；变化链在私有整数缓冲区中拼接。没有变化的链只引用当前链序列，不复制属性、不重算链内规则。

复杂候选可以建立受影响链的完整整数序列，不要求所有动作强行表达成一个公式。禁止回到“先为整份候选生成 Node/Chain/SchedulePlan，再转换回数组”的循环。

候选基本合法性与工艺评价分开：重复节点、错误来源、越界、非法片段、未授权资源变化等直接拒绝；工艺规则的违反仍按现有搜索允许的中间状态和九级评分处理，不能新增“所有中间候选必须零违规”的拦截。最终发布另行执行禁止规则门禁。

### 6.4 搜索状态与遍历

- 匹配关系、访问标记、队列、栈、前驱、可用节点标记和排序结果均用整数/布尔数组。
- 同一个节点是否可用依赖当前方案及候选；静态可连接关系与动态可用集合分别表达，不缓存脱离方案代次的“当前可用后继列表”。
- 广度/深度遍历仍有访问依赖，不强行改成并行矩阵计算。需要逐步遍历时使用编译循环操作上述数组。
- 随机种子、原单轮转游标、动作族游标及已接受计数集中管理；新运行仍须可重复，不以“无需兼容旧轨迹”放弃确定性。

### 6.5 后置结构精修的生成与物化边界

每个已接受方案代次只建立一次“当前方案只读搜索索引”。它直接引用方案数组，并包含链长度、链标识到链下标的定位、原单全部片段位置、关键原单节点标记及按链的关键节点累计计数。候选拒绝不重建；接受、动态目录正式扩展或链结构发布后，旧索引随旧代次失效，新代次重新建立。不得通过缓存 Python 链列表替代该数值索引。

候选身份由动作类型和全部结构坐标共同确定，包括稳定链身份、源/目标节点或区间、插入/切分/调序位置以及资源变化。当前方案代次不同，即使结构坐标相同也属于新状态下的候选；同一代次内身份相同的候选只能由一个自然入口产生。

| 动作族 | 唯一结构归属 | 唯一生成要求 |
|---|---|---|
| 链内单节点移动 | 节点行及链内位置 | 每个节点位置只展开一次目标位置 |
| 跨链节点移动 | 源节点行、源链、目标链及插入位置 | 不按原订单再次展开同一节点 |
| 节点交换 | 两个节点位置构成的无序结构对 | 用固定位置顺序确定唯一方向，不正反各生成一次 |
| 片段移动 | 源链的明确起止区间、目标链及插入位置 | 区间内只选一个确定的拥有位置；同一原单的多个片段不能因优先级相同重复拥有 |
| 片段交换 | 两个明确区间构成的无序结构对 | 用链、起止位置的稳定顺序确定唯一方向 |
| 切链 | 源链、切分位置及两条结果链的目标位置 | 每条链直接枚举一次，不由链内每个原订单重复触发 |
| 整链调序 | 链及目标生产位置 | 每条链直接枚举一次，不由链内每个原订单重复触发 |
| 普通连接材回收 | 链内连续可回收区间或明确单节点位置 | 每个区间/位置只扫描一次 |

原订单优先级仍决定候选首见顺序和重点/常规通道，但不再充当链级或区间级动作的生成实体。单节点使用节点自身归属；片段在区间内按“原订单优先顺序、链内位置”选择唯一拥有位置；切链和整链调序在整链真实来源中选择优先级最高且位置最早的代表原单，只用于排序。交换类动作先用相同稳定键确定唯一方向。新生成器输出顺序必须等于旧生成逻辑中各结构候选**第一次出现**的顺序，不得因改用集合、哈希遍历或数组内部编码重新排序。

重点订单/普通订单通道在展开目标位置前确定：单节点查看该节点标记；片段使用区间累计计数；交换检查两个区间；切链和整链调序使用整链标记。每个结构只在所属通道展开一次，不允许两个通道分别生成后再丢弃一份。生产代码不维护跨生成器的 `seen`/去重集合；测试应证明实际输出身份无重复。

40 万次候选额度仍表示“最多允许多少个规范结构候选进入结构/规则检查”，是上限而不是必须凑满的数量。每个按上述规则直接生成的候选在进入检查前恰好消费一次；不存在重复候选的额外计费，也不存在为寻找新的未见候选而不计费地扫描重复流。如果当前方案的规范候选已经穷尽且没有接受动作，搜索以本阶段完成结束，不继续循环凑满额度。生成器嵌套循环仍定期检查时间和取消状态，单次 `next()` 不得长时间绕过运行边界。

运行诊断记录规范候选生成数、候选消费数、完整评价数和接受数；可在测试或有界诊断中计算理论组合数并断言重复为零。历史“原始 60、过滤 50、送出 10”只作为旧缺陷证据，不能成为新的正常运行模式。

实际候选采用受影响链覆盖：未变链引用当前方案切片，移动/交换只建立源链和目标链的私有整数序列，切链只建立切分后的链，整链调序只保存链排列，连接材回收只建立所在链。评价器在“当前方案＋受影响链覆盖＋候选资源变化”上计算；拒绝时释放私有缓冲。只有严格九级评分确认接受后，才组装完整连续 `node_rows`、重建全局位置/原单片段索引、校验来源与重量工时守恒并生成下一代 `NumericPlan` 和指纹。独立双审计仍从发布后的完整方案重算，不因延迟物化而削减。

### 6.6 候选批次的纯数值布局

有界批次不能是 `tuple[CandidateDescription, ...]` 加逐条 Python 调用的别名。进入评价内核前，候选应整理为以下扁平布局；名称可在实施时按现有模块风格调整，但数据关系不得改变：

| 数组 | 含义 |
|---|---|
| `candidate_node_rows` | 批次内全部候选链的节点行，按候选、链、生产位置连续拼接 |
| `candidate_chain_offsets` | 批次内全部候选链到 `candidate_node_rows` 的起止偏移 |
| `candidate_offsets` | 每个候选在“批次内全部候选链”中的起止偏移 |
| `candidate_chain_ids`、`candidate_chain_periods` | 每条候选链的稳定身份和安排期 |
| `candidate_generation`、`candidate_sequence`、`candidate_action` | 方案代次、规范候选序号和动作类型 |
| `changed_chain_offsets`、`changed_chain_indices` | 每个候选实际变化链，用于增量事实复用 |
| `resource_row_offsets`、资源列 | 候选私有虚拟材/拆片行及谱系、用途、期锁等数值字段 |

这些数组只能使用明确宽度的整数、布尔值或本文规定的原生数值类型，不允许 `dtype=object`，不在内核中传递字典、列表、元组、数据类、规则对象或回调。共享当前方案和静态任务列只读；每个候选的工作区通过偏移隔离。

完整评分模式输出固定形状数组：

- `quality[batch_size, 9]`：九级评分；
- `status[batch_size]`：完成、结构无效、数值错误、取消或过时代次等状态码；
- `prohibited_count`、`prohibited_severity`、`underweight_count`、`underweight_gap` 等审计汇总；
- 旧欠清空、累计等待/延期负担、链间宽差、虚拟重量、链数等命名指标列；
- 违规规则类别位图或紧凑计数，用于主线程判断是否需要详细重放；
- 实际扫描节点/边/链数量及工作区容量状态，用于性能诊断。

普通拒绝候选不返回变长 Python 明细。只有主线程确定候选需要接受、输出阶段快照或执行最终审核时，才以“明细模式”重新调用同一套数值规则原语，把规则编号、原因编号、链/节点位置、严重度和指标写入预分配数值缓冲区，再由边界映射成 `NumericViolation`、`NumericMetric` 及领域对象。明细容量不足必须返回明确状态并由主线程扩容后重试，不能截断违规，也不能在内核内扩展 Python 列表。

动态桥接和拆单只要能把私有资源行放入上述批次布局，就可以使用同一内核；尚未具备私有批次布局时保持串行，但仍调用同一个单候选数值内核，不得回落到 Python 规则评价器。

## 7. 连接查询与初始解

### 7.1 完整连接语义编号

复用当前连接缓存按完整语义分配整数身份的思路，将实际使用的宽厚温、材料角色、软硬类别、热轧牌号及有效标记纳入语义键；规则身份和数值标准也是上下文的一部分。

不得只按宽度、厚度给规格编号，导致相同宽厚但不同软硬材或温区的订单错误共享连接结果。规则新增必需字段时，编译器必须同步更新语义键；缺少实现时明确拒绝。

### 7.2 有向数值缓存

在可控容量内使用 `int8` 表保存“未计算 / 允许 / 禁止”，按有向语义编号对查询；方向不能反转复用。规则严重度/原因按需重新计算或用紧凑数值记录保存，布尔表不能冒充完整规则评价。

- 先覆盖固定真实节点和原型；动态节点在串行边界登记新的语义身份。
- 只在实际需要时填充连接结果，除初始构图所需外，不强制预计算全部平方组合。
- 缓存容量是性能容量，不是业务容量；超过缓存容量的合法语义边直接使用同一数值连接内核，不回落对象、不判为禁止。
- 后续并行批次不直接扩容或写共享表；缺失边由主线程准备，或由工作线程在私有工作区用同一内核计算。提交缓存不是资源提交，仍要验证任务/规则身份。

### 7.3 有序邻接数组

初始构造沿用当前方向策略、节点/后继稳定排序以及匹配/路径覆盖逻辑。邻接关系使用压缩行布局：`offsets` 指出每个节点后继在 `indices` 中的位置。它是两个 NumPy 整数数组，不要求引入 SciPy。

邻接行必须保持算法约定的后继顺序，不能因为采用稀疏格式就按内部编码重新排序。数值化后的宽度、厚度、重量及优先级共同生成排序键，取消旧浮点排序投影。

**初始构造图的方向限制只是构造策略，不是全搜索的连接规则。**后续插入不能把构造图中的缺边当作不可连接，应查询第 7.2 节的权威有向连接。

### 7.4 直接插入位置

插入位置是否直连，由左端到插入节点、插入节点到右端两条有向边共同决定；首尾省略不存在的一条边。一次批量得到位置布尔数组，保持直接位置优先及同组稳定顺序。

不可直连的位置继续保留桥接机会，不能在数值过滤时直接删除。两个相邻边均可连接也不等于整链可行，仍需执行跨虚拟端点和连续规则。

## 8. 规则与评分的数值计算

### 8.1 规则映射与语义保持

下表描述新数值公式。具体阈值来自规则编译，不在计算函数硬编码；表中 20、200、700 等仅是当前冻结样本的示例。

| 规则 / 指标 | 数值判定或累计 | 必须保留的业务边界 |
|---|---|---|
| 逆宽幅度 | 真实到真实：`w_right-w_left <= L_real`；涉及生成虚拟：`abs(w_right-w_left) <= L_virtual` | 真实过渡材和普通真实材共用真实上限；示例 20/200 mm，不限制承接牌号 |
| 跨连续虚拟的真实端点 | 跳过一段或多段连续虚拟，检查前后真实端点净增宽 `<= L_real` | 先增后减也不能绕过真实端点限制；不只检查连续逆宽 |
| 厚度跳跃 | 按配置选择较厚/较薄基准；区间按原序首命中；绝对阈值或比例交叉乘积比较 | 保留区间开闭、默认档；不添加虚拟或过渡材新豁免 |
| 温区重叠 | `min(upper1,upper2)-max(lower1,lower2) >= minimum` | 忽略开关及虚拟自适应仍按配置；缺值策略不等于用零替代 |
| 软硬材连接 | 先按虚拟/真实过渡材策略，再判断普通材分类，缺类别时按热轧牌号策略 | 分类码分别表达，不能只比较节点牌号 |
| 高表面连续数量 | 逐段计数、逐段超限、每链保存最长值 | 只对规则认可的普通真实材计数；空等级、过渡材、虚拟材打断 |
| 普通窄钢连续重量 | 命中钢种及严格宽度上界的普通真实材逐段求重 | 材料角色或命中改变时断开；逐段报告，不只取最大段判断全部明细 |
| 同规格连续真实重量 | 按配置字段形成数值分组，逐个连续组累计重量 | 只对普通真实材；分组值与“非参与节点”标记不能混同 |
| 连续虚拟数量 | 生成虚拟材连续计数 | 真实过渡材不是虚拟；每段明细和最大段指标分别保存 |
| 逆宽总次数 | 保留当前规则的宽度基准：增宽时计数，非增宽时更新基准 | 不得改成“所有相邻增宽边数量”；缺宽度只清基准、不清累计数 |
| 连续逆宽 | 相邻增宽布尔值连续命中产生违规 | 配置启用才执行，不因整数化擅自启用当前停用规则 |
| 链重范围 | 全部节点重量求和，对上下限精确比较 | 欠下限可按规则允许偏差；超上限禁止；目标重量不是强制偏差 |
| 原单延后期 | 实际链期序大于真实节点来源期序 | 包含拆片；排得更早不因借用重量被额外惩罚 |
| 虚拟产出比例 | `virtual_weight * q <= total_weight * p` | 分母含全部真实和虚拟，严格按配置比例；零分母的空计划另作结构错误 |
| 填充目标 | 每链 `max(target-total_weight,0)` 求和 | 包含虚拟重量；默认诊断/动作依据，不新增评分项 |
| 拆单资格 | 角色、钢种、宽度、原安排期/来源期、父重、已拆状态、次数及片重上下限 | 同期和未来借入归还均保留；规则授权本身不生成或提交片段 |
| 链间宽差 | 按真实生产链序累计 `abs(前链末宽-后链首宽)` | 包括虚拟首尾及跨大辊期边界，不首尾闭环 |
| 交期表现 | 第 9 节整数时钟及原单最后片段统计 | 虚拟材占时、不算原单；晚交单数/吨位不偷偷进入评分 |

规则主体顺序、违规条数及原因含义保留。同一节点命中多个规则仍分别计数；审核明细可以延迟生成，但快速评价必须生成等价的数量和严重度。

严重度不是简单的“是否违规”。保留各规则的超限程度计算含义，按物理单位解释后再转换为统一的百万分之一严重度整数；不能直接把放大后的重量/宽度整数当作原单位严重度。涉及除法时用整数比值进行舍入，必须检查交叉乘积；零阈值分支需逐规则显式规定。零阈值的比例严重度在违规时取最低严重度 1，不用极小浮点分母制造巨量分数；此变化与逐条舍入均已获用户确认。

### 8.2 链摘要与全局指标

每链按规则身份保存重量、真实/虚拟重量、真实节点数、首尾、分组首尾段、最长连续段、逆宽状态以及违规数量/严重度。摘要长度由已启用规则决定，不为所有可能规则预建表。

- 未变链可直接复用链级评价，但实际所属期变化时必须更新期序相关规则。
- 连续段的合并必须处理边界相接；仅加两段最大值或两段违规数一般不正确。
- 保留基准式逆宽和跨虚拟真实端点检查若暂不能证明摘要合并正确，重扫受影响链的整数序列。重扫数值数组是正常实现，不是旧对象回落。
- 全局虚拟比例、来源覆盖、链序宽差和交期不可因链内内容未变而全部复用。

### 8.3 九级评分

当前专项保留已确认的欠重优先九级顺序，全部逐级最小化，不加权相加：

| 优先级 | 指标 | 数值评分单位 |
|---|---|---|
| 1 | 禁止违规数 | 条，整数 |
| 2 | 禁止违规严重度总和 | `10^-6` 严重度，逐条舍入后整数求和 |
| 3 | 欠重链数 | 条，整数 |
| 4 | 欠重总缺口 | 0.01 吨，逐链四舍五入后求和 |
| 5 | 旧欠订单全部完成用时 | 整秒 |
| 6 | 累计等待与延期负担 | 重量整数单位 × 整秒；输出时换算吨·小时 |
| 7 | 相邻链首尾宽差 | 第 4.1 节统一宽度单位 |
| 8 | 虚拟材重量 | 第 4.1 节统一重量单位；不再额外模拟浮点六位投影 |
| 9 | 非空小辊期数量 | 条，整数 |

在范围证明通过后，每候选评分可保存为 9 个 `int64`。不同列不要求同单位，只按列比较；同任务各候选必须共享单位。所有列相同即同分，不以未量化小数或其他统计暗中裁决。

评分排序从规则声明读取，不在内核把“第 5 项必定交期”写成不可变条件。首版数值编译器明确支持本文的声明组合；遇到其他有效规则组合须有对应覆盖与测试，不静默强行套九列。

### 8.4 权威完整评价内核与延迟明细

完整候选评价不能继续由“规则对象循环 → 每条规则生成结果对象 → 汇总对象 → 再组装九级评分”的路径承担。目标态只有一套权威数值事实计算，分为两个调用模式：

| 模式 | 使用时机 | 输出 | 对象边界 |
|---|---|---|---|
| 汇总模式 | 每个进入完整评价的候选 | 固定长度状态、违规数量/严重度、资源汇总、交期汇总、九级评分 | 不创建 `NumericRuleResult`、`NumericViolation`、`NumericMetric` 或领域结果对象 |
| 明细模式 | 被接受候选、必要阶段快照、最终审核/输出 | 在相同数值原语上增加规则编号、原因、主体位置、数值和严重度明细缓冲 | 内核返回数值缓冲；Python 仅在内核外映射对象与中文说明 |

两种模式必须共享以下数值原语：边规则、链连续段、链重及欠重、期序、虚拟比例、链间宽差、来源/资源、整数生产时钟和九级评分。明细模式不是调用旧 Python 规则评价器“再算一遍”，而是在同一原语上打开明细写入。这样既避免双实现漂移，也避免为大量最终被拒绝的候选分配变长对象。

完整内核的单候选形式先作为权威串行实现；批量串行只是对候选偏移循环调用该内核；Numba 并行只把同一个候选循环改为 `prange`。任何提前拒绝都必须返回明确状态，并证明未计算的评分后缀不可能改变决定。最终审核仍无缓存地重新准备事实并调用完整明细模式，不复用搜索候选的结果缓冲。

## 9. 交期、搜索排序与增量更新

### 9.1 唯一生产时钟

设起排为零、节点整数工时为 `d_j`，按生产位置累计 `E_j=sum(d_0..d_j)`。原订单 `i` 的完成 `C_i` 为其最后一个实际片段位置的 `E_j`；没有片段或重量不守恒不能得到合法完成结果。

设交期相对毫秒为 `D_i`：

- 旧欠集合：准备时冻结 `D_i <= 0` 的原订单；不读取求解过程中电脑日期。
- 旧欠清空：`max(C_i, i 属于旧欠)`，无旧欠为零，评分再量化整秒。
- 等待/延期：`wait_i=max(0,C_i-max(0,D_i))`。
- 第 6 项：先把每个 `wait_i` 四舍五入到整秒，再乘原订单权威重量并求和；不是乘每个拆片重量重复计分。
- 非旧欠晚交统计：`D_i>0 且 C_i>D_i`；等于交期边界不晚交。旧欠完成情况单独报告，不将其假称为本月新增晚交。

宽差、交期和输出必须使用同一生产链序；禁止评价器内单独排序。大辊期按权威期序稳定分组，组内顺序由候选决定。

### 9.2 候选排序也使用同一数值

最早交期、松弛量、旧欠完成先后、重量加权等待、关键节点后移潜力等全部由上述整数时钟与权威重量计算。它们是候选枚举依据，不是新增评分级。

保留既有重点/常规队列及原单片段回访策略；同分以稳定输入序号/原游标顺序裁决。不得一边用新毫秒评分，一边用旧 Decimal 结果给候选排序，否则仍有两套数值口径。

### 9.3 增量范围

- 整链调序：链内时长和规则摘要复用；改变链开始时刻，从最早变化生产位置更新完成时间及受影响原单贡献。
- 节点/片段移动：重算源/目标链内容和相关边界；时钟更新范围不能只包含这两条链，还包括两者之间或总时长改变后的下游。
- 虚拟新增/回收：总工时改变会传播到后缀，不能只检查被编辑链上的原单。
- 拆单：使用固定片段工时，重新定位该原单最后片段；其他原单的完成仍受插入/分隔材占时影响。
- 当后续节点顺序与旧方案相同且进入该后缀的累计整数时刻相同，才可整段复用。

整数累计在不溢出时可以按链/片段分组求和，允许真正的前缀与局部更新，不再承担复现旧 Decimal 每一步舍入的约束。但全量与增量必须按同一规范返回相同整数结果。

## 10. 接受、缓存与并行边界

### 10.1 完整候选的唯一接受点

候选计算输出数值评分、受影响链、资源变化与状态码，不直接修改正式方案。主控制逻辑按顺序：校验代次和描述、核对资源/期锁、完成所需评价、严格逐级比较、原子发布被接受的数值方案及索引。

“唯一接受点”不负责修复候选生成重复。进入该入口前，候选已经按第 6.5 节由结构归属唯一生成，并保持规范顺序；接受点不得依赖哈希集合跳过重复，也不得重排候选来掩盖生成器错误。

正式虚拟/拆分序号只在接受时推进；拒绝、取消和过期候选不写正式资源。合法性失败不能伪装成内核异常，内核异常也不能伪装成普通候选拒绝。

计算可以按评分前缀提前停止，但必须已经证明该候选不可能改善；禁止拿未计算列的默认零决定接受。完整审核和最终输出始终需要全部指标。

### 10.2 缓存有效性

| 缓存 | 有效依据 | 更新方式 |
|---|---|---|
| 字段与派生分类 | 输入、数值标准、启用规则/参数身份 | 每任务固定，动态节点按同规则生成 |
| 连接结果 | 完整有向语义、规则、数值标准 | 按需填充；不能跨任务混用 |
| 当前方案只读搜索索引 | 方案代次、节点目录代次、有序链结构 | 每个已接受代次建立一次；候选拒绝复用，接受或正式扩容后整体失效 |
| 链规则摘要 | 有序节点内容、字段、所属期、规则 | 未变复用，变化重算或经证明合并 |
| 时钟/原单贡献 | 当前生产序列、工时、原单片段位置 | 按第 9.3 节更新 |
| 候选结果 | 方案代次、描述、规则和数值标准 | 一次接受使旧批次后续结果失效 |

不以链编号相同、对象地址相同或“节点集合相同”代替有序内容身份。允许用版本和明确变化集合避免每次哈希全方案，但缓存命中必须有可验证依据。

### 10.3 并行准备与试点范围

本设计先要求完成第 8.4 节的权威数值串行内核，不把“有 NumPy 数组”直接等同于“可以使用多核”。候选并行的进入条件必须全部满足：

1. 完整候选评价入口是 Numba 可编译的函数或调度器，内核中没有 Python 对象、字典/列表增删、回调、异常对象构造或 Python 规则分派。
2. 任务列、规则数值表和当前方案为连续只读数组；候选输入按第 6.6 节扁平化，每个候选只写自己的固定输出行和私有工作区。
3. 单候选权威内核、批量串行内核及明细模式已完成差分验证；拒绝候选不会创建 Python 明细对象。
4. 候选顺序、逻辑额度、取消、首改善接受、正式编号、资源提交和过时代次处理仍由主线程掌握。

2026-09-16 的 256 候选试验不满足第 1～3 项：它用 1/2/4/8 个 Python 工作线程并发调用普通 Python `evaluate_numeric_overlay_candidate()`，因此 2/4/8 线程分别比单线程慢 1.84%/3.65%/7.48%，CPU 时间还增加 3.27%/10.89%/20.08%。这个结果用于否定“给现有 Python 评价器直接套线程池”，不用于否定完成内核后的 Numba 候选并行。

满足前置条件后，试点仍优先选择后置节点/片段候选的完整评价，覆盖受影响链规则、资源、交期和九级评分：

1. 主线程形成有界、无正式资源副作用的候选批次；候选共享只读属性，各有私有序列和工作数组。
2. 先调用同一内核的批量串行版本，再只把候选外层循环改为 Numba `prange`；不使用 Python `ThreadPoolExecutor` 作为 CPU 密集评价的生产后端，不新增 joblib/Dask 第二套后端。
3. 主线程按规范候选原顺序消费结果，不按哪个线程先结束接受；第一项改善被接受后，同代次尚未消费结果全部作废。
4. 预计算量与实际消费量分开统计，共享逻辑额度不得按线程倍增。取消后不发布批次结果；线程初始化、内核编译或工作区容量错误必须明确失败，不静默切换旧求解器。
5. 动态桥接或拆单尚未能批量表达时，继续调用同一单候选数值内核串行计算；不能让它们成为旧 Python 评价器的长期例外。

并行没有端到端收益时可以保留同一数值串行实现，不因此恢复双口径。NumPy 的线程安全要求、Numba 线程层以及 Windows exe 与目标机器的实际表现仍分别验证；本版不声称生产并行已经实现或通过。

## 11. 审核、输出与身份

### 11.1 双审计仍保留，口径统一

核心无缓存审核重新验证：全部来源覆盖、整数重量守恒、节点唯一性、片段授权、分片工时守恒、虚拟用途和比例、期锁/期序、全部启用规则、整条生产时钟及最终九级分数。应用审核继续检查请求/结果身份、输出映射和发布资格。

审核读取从冻结输入和最终方案重新建立的数组，以权威完整评价内核的明细模式无缓存重算，不信任搜索的链摘要、原单完成时间、质量数组或候选结果缓冲。这里的“独立”是输入重建、无缓存和重新执行，不是再维护第二套规则公式；“再次返回搜索已算分数”不算独立审核。测试还需用固定小例和迁移期 Python 参考路径核对内核语义，参考路径不进入最终生产求解。

最终只有规则允许的链重欠下限可以作为偏差发布；工艺禁止、超重、来源/谱系错误不能发布。当前 GQGA4 对照另要求零欠重，必须分开报告“通用可发布”和“本次质量门通过”。数值错误或审计失败不能伪装成超时后可发布的最好解。

### 11.2 结果对象与报告

- 仅在需要阶段快照、接受轨迹摘要或最终结果时生成边界对象；不得通过结果模型的旧构造副作用重新执行旧评分。
- 宽度/厚度/重量从整数与倍率恢复原单位，能精确还原的物理值不得改写；类别和身份由映射恢复。
- 完成日期从起排时间加权威毫秒生成，报告可显示秒级，也可保存毫秒明细；不得重新按旧工时重算后覆盖它。
- 九级指标保留用户可理解的原单位名称，例如小时、吨·小时、毫米；比较使用内部整数，显示转换不参与排序。
- 保留转换报告：数值标准、各字段倍率、工时量化单位、实际转换差值摘要、零工时片段数量、范围证明和未支持项。无需逐候选大量落盘。
- 继续每行日志带时间，记录准备、构图、首轮、拆分/重放、精修、审核的墙钟时间与进程 CPU 时间。

### 11.3 新数值身份与历史边界

复用现有 `numeric_semantics_key` 等身份机制，为本设计建立新的数值标准版本。绑定信息至少含：字段单位/倍率、时间单位、舍入规则、比较余量策略、严重度聚合、字段编码/规则编译版本。

数值指纹采用固定字段顺序、类型和字节序，只覆盖有效行及相关单位，不包含未使用容量、内存地址或进程随机哈希。物理行整理不得改变业务身份；不同任务使用不同倍率时，必须先按共同物理单位/标准重算才能比较结果。

取消旧浮点投影的目标声明要产生新声明/规则身份，不能让 `reference_float_round_6` 名称继续表示另一套整数算法。同一输入按新标准运行必须产生可区分的新请求/运行身份，不能保留旧指纹却替换内部语义。

首个验证入口建议由后端工具显式派生新的实验请求，不修改旧冻结文件或自动改活动规则数据库。未来切换正式服务时只保留一套当前求解实现，外部请求地址/字段不因内存布局自然改变；但涉及规则声明、版本绑定及服务适配的实际改动必须在后续实施计划列明，不能漏改审核或悄悄更新数据库。

历史输入/输出作为文件保留和对照，不要求当前引擎重跑旧数值语义，不新增 `legacy_float` / `legacy_decimal` 运行模式。回滚通过 Git 和既有版本恢复机制完成，而非长期保留双求解器。

## 13. 质量验证与性能测量设计

### 13.1 验证主线

**数据表示迁移要求行为一致；已确认的新数值标准允许出现单独解释的临界差异。**

| 检查层 | 验证内容 | 通过条件 |
|---|---|---|
| 数值转换 | 倍率、缺值、正负时间、四舍五入中点、范围、超精度输入 | 精确字段无损；时间量化符合声明；错误有定位 |
| 规则 | 开闭区间、恰等阈值、前后一个数值单位、零阈值、停用及未支持项 | 与新规则规范一致；不依赖旧浮点结果充当真值 |
| 资源 | 同期间/未来拆单、分隔、桥接回收、原单全部片段 | 重量及分配工时守恒、编号唯一、资源授权正确 |
| 交期 | 旧欠、本月订单、跨链/跨期、虚拟占时、最后片段、毫秒交期边界 | 独立重算与数值结果一致 |
| 评价 | 全量/增量、缓存开关、前缀拒绝、明细延迟生成 | 全部应得指标与接受决定相同，不能错误提前拒绝 |
| 完整数值内核 | 单候选、批量串行、明细模式，及旧 Python 评价的迁移对照 | 固定输入的状态、规则汇总、资源、交期、九级评分及明细逐项一致；普通拒绝候选不创建 Python 明细对象 |
| 搜索 | 每类动作、结构唯一归属、稳定首见顺序、4/64 轮转、额度、首改善与取消 | 同一数值标准下 Python 参考与 NumPy 路径的规范候选流、消费序号、接受轨迹和最终结果一致；实际生成身份无重复 |
| 并行 | 同一编译内核的批量串行与 Numba 2/4/8 线程、过期批次、资源隔离 | 全部固定输出数组、消费顺序、接受、最终结果一致；无竞争、编号抢占或 Python 回调 |
| 最终输出 | 双审计、报告/CSV/响应、原值还原和身份 | 输出与已审计数值一致，不把不同标准结果混用 |

关键小例包括：`FC→空→FC`；真实→多个虚拟→真实净逆宽；同宽厚不同软硬类别；链重/比例恰等边界；正负中点四舍五入（2.5 秒→3 秒、-2.5 秒→-3 秒）、欠重 1.005 吨→1.01 吨、严重度 1.0000005→1.000001；父工时无法平均分片但总和守恒；零毫秒片段仍必须覆盖；节点移动使下游订单跨交期；移除桥接使整条后缀提前；最后一个逻辑额度被接受/拒绝；无旧欠、无拆单和停用交期目标的任务。

候选生成另设结构计数小例：6 个原订单同处一条链时，5 个切分点和 2 种结果链位置只生成 10 个切链候选，不能生成 60 个再过滤 50 个；同一原单存在多个片段时，每个片段区间候选仍只有一个拥有位置；节点/片段交换的正反方向只能出现一个。测试可保存输出身份检查重复，但生产生成器不能依靠该检查去重。

完整评价另设对象边界见证：在违规/指标 Python 构造器替换为“调用即失败”的测试环境中，普通拒绝候选的汇总模式仍必须完成并得到相同九级评分；被接受候选再启用明细模式，明细数量、规则编号、原因、主体和严重度必须与汇总一致。固定候选还须依次比较单候选内核、批量串行内核和 Numba 2/4/8 线程输出，任何一列差异都禁止进入完整性能测试。

测试集中在数值标准、完整串行接线、并行/最终收口等必要检查点，不要求每次编辑或每个小提交都全量重跑。纯文档交付只做文档与工作区保护检查，不运行业务回归或完整排程。

### 13.2 表示等价与新数值标准如何分别比较

1. 固定同一批原始订单、规则配置含义、起排时间、速度、种子和 400000 次逻辑候选额度。
2. 先固定同一数值标准，对 Python 参考路径和 NumPy 路径比较规范候选身份、第一次出现顺序、通道、消费序号、接受序号、停止原因和最终结果；任一差异都属于表示迁移缺陷，不能继续完整性能验收。
3. 对旧生成器仅提取每个结构身份第一次出现的序列作为生成顺序参考；旧的重复出现次数是缺陷证据，不作为新候选额度要求。新生成器必须直接得到该序列，重复数为零。
4. 再记录旧数值标准及新数值标准的不同身份，不伪造同一个请求指纹；在固定方案和固定候选上解释单位、量化、隐式余量取消、严重度聚合造成的预期差异。
5. 表示等价通过后再分别完整求解；报告禁止规则、欠重、旧欠清空、本月晚交名单/吨位、累计负担、宽差、虚拟和链数。
6. 对适用的新标准，重算两份方案后比较质量；若旧方案因新临界判定而不合规，明确列出，不做无条件优劣排名。
7. 最终质量下降不能因“这是新口径”一笔带过；必须区分数值标准变化、已登记的候选唯一生成缺陷修复和意外搜索机会变化，给出是否值得采用的结论。
8. 新结果不得覆盖旧产物；当前本机样本不能替代 Windows 实包验收。

### 13.3 一分钟目标的测量口径

仍用完整绑定请求作可比输入：400000 次逻辑额度，历史性能请求 9999 秒搜索＋10 秒收尾；服务 YAML 的 300＋10 秒是另一运行配置，本次不修改。自然提前结束如实记录，不能强制补满额度。

测量覆盖输入准备、字段转换、连接/构图、初始方案、各搜索阶段、审核及结果构造；分别记录冷启动编译与已预热执行，不能把编译或数组准备悄悄排除在完整时间外。API 往返、诊断写盘时间另外列明。

至少记录：

- 完整和逐阶段经过时间、进程 CPU 时间；并行时不能只看主线程 CPU。
- 实际描述数、逻辑消费数、规则/完整评价数、接受数、批次作废数。
- 后置结构精修的规范结构候选生成数、候选消费数、各动作族数量、最长一次生成器推进耗时，以及完整方案物化和 `_layout()` 高频调用次数；有界测试另断言重复身份数为零。
- 业务对象构造次数、数组准备/拷贝/扩容次数、峰值数组字节与进程峰值内存。
- 汇总模式的 Python 违规/指标/完整评价对象构造次数；目标为拒绝候选全部为零。分别记录数值内核时间、批次整理时间、明细投影时间和主线程消费时间。
- 连接缓存命中、变化链扫描节点数、时钟更新长度、并行等待与批次最长耗时。
- 最终结果、停止原因、九级分数、规则与守恒审核。

先记录权威单候选内核和批量串行内核，再选择真正占时的候选评价做 Numba 并行。既要比较内核耗时，也要比较包含候选整理、主线程消费、接受后明细及最终审核的端到端耗时；不能只凭局部内核提速宣称求解提速。性能比较用同机、同输入、相同运行模式的重复样本，报告中位数和波动；具体样本数量在实施计划冻结。一分钟是优化目标，未测达不能标完成。

| 风险 | 处理 |

| 串并行各写一套规则或评分 | 规则只编译为一组数值表，单候选、批量和 `prange` 调用同一内核；差分未通过不接生产 |
| 变长违规明细迫使内核创建 Python 对象 | 热路径只返回固定汇总；明细模式写预分配数值缓冲，容量不足显式扩容重试，不截断 |

| 动态桥接/拆片无法批量表达 | 暂时串行调用同一单候选内核；完成私有资源数值布局后再纳入批次，不回落 Python 评价 |
| 以订单为入口重复展开链级/区间级动作 | 改由节点、明确区间、链或结构对直接拥有；原订单只决定优先顺序和通道，生产运行不使用生成后去重集合 |
| NumPy 改造夹带搜索流程变化 | 同数值标准冻结规范候选流、消费序号、接受轨迹和最终结果；数值标准差异另用固定候选验证并单列报告 |
| 为修复热点只缓存 Python 链列表 | 不采用该方案作为最终修复；按方案代次复用数值索引，保持 NumPy 结构为搜索事实源 |
| 摘要/缓存漏掉规则状态 | 全量无缓存对照，不能证明的连续状态重扫数值链 |
| 并行生成资源或破坏稳定顺序 | 只读批次、私有临时行、主线程原序接受、过期作废；正式编号只由主线程推进 |
| 把普通 Python 线程无收益误判为 Numba 无收益 | 只有权威内核可编译且无对象后才进行候选维度试验；同时报告内核和端到端结果 |
| 只移植 GQGA4 参数而损失多产线能力 | 按启用规则/参数覆盖表编译，未支持明报；不宣称未测产线可用 |
| 编译或平台行为差异 | 沿用已安装依赖；冷/热分测，Windows 实包后验，不在本文中增加兼容后端 |

## 15. 已确认设计决策

### 15.1 已确认方向

- 搜索、计算使用 NumPy 原生数值结构，不要求保留旧对象计算链路。
- 一个字段一份权威数值，能统一就统一，不为历史浮点/Decimal 差异做兼容。
- Python 对象改为 NumPy 数值结构本身不得改变求解阶段、动作集合、规范候选顺序、重点/常规轮转、候选额度含义、首改善接受和最终行为；同一数值标准下必须逐项等价。
- 已确认的新数值标准可以改变旧浮点/Decimal 的临界小数结果，但必须与表示迁移分开验证、分开归因；不能以此放弃同标准的行为等价。
- 后置结构精修按方案代次复用只读数值索引；候选生成、通道归属和快速过滤禁止恢复完整 Python 链容器。
- 候选按节点、区间、链或结构对的自然归属直接唯一生成，不允许先生成重复候选再用 `set`/字典过滤；新顺序等于旧逻辑中各结构身份第一次出现的顺序。
- 一个规范结构候选只进入一个搜索通道，并在执行结构/规则检查前恰好计入一次 40 万次逻辑额度；额度是上限，不要求候选穷尽后继续凑满。被接受前只物化受影响链，被接受后才发布完整下一代方案。
- “数值存储已完成”“部分向量/增量计算已完成”“完整数值评价内核已完成”是三个独立状态；阶段 7.4 已通过第三层的单候选串行验收，但批量内核和候选并行仍未完成，不能合并宣称。
- 完整候选评价使用唯一的数值事实内核；拒绝候选只产生固定长度汇总，不创建违规、指标或完整评价 Python 对象。接受候选和最终结果的明细从同一数值原语生成，不调用第二套 Python 规则评价器。
- 候选批量采用扁平原生数组和偏移；先完成权威串行内核及生产接线，再试点 Numba 候选维度并行。普通 Python 线程池的 256 候选无收益试验只否定直接套线程，不否定满足前置条件后的 Numba 试验。
- 主线程继续决定候选原序消费、逻辑额度、取消、首改善接受、正式资源编号和代次发布；并行不能改变这些算法语义。
- 按已同步实施计划执行；本轮只完成至 7.4，不直接继续阶段 8 或清理收口。未实施部分不能用既有代码授权代替验收。

### 15.2 四项数值约定：全部已确认

用户于 2026-09-15 确认本节全部四项约定，随后明确要求舍入改为四舍五入。以下以该最新要求为准；所有规定的量化点统一采用第 4.5 节的 `ROUND_HALF_UP` 语义，其余约定不变。

| 项 | 决策内容 | 已确认约定与影响 |
|---|---|---|
| 1 | 物理量/重量精度及超范围输入 | 每任务按字段从输入与参数选择精确十进制倍率；`int64` 全过程范围证明失败则明确拒绝数值求解，不舍入原重量、不启用旧求解器 |
| 2 | 时间量化与拆单工时 | 权威时钟用毫秒，四舍五入；原单总工时固定，按稳定片段序号分配且守恒；零毫秒派生片段可存在，评分继续整秒。临界交期可能变化 |
| 3 | 规则比较余量 | 移除旧内部 `1e-9`、`1e-6` 比较宽限，使用整数值和配置边界直接比较；工艺容差继续显式配置，虚拟比例也严格按配置判定 |
| 4 | 禁止严重度聚合 | 各规则严重度按物理单位计算，逐违规四舍五入到 `10^-6` 后整数求和；比例式零阈值违规严重度取 1，不再模拟旧浮点总和与极小分母 |

四项业务决策已经关闭，不再重复请求确认。实施计划直接以这些约定为依据，安排数值范围、舍入边界、工时守恒和结果质量验证。已获后续代码实施授权，但不授权自动切换生产配置或部署。

## 16. 术语与资料

| 名称 | 本文含义 |
|---|---|
| 定点整数 | 按固定倍率保存物理量，例如 12.63 吨在倍率 100 下存为 1263 |
| 列式数组 | 同字段连续存储，不是每个订单一个对象，也不是混合类型大表 |
| 压缩行邻接 | 一条后继编号数组加一条起止位置数组，保持各行后继顺序 |
| 方案代次 | 每次正式接受后递增的版本，防止使用旧位置/旧候选 |
| 结构归属 | 某类调整由节点、明确区间、链或结构对直接拥有，而不是由涉及的每个原订单分别生成 |
| 规范候选流 | 每个结构身份只出现一次、保持既有第一次出现顺序的候选序列 |
| 数值内核 | 直接读取原生数组、返回数值结果的计算函数，可由 Numba 编译执行 |
| 完整数值评价内核 | 在一套原生数值计算中完成规则、资源、交期和九级评分，串行、批量和并行共用 |
| 汇总模式 | 候选热路径只返回固定长度状态和评分，不构造变长违规/指标对象 |
| 明细模式 | 在同一数值原语上写出规则、原因、主体和严重度明细，供接受、审核和输出使用 |
| 候选维度并行 | 不拆分一个候选内部的规则，而是在外层并行评价多个相互隔离的候选 |
| 四舍五入 | 小于半单位舍去，达到半单位进一；中点远离零，例如 2.5→3、-2.5→-3 |
| 独立审核 | 从冻结事实重建并无搜索缓存重算，不是读取搜索返回的“通过”标记 |
