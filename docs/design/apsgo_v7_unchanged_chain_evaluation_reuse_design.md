## 3. 选择的方案

| 方案 | 取舍 |
|---|---|
| 保持全量评价，直接编译数值函数 | 仍重复处理未变链，并引入类型转换、依赖和打包成本；暂不采用 |
| 保存所有曾经评价的候选链 | 可能提高命中，但随历史候选增长，需要容量和淘汰策略；首版不采用 |
| **只保存当前已接受方案的链评价** | **采用。生命周期明确、内存有界，复用现有候选提交点** |

首版有意采用保守方式：第一个完整候选从空缓存计算；只有候选被正式接受后，才保存该候选的评价条目。拒绝候选不保留任何新条目，也不借机给当前方案补建缓存。若整轮没有一次采纳，则本项不会减少规则调用；这是为简化生命周期接受的已知限制，应实测而不是暗中扩展缓存。

## 4. 复用什么、不复用什么

### 4.1 数据条目

“规则原始贡献”指规则返回的违规明细及逐项指标 `RuleContribution`，不是最后已经汇总的分数。

每条长期保存的条目只对应当前已接受方案中的一条链，包含：

| 内容 | 用途 |
|---|---|
| 原 `Chain` 对象的强引用 | 验证本次候选确实使用同一不可变链，不仅仅是编号相同 |
| 完整链的原始 `RuleContribution` | 保存链级规则、相邻边规则和内部跨虚拟材检查的全部有序贡献 |
| 该链内逐节点的有序 `RuleContribution` | 复用未变链内订单的节点规则；不建立独立的跨链节点缓存 |
| 原 `ChainEvaluation` | 复用该链摘要及聚合结果；不能用它替代原始贡献 |

复用条目为核心内部数据，不进入 `PlanEvaluation`、`SearchState`、请求、响应、运行清单、方案指纹、规则配置或数据库。不把缓存追加到公共模型，避免改变已有序列化与身份。

### 4.2 每个候选仍必须重新计算

1. [`derive_evaluation_resource_view()`](../../src/apsgo_scheduler/core/resource_facts.py)：当前完整方案的真实、虚拟、借用等资源事实。
2. 全部方案级规则，包括延后计划期、虚拟比例、链间宽差、填充缺口等实际启用项；没有启用的仍不执行。
3. 按候选实际链序和节点序重新组装完整违规、原始指标、结构指标和七级质量键。
4. 原结构合法性、来源覆盖、拆单授权、期锁、正式虚拟编号、候选采纳和预算检查。

本次不复用 `quick_chain_prohibited_profile()` 的正反链快速检查，不在拆单资格判断、虚拟工厂或宽差预筛中引入其他缓存。初始方案仍走原无缓存评价。

## 5. 命中条件与失效规则

### 5.1 绑定范围

复用器是 [`SearchContext`](../../src/apsgo_scheduler/core/neighborhoods.py) 的私有状态，首次完整候选时懒建立。绑定当前 `SearchState`、当前已接受的 `SchedulePlan`、规则集及 `RuleEvaluationContext` 对象。

[`solver.py`](../../src/apsgo_scheduler/core/solver.py)已在首轮、拆单、拆后重放及宽差阶段间共享同一个 `SearchContext`；不新增各阶段独立缓存，不在 `__post_init__` 提前重算初始方案。

绑定身份变化时清空旧条目，重新冷算；不得只因为两份规则或上下文的文本指纹相同，就跨对象、跨任务共享。正常采纳后显式更新绑定的当前方案；外部直接替换当前方案不能误用旧条目。

### 5.2 单链命中

`chain_id` 只用作映射定位，命中还必须满足 `candidate_chain is cached_chain`。保存对象强引用，不单独保存 `id(chain)`，避免对象释放后编号重用。

| 场景 | 处理 |
|---|---|
| 当前方案原链对象，所属期和全部字段均未变 | 可命中 |
| 链内容相等，但重新创建了对象 | 未命中，重新评价；不做深度相等或指纹搜索 |
| 同编号但节点顺序、宽厚、重量、属性、角色、谱系或所属期改变 | 新对象，重新评价 |
| 同期整链调序，链对象保持 | 链内可命中；按新链序组装贡献，全局宽差重算 |
| 拆单、合链、切链、增减虚拟材 | 受影响的新链重算；其余同对象链可命中 |
| 从一条链移到另一条链的原节点 | 两条新链都重算；不额外复用移动节点贡献 |
| 缓存条目不属于当前已接受方案 | 不得命中 |

不通过改造各算子的对象创建方式来追求命中率，不把 `affected_chain_ids` 单独视为复用授权。

### 5.3 自定义规则兼容

当前 `Rule` 允许自定义实现，但没有通用“相同输入必得相同结果”的复用声明。不可变规则对象也不能证明其方法不读取外部状态。现有 `edge_semantic_fields()` 是边缓存专用契约，不能挪作整链评价的授权。

首版在核心评价模块维护一份小型、私有的**已核验内置具体类型集合**，采用精确类型判断：

- 核验所有实际启用规则及作用域派生规则；包括内部 `_VirtualBridgeWidthRule`，不能只检查公开配置列表。
- 规则分派本身也要求精确 `ProcessRuleSet` 类型；未知规则集子类可能覆写分派，同样回落无缓存，不拒绝输入。
- 任意启用类型未进入该集合，本次搜索不启用评价复用，继续调用原无缓存入口；不拒绝该规则、不改变加载或业务行为。
- 首版类型范围见实施计划阶段 1；逐个核验后显式列入，不按模块反射自动收集，不按名称或 `isinstance` 放行未知实现。
- 集合只表达已核验的计算确定性，不包含产线名称、业务阈值或第二套规则注册关系。不从 `core` 反向导入 `app.RULE_REGISTRY`。
- 不新增规则基类方法、公开能力开关或配置项。新增规则默认可用但暂不享受本优化，核验后再加入。

已核验类型仍通过原规则集执行。规则集合、版本、参数、启停或上下文更换均使旧绑定失效；不缓存“异常”“返回不完整贡献”或伪造默认值。规则执行中的异常继续沿现有错误路径传播。

## 6. 评价顺序与数值语义

生产只有一份完整评价的汇总逻辑。保留公开 `evaluate_plan(plan, rule_set, context)` 的三参数和 `PlanEvaluation` 返回值，始终无缓存；内部共用实现允许搜索侧提供可复用条目，并取得当前候选的临时条目。无缓存入口无需创建、保存这些条目。

内部组装顺序必须与现状一致：

1. 按当前候选链序，处理**全部链的完整链贡献**；未命中仍调用 `evaluate_complete_chain()`。
2. 然后按相同链序及链内节点序，处理**全部节点贡献**；未命中仍调用 `evaluate_node()`。
3. 最后执行方案规则，调用既有汇总和质量键计算。

不能改成“一条链贡献紧跟该链节点贡献”的交错顺序。未命中规则的执行也要保持原相对顺序，不能预先执行节点规则再延后追加结果。完整链内部沿用规则集原有链级/相邻边交织与派生检查，不手工拆成另一份调度器。

必须保留：

- 原始 `Decimal` 重量与指标，不提前转浮点或舍入。
- 欠重缺口逐项保留两位小数后求和，以及原半偶舍入；不能先按链或方案预聚合再舍入。
- SUM、MAXIMUM、COUNT 等声明的原始贡献数量与顺序。
- 重复违规及具体主体、原因、信息、严重度，不按链或规则去重。
- 禁止严重度按原序浮点累加及原投影方式，不用缓存分段求和改变顺序。
- 七级目标及严格逐级比较，不增添缓存命中率、借用或其他隐式裁决。

## 7. 候选生命周期与提交边界

唯一接入点是 `try_complete_candidate()` 中原完整评价的位置；其他算子只使用既有调用路径。

| 时点 | 行为 |
|---|---|
| 原结构、授权、编号和预算校验 | 全部保持原位置；未进入完整评价则不建立候选条目 |
| 进入完整评价 | 原 `complete_candidate_evaluation_count` 仍加一；复用只减少内部规则执行，不减少此计数 |
| 计算完整候选 | 只读当前方案条目，缺失部分调用原规则；在局部变量中形成完整评价与临时条目 |
| 质量不改善、专项保护失败或评价后预算耗尽 | 丢弃临时条目，长期条目仍对应原方案 |
| 原 `state.commit_accepted()` 之前 | 临时条目及全部可能失败的准备均完成；不提前更新长期缓存 |
| `commit_accepted()` 成功 | 将准备好的候选条目整体替换为当前条目；这里只作引用赋值，不再运行规则、分配大映射或插入新预算检查 |
| 提交失败或异常 | 不提升候选条目，不用候选污染原缓存；异常沿原路径传播 |
| 搜索结束 | 不向审计、结果或下一请求传递复用器；所有者释放后不再保留新增长期引用 |

原预算检查次数与位置、轨迹构造和记录、正式编号、拆单序号保持。正常接受之后的缓存赋值与原轨迹更新位于同一同步执行段，不引入锁、异步操作、回调或新事务框架。

内存随**当前方案加一个正在评价的候选**的节点和贡献规模增长，不随候选历史数量增长。采纳后旧方案条目退出长期映射；拒绝时临时映射退出作用域。已有轨迹或诊断工具可能另行持有历史对象，不能据此承诺整个进程的所有历史对象立即释放。

## 8. 最终审计和验证原则

[`audit_core_without_search_cache()`](../../src/apsgo_scheduler/core/final_audit.py)继续从权威问题建立新上下文，直接调用无缓存 `evaluate_plan()`；结果契约审计保持。禁止通过复用搜索结论来证明搜索结论正确。

现有审计部分比较使用违规多重集合，能够核对内容和重复数，但不能单独证明顺序完全一致。因此本专项另做完整 `PlanEvaluation` 逐字段、有序违规及指纹对照，不只看七级评分或“审计通过”。

| 验证层次 | 必须证明 |
|---|---|
| 聚焦评价测试 | 同对象命中、所有失效条件、原始贡献和顺序、精度、停用和未知规则回落 |
| 搜索生命周期测试 | 接受才提升；拒绝/异常/取消/提交失败不污染；所有搜索阶段共用；规模不累积 |
| 独立审计测试 | 审计不访问复用器；故意污染搜索评价仍被独立重算识别 |
| 固定工作量真实对照 | 初始/首轮/完整方案、全部有序评价、轨迹、来源及拆单事实、正式计数、停止原因一致 |
| 同机无分析器配对 | 记录首轮与完整服务的经过时间和 CPU，验证实际收益及是否出现阶段回退 |
| 独立函数分析 | 实际链/节点规则执行下降，区分冷算、命中和全局重算；不把分析器耗时当性能样本 |
| Windows 实包 | 明确提交/包身份、同输入配置、真实 EXE 与审计；缺条件仍记待验 |

固定工作量下允许实际链/节点规则调用次数、内部对象创建和内部指纹备忘录统计变化；候选检查数、完整候选评价数、采纳轨迹和公开边缓存统计不得因此改变。完整链评价原本直接经规则集执行，不使用 `RuleEdgeDecisionCache`；本次不得将其改道以“优化统计”。

墙钟限时下加速可能改变截断位置及最终方案，须另记为限时实验；同一工作前缀的决策差异仍是缺陷。全部原始样本保留，收益不稳定或回退时不得调整质量门、预算、选样方式来换取通过。

## 9. 已确认决策与后续

用户于本轮确认按实施计划持续推进，以下方案作为代码实施依据：

1. 仅当前已接受方案、同对象复用；拒绝候选不缓存，首次候选冷算。
2. 同时复用未变链的完整链贡献、节点贡献和链摘要；全局评价与最终审计不复用。
3. 未核验自定义规则保守回落，不扩展规则基类或引入依赖。
4. 先以已优化 Python 基线做同工作量验证和同机测量，不预设提速百分比。

若实际命中率低或收益不足，先报告具体原因；跨候选历史缓存、独立节点缓存、数值编译或增量全局评分均属于后续新范围，不在实施时自动加入。
