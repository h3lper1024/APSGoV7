# APSGo V7 Windows EXE 发布打包详细设计

## 1. 文档状态与适用范围

| 项目 | 内容 |
|---|---|
| 版本 / 日期 | v0.1 / 2026-09-08 |
| 状态 | 设计完成，待按实施计划执行；代码、构建脚本和 Windows 实包尚未实施 |
| 当前代码基线 | `codex/rule-setting-api-integration@c8c26dff96c6bd290c41afba0d0d7405d6b2d337` |
| 适用系统 | 64 位 Windows；确切 Windows 版本须在目标部署机验证 |
| 构建环境 | Conda `aps_3.10.18`，Python 3.10.18 |
| 发布对象 | APSGo V7 规则设置与 GQGA4 月计划求解 HTTP 服务 |
| 配套计划 | [Windows EXE 发布打包实施计划](../implementation/apsgo_v7_windows_exe_release_packaging_implementation_plan.md) |

本文设计将 APSGo V7 打包为可在未安装 Python 和 Conda 的 Windows 电脑上运行的服务程序。发布包继续提供现有规则查询、规则保存并启用、GQGA4 月计划求解三个 HTTP 接口，不改变请求、响应、规则、求解流程、评分或 C# 客户端契约。

用户已确认 `data/apsgo_v7_rules.sqlite3` 可以由 Git 跟踪。本文据此把仓库中的数据库定义为“发布基准库”，但不把部署现场持续写入的数据库反向等同于仓库文件。

## 2. 目标与非目标

### 2.1 目标

1. 在 64 位 Windows 上生成可独立运行的 `APSGoV7Service.exe`。
2. 目标电脑不需要安装 Python、Conda 或项目依赖。
3. 保留当前 YAML 作为唯一服务运行配置来源。
4. 保留 SQLite 规则版本、虚拟原型和软硬钢字典的可写与持久化能力。
5. 使发布内容能够关联到准确 Git 提交、配置、规则数据库和构建环境。
6. 支持首次部署、正常启停、程序升级、数据备份和失败回退。
7. 在 Windows 实包上完成规则读取、规则写入后重启、完整 GQGA4 求解和局域网访问验证。

### 2.2 非目标

- 不修改求解算法、规则语义、七级评分、时间预算或候选检查次数。
- 不修改现有 HTTP 地址、字段、状态码和 C# `PipelineV7ApiBaseUrl` 读取逻辑。
- 不在本阶段制作 MSI 安装包、自动更新器、Windows 服务注册器或托盘程序。
- 不新增第二套环境变量配置，不把端口或数据库路径重新移出 YAML。
- 不把登录鉴权、TLS 证书或公网部署纳入本次打包；局域网边界沿用用户已确认范围。
- 不在 macOS 上声称已生成或验证 Windows EXE。
- 不把历史 V3 的日计划数据库、GQPT 训练数据、GQGA5 Worker 或其他产线资源带入 V7。

## 3. 当前实现事实

| 对象 | 当前事实 | 设计影响 |
|---|---|---|
| Python 包结构 | `src/apsgo_scheduler` 与 `src/apsgo_v7_service` 的 `src` 布局 | PyInstaller 入口必须把 `src` 加入模块搜索路径，不能按仓库目录名导入 |
| 服务入口 | `apsgo_v7_service.app:main`，支持 `--config` | 使用极小冻结入口调用既有 `main()`，不复制启动逻辑 |
| 生产依赖 | FastAPI、PyYAML、Uvicorn；其余求解核心使用标准库 | 先依靠 PyInstaller 常规分析，仅显式收集 Uvicorn 动态子模块 |
| 并发方式 | Uvicorn 单 worker；求解任务通过线程池执行 | 当前不需要复制 V3 的多进程包名注入和 Worker 入口 |
| 配置 | `config/apsgo_v7_service.yaml` | 构建为不同文件名的配置模板；首次启动生成现场配置，升级时不覆盖 |
| 数据库路径 | YAML 中为 `../data/apsgo_v7_rules.sqlite3`，按配置文件目录解析 | 发布目录保持 `config/` 与 `data/` 同级即可沿用现有配置 |
| 监听 | YAML 当前为 `0.0.0.0:8001` | EXE 不覆盖监听地址；C# 使用部署电脑的真实局域网 IP |
| 求解策略 | 总时限 310 秒，其中 10 秒收尾；候选检查上限 200000 | 打包不改变当前求解策略；C# 既有等待超时继续生效 |
| 规则数据库 | 已由 Git 跟踪；schema v2 | 仓库数据库是发布输入，SQLite sidecar 文件仍不得跟踪 |
| 当前活动快照 | 现场核验为活动版本 5、17 条规则、27 个虚拟原型、230 条字典 | 作为本次文档基线；正式发布以构建时重新核验并写入清单的值为准 |

V7 的默认配置路径是相对当前工作目录的 `config/apsgo_v7_service.yaml`。发布启动脚本必须先切换到自身目录，并把配置绝对路径传给 EXE，不能依赖用户从哪个目录或快捷方式启动。

## 4. V3 打包方案的借鉴边界

### 4.1 可直接借鉴的发布主干

V3 的 `release/build_exe.bat` 只转调 `build_exe.ps1`，PowerShell 脚本完成输入预检、PyInstaller 构建、外部资源复制、哈希核对以及启停脚本生成。V7 继续使用这一层次划分：

1. `build_exe.bat` 提供双击和命令行入口；
2. `build_exe.ps1` 是唯一构建编排入口；
3. 构建前先验证环境、配置和数据库；
4. 生成控制台 EXE；
5. 配置与可写数据库留在 EXE 外部；
6. 构建结果记录文件摘要并执行 Windows 冒烟测试；
7. 生成按自身路径启动和精确停止的批处理文件。

本机核验来源为 `/Users/miles/dev/dev-py/apsgo-v3/release/build_exe.ps1` 和 `/Users/miles/dev/dev-py/apsgo-v3/doc/frontend_backend_scheduling_solution_design.md`。V7 已在本节完整写明吸收行为，不把这些外部绝对路径作为 Windows 构建机的必要入口。

### 4.2 不照搬的 V3 内容

| V3 做法 | V7 处理 |
|---|---|
| 根据仓库目录名构造 Python 包名 | 固定导入真实包 `apsgo_v7_service`，只把 `src` 加入搜索路径 |
| 动态注入 V3 包名并加载多进程 Worker | V7 当前只有线程池，不引入未使用的多进程适配 |
| 收集整个 Conda 环境中的 DLL/PYD | 先使用 PyInstaller 分析和官方 hook；仅在 Windows 错误证据明确时补缺失依赖 |
| 携带日计划种子、训练数据和多产线配置 | 仅携带 V7 YAML 与受跟踪 GQGA4 规则数据库生成的发布种子 |
| 通过环境变量指定 host、port、规则库 | 继续使用 V7 已验证的 YAML 配置 |
| 默认构建环境 `apsdemo_3.10.18` | 使用项目已确认的 `aps_3.10.18` |
| 单文件模式 | 首版选择目录式发布；理由见下一节 |

## 5. 打包方式选择

PyInstaller（Python 应用冻结打包工具）支持目录式发布和单文件发布：

| 方案 | 说明 | 优点 | 局限 | 结论 |
|---|---|---|---|---|
| 目录式发布 `onedir` | 一个 EXE 与 `_internal` 依赖目录 | 启动快、问题容易定位、无需运行时解压 | 交付文件较多 | **首版采用** |
| 单文件发布 `onefile` | Python 代码和依赖压入一个 EXE | 程序文件更集中 | 每次启动解压；YAML 与可写 SQLite 仍须外置 | 保留为后续可选项 |
| 仅发布 wheel | 目标机安装 Python 后安装项目 | 构建最简单 | 不满足目标机无需 Python | 不采用 |

即使使用单文件模式，V7 仍必须携带 YAML 和可写 SQLite，交付物并不会成为真正的单文件。目录式发布更适合当前服务首次落地和 Windows 联调。若后续确认目录文件数量带来实际运维问题，只调整 PyInstaller 构建方式，不修改业务代码、HTTP 或数据库契约。

官方资料：

- [PyInstaller Manual](https://pyinstaller.org/en/stable/)：PyInstaller 不是跨平台编译器，Windows 程序需要在 Windows 上构建。
- [Using Spec Files](https://pyinstaller.org/en/stable/spec-files.html)：单文件模式中的附加数据在临时目录展开，对嵌入数据的修改不会作为持久数据保留。

## 6. 目标发布目录

```text
release/dist/APSGoV7/
├─ APSGoV7Service.exe
├─ _internal/
├─ start_apsgo_v7_service.bat
├─ stop_apsgo_v7_service.bat
├─ release_manifest.json
├─ README.md
├─ config/
│  └─ apsgo_v7_service.example.yaml
└─ data/
   └─ apsgo_v7_rules_seed.sqlite3
```

`release/build/` 和 `release/dist/` 都是构建产物，不进入 Git。Git 只跟踪构建脚本、冻结入口、构建依赖声明、验证代码、设计与实施记录，以及仓库根 `data/apsgo_v7_rules.sqlite3` 发布基准库。首次正常启动后，同目录会新增 `config/apsgo_v7_service.yaml` 现场配置和 `data/apsgo_v7_rules.sqlite3` 运行库；正式压缩包在交付前必须删除冒烟产生的这两个运行文件，只保留配置模板和数据库种子。

## 7. 服务冻结入口与依赖收集

### 7.1 冻结入口

不能把 `src/apsgo_v7_service/app.py` 当作普通脚本直接执行，因为该模块使用包内相对导入。发布入口保持最小职责：

```python
from apsgo_v7_service.app import main


if __name__ == "__main__":
    main()
```

入口不重复解析 YAML、不自行创建 FastAPI、不覆盖监听地址、不直接调用求解器。当前代码未使用进程池或子进程，因此首版不增加 `multiprocessing.freeze_support()`；未来只有在引入 Windows 多进程并出现真实冻结需求时再增加。

### 7.2 依赖收集

构建从 `pyproject.toml` 的现有生产依赖出发：

- FastAPI；
- PyYAML；
- Uvicorn；
- `apsgo_scheduler`；
- `apsgo_v7_service`。

Uvicorn 会按字符串选择部分协议实现，首版构建显式收集其子模块。不要复制 V3“扫描 Conda 全部 DLL/PYD”的做法；若 Windows 实包出现明确的缺失模块或 DLL，再以错误信息和最小复现补充，不能预先把整个环境塞进发布包。

PyInstaller 仅属于构建依赖，不加入 V7 生产 `dependencies`。实施时先在 `release/requirements-build.txt` 写入一个精确候选版本并随构建脚本提交，再从该提交的分离 worktree 由开发人员显式安装和试构建；若失败，以独立 `#fix` 提交更新候选或脚本。Windows 构建通过前，该阶段不得标记完成；后续正式发布不得静默升级，构建脚本也不得自动安装或升级。

## 8. 配置与启动设计

启动脚本的核心行为固定为：

1. 使用 `%~dp0` 取得脚本所在目录；
2. `cd /d "%~dp0"`，消除调用目录差异；
3. 检查 EXE、配置模板和数据库种子是否存在；
4. 仅当现场配置不存在时，从模板复制为 `config\apsgo_v7_service.yaml`；
5. 仅当运行库不存在时，从种子复制为 `data\apsgo_v7_rules.sqlite3`；
6. 现场配置或运行库已存在时绝不覆盖、合并或重建；
7. 执行 `APSGoV7Service.exe --config "%~dp0config\apsgo_v7_service.yaml"`；
8. 进程异常结束时保留退出码和控制台错误信息。

不在启动脚本设置 `listen_host`、`listen_port`、数据库路径或求解预算。配置仍完全来自 YAML。目前 `listen_host: 0.0.0.0` 表示服务监听本机所有 IPv4 网卡；其他电脑应访问 `http://部署电脑局域网IP:8001`，不能使用 `0.0.0.0` 作为客户端地址。

停止脚本借鉴 V3：按发布目录中 `APSGoV7Service.exe` 的完整绝对路径筛选进程，只停止这一份发布实例，不按端口、不按所有同名进程、更不能终止全部 Python 进程。

## 9. 规则数据库生命周期

### 9.1 三种数据库身份

| 身份 | 路径示例 | 是否由 Git 跟踪 | 是否允许运行时写入 | 用途 |
|---|---|---:|---:|---|
| 仓库发布基准库 | `data/apsgo_v7_rules.sqlite3` | 是 | 开发时只允许有意识地更新并单独审查 | 正式构建输入 |
| 发布种子库 | `release/dist/APSGoV7/data/apsgo_v7_rules_seed.sqlite3` | 否 | 否 | 新安装的初始数据；升级时只更新种子，不覆盖运行库 |
| 部署运行库 | `部署目录/data/apsgo_v7_rules.sqlite3` | 否 | 是 | 规则查询、保存、启用和求解实际使用 |

这不是三套需要人工同步的规则来源：仓库基准库是唯一受控来源，构建时生成逻辑上不可变的种子，新安装时再一次性生成可写运行库。这里的“不可变”是构建和运行流程约束，不给 Windows 种子设置会随复制传播的只读文件属性；生成的运行库必须保持可写。保留不同文件名是为了防止新版压缩包覆盖解压时误覆盖现场规则；该数据保护不能通过“操作人员记得不复制 `data/`”替代。SQLite 的 `-wal`、`-shm`、`-journal` 文件都是运行时 sidecar 文件，不进入 Git 或正式发布包。仓库发布基准库的任何变化必须连同活动版本、规则指纹、字典指纹和摘要一起验证，不能只看二进制文件是否变化。

### 9.2 构建种子库

正式构建必须从准确 Git 提交的干净工作树读取基准库，复用现有 `backup_sqlite_database()` 通过 SQLite Backup API（一致性备份接口）生成发布种子，而不是在服务可能写入时裸复制主文件。生成后至少检查：

- `PRAGMA integrity_check` 为 `ok`；
- schema 版本和完整对象定义可被当前 `RuleStore.open()` 接受；
- 外键检查无记录；
- 存在唯一 GQGA4/default/month 活动版本；
- 活动规则能够编译和加载；
- 规则数、虚拟原型数、软硬钢字典数符合构建时清单；
- 源基准库和发布种子的逻辑内容身份一致。

### 9.3 首次启动、升级与回退

- **首次部署**：运行库不存在时，启动脚本才从种子复制；种子缺失或复制失败则服务不启动。
- **正常运行**：所有规则保存和启用只写部署运行库，不修改种子或仓库基准库。
- **程序升级**：先停止服务并备份运行库，再替换 EXE、`_internal`、配置模板和数据库种子；默认保留运行库和现场 YAML。
- **数据库升级**：只有代码明确要求新 schema 时，执行独立迁移；不能靠覆盖数据库完成升级。
- **失败回退**：恢复旧 EXE、旧 `_internal`、旧配置模板和升级前运行库备份；现场 YAML 默认保留，只有它在升级中被人工迁移时才恢复对应备份。
- **发布新默认规则**：在仓库基准库中有意识地完成规则变更、验证并提交；它只影响新安装种子，不自动覆盖既有部署。

若部署到 `Program Files` 等普通用户不可写目录，规则保存会失败。首版便携发布应放在具有写权限的专用目录；以后若必须安装到受保护目录，再把数据库配置到 `ProgramData` 等独立可写位置。

## 10. 构建编排

### 10.1 构建前检查模式

`release/build_exe.bat -CheckOnly` 必须真正做到只读：

- 不安装 PyInstaller；
- 不生成临时入口或 `.spec`；
- 不创建、删除或覆盖发布目录；
- 不复制或修改数据库；
- 只检查 Windows x64、Conda 环境、Python 版本、构建依赖、Git 状态、配置加载和数据库身份。

这里的只读边界是项目工作树、源数据库和发布目录零写入，并设置 `PYTHONDONTWRITEBYTECODE=1`；不对 Conda、操作系统或安全软件自身缓存作不可验证的“全系统零写入”承诺。这修正了 V3 `CheckOnly` 仍会创建项目目录、甚至可能安装 PyInstaller 的边界，不照搬该副作用。

正式构建目录必须是目标提交创建的全新、分离 Git worktree（Git 独立工作目录）。它既保持工作树干净，又保留 `.git` 元数据，构建脚本可以直接读取并校验提交号。`git archive` 仍用于各提交的源码测试，但不作为正式构建目录，因为归档不包含 Git 元数据。发布清单以提交号为权威身份；分支名只作可空的辅助信息。

### 10.2 正式构建顺序

1. 校验当前处于 64 位 Windows，解析 Conda `aps_3.10.18` 的 `python.exe`。
2. 校验 Git 提交、精确工作树状态和发布输入文件均已跟踪。
3. 加载 YAML，并确认数据库路径指向仓库发布基准库。
4. 校验活动规则快照，记录活动版本和各项指纹。
5. 清理本次 `release/build` 和 `release/dist/APSGoV7`。
6. 生成一致性数据库种子。
7. 使用 PyInstaller `onedir + console` 构建 EXE。
8. 把源 YAML 复制为配置模板，生成启动、停止脚本并复制发布说明。
9. 计算 EXE、依赖目录、配置模板、种子数据库、启停脚本和发布说明摘要，写入发布清单。
10. 在发布目录执行静态核对；真正运行验证进入 Windows 验收阶段。

构建失败时保留可诊断日志，但不得把半成品发布目录标记为可交付结果。下次构建使用 `-Clean` 从头生成，不在失败产物上补文件。

## 11. 发布清单

`release_manifest.json` 是机器生成的只读发布证据，不是运行配置。至少记录：

- 应用名称和项目版本；
- Git 提交、可空分支名和构建时间；
- Windows 架构、Python 版本、Conda 环境名、PyInstaller、FastAPI、Uvicorn 和 PyYAML 的实际版本；
- EXE 和 `_internal` 文件集合摘要；清单不计算自身摘要；
- 配置模板、启动脚本、停止脚本和发布说明的相对路径及 SHA-256（文件内容摘要）；
- 仓库基准库和发布种子的相对身份及 SHA-256；
- SQLite schema 版本；
- 活动版本 ID、规则数、虚拟原型数、字典数；
- 规则指纹和字典指纹；
- 构建模式 `onedir`、控制台模式和入口模块；
- 构建与验证状态。

清单不得包含订单明细、密码、访问令牌或数据库连接密码。

## 12. 发布与运行验证

| 层级 | 验证内容 | 通过条件 |
|---|---|---|
| 源码预检 | 入口导入、YAML、数据库、Git 跟踪状态 | 无错误，身份完整 |
| Windows 构建 | PyInstaller 目录式控制台构建 | EXE 和 `_internal` 完整，构建退出码 0 |
| 空白目标机 | 未安装 Python/Conda 的 Windows x64 | `APSGoV7Service.exe --help` 正常 |
| 首次启动 | 仅有配置模板和种子，无现场配置与运行库 | 自动生成现场配置和运行库并成功监听 YAML 端口 |
| 规则读取 | 调用现有 GET 接口 | HTTP 200，活动版本和数量与发布清单一致 |
| 规则持久化 | 在验收副本保存并启用规则，停止后重启 | 新活动版本仍能读取，证明运行库外置可写 |
| 月计划求解 | 使用冻结 531 单与正式求解策略调用现有 POST 接口 | 可发布、零禁止违规、零欠重、来源与重量守恒、双审计通过 |
| 求解一致性 | 同提交、配置、数据库、请求、随机种子 | EXE 与 Python 入口的发布质量和核心身份一致；耗时单独记录 |
| 局域网 | 第二台电脑访问部署机 IP | 规则 GET 和授权范围内的求解请求可达 |
| 精确停止 | 执行停止脚本 | 只停止当前目录对应 EXE，无残留实例 |
| 升级演练 | 备份运行库后替换程序文件 | 现场活动规则和历史版本不丢失，失败时可回退 |

V7 当前没有独立健康接口，因此首版用“EXE 进程已监听 + 活动规则 GET 返回 200 且身份匹配”作为服务冒烟。是否新增健康接口属于单独的 HTTP 契约需求，不由打包任务顺带增加。

打包验收不重新定义求解质量门槛或性能门槛。发布功能验收使用当前服务 YAML 的 310 秒总时限，并要求在 C# 的 370 秒等待上限内返回；历史 180 秒算法性能门槛是另一份冻结策略，不能用本次 310 秒运行宣称通过。是否继续单独执行 180 秒性能验收，以现有算法验收计划或用户后续确认处理。完整 GQGA4 的业务质量继续使用现有规则、审计和基线；EXE 耗时与相同输入的 Python 入口成对记录，出现明显退化再定位打包依赖或运行环境，不能反向放宽业务门槛。

## 13. 风险与控制

| 风险 | 影响 | 控制方式 |
|---|---|---|
| 在 macOS 构建 Windows EXE | 产物平台错误或根本无法生成 | 只在 Windows x64 构建并验收 |
| 构建时数据库仍在被写入 | 发布种子与声明身份不一致 | 干净提交、活动快照校验、SQLite Backup API、构建后回读 |
| 升级覆盖运行数据库 | 丢失现场规则版本和字典历史 | 种子与运行库使用不同文件名，已有运行库永不覆盖，升级前备份并演练 |
| 升级覆盖现场 YAML | 丢失端口、路径或预算等现场设置 | 配置模板与现场配置使用不同文件名，已有现场配置永不覆盖 |
| 发布目录不可写 | 规则保存失败，SQLite 无法生成 sidecar | 使用可写部署目录或显式配置独立数据目录 |
| Uvicorn 动态模块漏包 | EXE 启动失败 | 首版收集 Uvicorn 子模块，Windows 空白机真实启动验证 |
| 盲目复制全部 Conda DLL | 包体过大并引入无关依赖 | 只补真实缺失依赖，保存错误证据 |
| YAML 与 EXE/数据库不匹配 | 启动失败或使用错误数据 | 发布清单记录三者摘要，作为一套发布 |
| 防火墙阻止 8001 | 其他电脑无法访问 | Windows 部署验收明确检查端口与入站规则；不由程序静默修改防火墙 |
| 杀错进程 | 影响其他服务 | 停止脚本按 EXE 完整路径匹配 |

## 14. 设计决策汇总

1. **采用 Windows x64 原生构建**，不做 macOS 到 Windows 的交叉打包。
2. **首版采用 PyInstaller 目录式控制台发布**，不追求形式上的单文件。
3. **复用现有 `apsgo_v7_service.app:main`**，只增加极小冻结入口。
4. **YAML 是唯一运行配置来源**，发布模板与现场配置分名，启动脚本只在现场配置不存在时初始化。
5. **仓库规则数据库可以并且需要被 Git 跟踪**，作为可审计发布基准。
6. **发布种子库与部署运行库分离**，已有运行库永不覆盖，程序升级必须保留现场规则数据。
7. **复用现有 SQLite Backup API 和规则快照加载能力**，不写第二套数据库复制逻辑。
8. **不照搬 V3 全环境 DLL 收集、多进程入口和专属资源**。
9. **发布结果必须带构建清单并经过空白 Windows 目标机、完整求解和持久化重启验收**。
10. **首版是便携目录，不包含安装器、系统服务、自动升级、代码签名和新健康接口**。
