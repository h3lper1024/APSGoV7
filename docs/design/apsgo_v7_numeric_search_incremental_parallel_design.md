本设计替代上一版“保留原对象计算、补查询索引和缓存、最后仅试整链多进程”的技术路线，改为：**建立紧凑的搜索计算视图，减少完整候选构造和重复计算，再对独立候选的数值计算进行有序并行。**

仍采用一份设计、一份实施计划；实施顺序是阶段 0 核对基线，然后依次完成数据结构、缓存与按需评价、候选并行。允许必要的评价层重构，不以最少改动行数限制已确认范围；也不另造规则平台、调度框架或另一套排产算法。

目标是在相同输入、40 万次逻辑候选额度和相同接受语义下，将完整求解耗时向一分钟压缩。**一分钟不是 60 秒截断搜索，也不是已经达到的结论。**本轮已获授权继续第二阶段，不改依赖、规则库、正式配置、前端或发布包，不启停服务、创建分支、合并或推送。

第一阶段实际结果见[执行记录](../implementation/evidence/apsgo_v7_numeric_search_incremental_parallel/stage1.md)：共享/精确导出各 4095 项回归通过，两次完整 40 万次与原版业务等价；新版 1123.22 / 1152.12 秒，对照 1126.14 秒，未体现稳定提速。数据基础通过验证不等于一分钟目标完成；第二阶段依据用户后续明确授权开展，见[第二阶段记录](../implementation/evidence/apsgo_v7_numeric_search_incremental_parallel/stage2.md)。

第二阶段共享/精确导出各 4110 项通过；完整影子与两次正常 40 万次的方案、评价、轨迹及逐单精确日期均与原版一致，双审计通过。正常 720.47 / 739.98 秒，平均较第一阶段两次降低约 35.81%；完整候选评价 172312→881，但结构构造和部分精确评分仍保留，不代表全部计算削减 99.49%。本机两次观察不是 Windows 或正式多样本性能验收；一分钟目标未达，尚不进入第三阶段。

## 3. 不改变的业务与搜索契约

### 3.1 九级评分与数值口径

以下九项均最小化，按原声明顺序逐级比较，不是加权求和，也不是平级目标。

| 优先级 | 指标 | 保持要求 |
|---|---|---|
| 1 | 禁止违规数量 | 按原违规记录计数，不能改成“是否违规”或按订单去重 |
| 2 | 禁止违规严重度 | 沿原贡献、投影和汇总顺序，不改公式 |
| 3 | 欠重链数量 | 原链重下限及比较边界不变 |
| 4 | 欠重总缺口 | 每链按既有两位半偶舍入后汇总；原始重量不先舍入 |
| 5 | 旧欠订单全部完成用时 | 所有旧欠原单完成时刻的最大值，评分按既有整秒处理 |
| 6 | 累计等待与延期负担 | 沿原单重量、完成时间、交期及现有秒级公式 |
| 7 | 相邻链首尾宽差总和 | 包括跨大辊期边界、实际虚拟端点；不首尾回接 |
| 8 | 生成虚拟材重量 | 按现有资源定义，不以毛回收量代替净消耗 |
| 9 | 非空链数量 | 不设最多 22 条链门槛 |

本月晚交单数/重量保留统计，不新增评分项。原七级、其他九级及未知规则组合不强行套本表；无法证明适用的执行方式回到现有通用评价。

### 3.2 顺序、资源、时间和审计

- 原订单输入序、权威大辊期顺序、借用和拆单权限、拆片期锁、材料角色、原始物理属性不改。
- 初始构造、合链、节点调整、填充、整链调序、必要拆单及重放、后置精修的流程不改；原 4/64 提案轮转和接受后续访不改。
- 仍是按原顺序遇到第一个改善即接受，同分拒绝；不能因并行改成最快返回、整批最优或多条同时提交。
- 原单以所有片段的最后完成时刻为完成；真实过渡材也属真实订单，虚拟材耗生产时间但不作为交期订单。
- 起排显式输入；本样本六月一日零点，交期当天 24 点截止，虚拟速度 100 米/分钟。原始逐节点工时不先取整，秒级是评分投影，不是生产时钟精度。
- 生成编号只在原接受边界生效；拒绝、并行作废和内部整数行号不消费正式编号、不回退生成上界。
- 独立无搜索缓存的核心审计、应用审计和最终完整明细保留。加速路径不得把缺失字段、错误规则、越界、未知身份或异常伪装成普通拒绝。
- 完整性能对照仍使用原 400000 次、9999 秒搜索＋10 秒收尾请求。服务 YAML 当前 400000 次、300＋10 秒，两者不是同一条件；不改库或服务设置。

## 4. 第一阶段：数值化数据与轻量候选

### 4.1 两种表达，只有一个可提交方案

公开 `Node / Chain / SchedulePlan` 继续承担输入、结果、追溯和审计。内部计算视图是由已验证任务和当前方案派生的只读表示，不是第二套业务状态。

每次接受时：先由原唯一提交边界产生正式方案及完整评价，再发布与其绑定的新计算视图。准备失败或验证失败不能出现“正式方案已更新、视图仍指向旧方案”的可用状态。拒绝只释放候选临时数据，不改变当前视图。

| 数据 | 设计表示 | 生命周期 / 边界 |
|---|---|---|
| 外部订单、节点、原型、期标识 | 原文身份表＋内部整数索引 | 对外标识不重写；整数仅在本任务内有意义 |
| 节点物理字段 | 按字段保存的连续数值数组＋缺值标记 | 投影遵守原规则数值语义，不能把缺值一律当 0 |
| 材料角色、来源期、规则命中条件 | 整数或布尔数组 | 由已启用规则和验证后字段派生；不写死 GQGA4 |
| 重量、工时、交期 | 原精确值表＋经适用性验证的数值列 | 无法无损表示时精确路径仍可运行，不拒绝原本合法输入 |
| 当前链内容与生产序 | 展平的节点整数序列、链边界偏移、链顺序 | 接受后重建或更新；不为每个候选复制全部 Node |
| 定位与拆片 | 节点位置索引、原单对应全部片段位置 | 检查唯一性；原单索引不能覆盖多个片段 |
| 候选动作 | 方案代次、原顺序号、动作类型、来源/目标位置、局部替换段、入口保护模式 | 保存“怎么改”，不是先保存完整新方案；未知动作沿原路径 |

仅需时生成受影响链的临时整数序列。候选涉及新虚拟材/拆片时，临时行仅属于该候选；发布前核验真实节点值、谱系及原正式编号。运行批次期间不扩容或写入线程共同读取的数组。

### 4.2 连接查找与直接插入位置

为完整连接语义分配整数编号，复用现有规则身份、材料角色和谱系字段。连接表可使用“未计算/允许/禁止”数值格，或按需构建的有向行；先测填充成本和峰值内存，不强制全量平方预计算，不同时长期维护多份内容相同的缓存。

一个插入空位是否直连，由左端到插入节点、插入节点到右端两项有向判断组成；首尾空位分别免去不存在的那一边。用数组批量生成真假标记，再按原游标顺序先输出直接位置、后输出其他位置。**不能直连的位置仍可能经桥接形成候选，不删除。**

第一阶段接线补充：批量只窥看已有整数语义连接结果，未知标记保留为“待查”，到原游标才执行原规则查询；原每位置三次预算/取消检查保持。不在批量准备时评价未来未请求的边，不搬动错误触发或停止边界。表内只有一份权威连接决定，批量标记仅为当前生成器的短期只读数组。实际标记查询次数与原缓存命中分开统计。

规则或完整语义改变必须得到不同连接身份；候选临时节点不可仅按宽厚相同复用。初始构造有向图的方向筛选不适用于完整搜索，不以它的缺边判搜索连接非法。

### 4.3 轻量描述的真实性检查

候选描述必须核对当前方案代次、来源身份、下标范围、实际移动节点、目标期及重叠区间。类型正确不等于动作合法；不能仅相信 `affected_chain_ids` 或一个“已验证”标记。

纯移动/交换可从经过核验的描述证明真实节点多重集合不变；这允许复用守恒事实。新增、删除、拆分、回收或重建桥接则需逐项验证对应差异。最终独立审计仍重新核验全方案。

第一阶段先用这些描述还原原完整候选并走原评价，证明有序候选和结果一致；按需跳过完整构造在第二阶段才启用，线程在第三阶段才启用。

第一阶段实际复用既有位置配方元组：整链、节点、连续块及链内移位绑定当前视图/代次、逻辑序号、实际链和节点，再还原该元组交原处理函数。切链、虚拟回收、拆单及其桥接修复保留原串行守卫，不强装进纯移动描述；新虚拟/拆片数组行仅属于私有候选视图，在接受后才发布。本阶段不证明并跳过原守恒检查，不改变资源动作。

## 5. 数值内核与规则适用性

### 5.1 规则配置不变，改变执行数据

将启用规则的已验证参数、顺序、阈值、缺值策略和角色条件一次转换为数值内核需要的参数。使用少量明确的计算函数，不新增通用语言、动态代码生成器或另一份 GQGA4 规则文件。

现有 `_bridge_numeric.py` 可共用的投影和支持性核验应提取复用；其虚拟材特例必须保留适用范围。真实材软硬连接、跨连续虚拟材的真实端点约束、连续重量等不能因已有桥接内核而视为已支持。

每种支持的规则记录：输入字段、投影方式、原比较顺序、所需摘要、哪些结果精确、哪些仅是安全界限，以及回落条件。规则公式尽量抽取共用纯计算，现有规则对象负责完整贡献和诊断组装；需要独立编译表达时，必须有与权威实现的差分证据，不能仅复制阈值后宣布等价。

未知规则类型、自定义子类、未支持参数或历史模式在接入前识别，按候选或任务粒度明确回落。第一版不混用一半未经证明的分数去决定接受。

### 5.2 精度分级

| 数据 / 运算 | 可采用方式 | 必须满足 |
|---|---|---|
| 身份、位置、计数、角色 | 整数/布尔数组 | 范围检查，缺值和未知身份有明确表示 |
| 原规则已经采用浮点投影的物理比较 | 同精度浮点数组与同操作顺序 | 有限值、缺值、容差、区间开闭和首命中语义一致 |
| 可精确缩放的重量等 | 经验证的定点整数，即固定比例放大保存 | 输入及所有中间结果不溢出，换算和聚合与原 Decimal 上下文结果一致 |
| 无法证明无损的重量/工时/聚合 | 原 Decimal 运算与缓存 | 不直接转换为 `float64` 或整数秒，不增加限制来排除原合法输入 |
| 仅用于提前拒绝的数值估计 | 可证明覆盖精确结果的上下界 | 不确定则精算；没有误差界限证明时禁止据估计拒绝 |

保持原有 28 位 Decimal 上下文及相关精确求和约定；加法改分组、减旧加新、链内相对时间加新起点，都可能改变末位。定点整数并不天然等价，必须同时检查原运算是否发生舍入。

生产时钟继续逐节点顺序累加。只有证明等价的片段可跳过；同一候选内部不做改变加法结合顺序的并行归约。数值内核禁止 `fastmath=True` 等放宽运算顺序的设置。Numba 官方明确说明快速数学选项和并行求和可能允许重新结合运算；本专项不采用这种数值让步。[Numba 数值运算与并行说明](https://numba.readthedocs.io/en/stable/user/performance-tips.html)

### 5.3 不确定不是拒绝

内部计算结果区分“已证明不改善”“需要完整确认”“不支持/数值不确定”；另有原有预算停止和真正错误。后两种正常回落必须走原精确路径，错误不得变成分数无穷大或普通拒绝。首次内核编译失败需明确报告并停止该加速试验，不能静默回落后声称数值版已验证。

## 6. 第二阶段：缓存和变化部分评价

### 6.1 缓存层次与失效

| 层次 | 保存内容 | 有效依据 |
|---|---|---|
| 任务固定准备 | 规则数值参数、节点属性投影、原单交期、单位工时、节点精确生产用时 | 实际任务、规则、工时上下文及节点重量/谱系；请求结束释放 |
| 链/片段摘要 | 现有链贡献、重量、首尾、规则连续段信息 | 完整有序内容、实际所属期和上下文；同链号不代表相同内容 |
| 当前方案事实 | 位置、来源重量和覆盖、资源分类、原单最后片段、生产前缀、各项已确认指标 | 绑定唯一正式方案代次，接受后替换，拒绝不提升 |
| 本轮候选临时结果 | 差量、需要重算的时间范围、判分结果 | 只在当前代次与描述内使用，不能污染后续搜索 |

沿用 `ChainSummary` 和现有未变链复用，不复制一套同义模型。若反复生成内容相同但对象不同的变化链，允许按完整内容建立有容量上限的摘要缓存；这是待测增强，须记录命中率和成本，不无界保存 40 万个拒绝方案或完整明细。

原单列表、借用节点、虚拟节点、分区等有序明细随新生产序重组；总量相同不代表可以返回旧的有序资源视图。规则停用、规则上下文不同、候选删除/新增/拆单、缓存淘汰及任务切换分别核验。淘汰只影响速度，不影响结果。

### 6.2 按动作计算影响

| 动作 | 可复用事实 | 必须重算 / 核验 |
|---|---|---|
| 同期整链换位 | 已证明链内容及所属期不变后的链内规则、来源集合和重量 | 变化交界、生产时间影响区间、原单完成位置、有序资源明细 |
| 单节点或连续片段移动/交换 | 未变链、未变片段的规则事实与节点属性 | 被改链、拼接边界、连续段传播、期锁与跨链原单最后片段 |
| 普通桥接材回收 | 未动真实材、未变链摘要 | 删除用途合法性、新相邻关系、重量/虚拟比例、后续时钟全部影响 |
| 新桥接或受控拆单 | 任务固定字段及不受影响链 | 仍用既有生成与授权；新节点、来源守恒、分区、编号、工时全部核验 |

片段摘要先覆盖可直接合并的重量、首尾和简单连续段。高表面连续数量须携带开头/结尾连续段和内部最大段；同规格连续重量还需规格身份及边界连续重量。保留基准的逆宽计数、跨虚拟真实端点等携带状态的规则若暂不能安全合并，就重扫变化链的数值序列，不用不完整摘要近似替代。

### 6.3 交期与资源的精确增量

1. 节点精确用时只在重量/工时绑定变化时重新计算；输入验证和参数准备不在每个订单的每次评分里重复建立。
2. 找到候选与当前方案的首个变化位置，复用之前的精确累计时钟。
3. 从该位置顺序处理实际候选节点。只有剩余序列及精确起始时钟都与缓存相同，才能接回原后缀；仅总重或秒级分数相同不够。
4. 根据原单全部片段确定新的最后完成位置，更新实际受影响原单的等待/延期贡献，再按原指标次序汇总。
5. 删除虚拟材或改变生产用时可能影响整个后缀，不能只重算搬动的订单。资源差量汇总也必须满足第 5 节的精确性条件，否则保留有序求和。

交期数值加速先做已经证明精确的准备与区间复用。进一步采用浮点筛选时，须为累计误差、秒级半偶边界、延期等号及加权汇总提供覆盖界限；先运行影子对照再启用拒绝。不能证明时返回“需要完整确认”，不放宽精度。最终结果日期、逐单统计和审计始终由精确路径生成。

## 7. 按需评价与唯一接受边界

### 7.1 四个职责，不是四套求解器

| 顺序 | 职责 | 产物 / 后续 |
|---|---|---|
| 1 | 验证轻量候选描述与变化事实 | 已绑定当前方案的只读候选视图；非法描述按原错误或拒绝语义处理 |
| 2 | 按优先级计算必要指标 | 已证明不改善则结束；可能改善、临界或不支持则进入完整确认 |
| 3 | 精确确认并按需组装正式对象 | 沿原完整规则/精确路径计算全部指标、违规和明细，执行原专用入口保护 |
| 4 | 唯一接受与提交 | 仍由主搜索入口作出决定，生成原轨迹、提交方案和编号，更新复用视图 |

快速路径**只能安全排除，不直接发布**。即使高优先级已改善，仍须完成必要规则、来源/期锁/编号校验和完整精算，不能以此绕过硬约束、后置精修准入或完整评价。

### 7.2 逐级比较的精确定义

对最小化的第 `k` 项，只有前 `1…k-1` 项已被证明与当前方案相等，且候选第 `k` 项被证明更大，才能提前判为不改善。不能看到某个低级目标更差就拒绝，也不能在前项只有估计值时跳到后项。

- 已知精确分数按原比较；全部精确相同则按原同分拒绝。
- 若使用包含真实值的区间，区间整体高于当前值才可证明这一项更差；包含当前值不代表相等，必须精算或继续收紧界限。
- 例如前两项精确相同、欠重链数更多，后续交期和宽差不必计算；若禁止数更少，不能因欠重更多直接拒绝。
- 保留原动作特定保护：整链换位、宽差/交期精修等不仅有全局质量比较，还存在各自准入条件，不用一套通用比较替换这些条件。
- 未证明可跳过的规则、可能触发输入错误的计算或未核验新增节点，不进入提前拒绝通道；不能用少算掩盖原本应报告的异常。

核心维护一份目标声明顺序和一份正式接受逻辑。数值内核返回计算结果及确定性类别，而非拥有自己的评分优先级、权限或接受权。

### 7.3 明细延迟生成与等价性

普通快速拒绝不建立完整 `PlanEvaluation`、违规文本和全方案有序资源列表；需要确认的候选仍建立。最终接受的方案完整评价、逐原单日期和公开输出与原实现精确一致。

验证模式称为**影子对照**：快速路径给出结论后，另调用原完整精确路径核对，但真正接受仍遵循权威结果。错误提前拒绝必须定位到首个候选、目标项与差异；不能只拿最终方案相同当作筛选器正确的证据。影子模式不作为加速计时样本，正常运行不永久双算所有候选。

原 `complete_candidate_evaluation_count` 按实际完整评价次数记录，允许因按需评价下降，不造假填回 172312。逻辑候选额度和接受轨迹中的原扣费位置仍保持；新增快速拒绝、精算回落、数值不确定和对象组装次数分别统计。

第二阶段实现覆盖：快筛首批用于已验证内置规则和秒级交期；原历史模式、未知规则、新真实节点/拆片、可能出现 Decimal 指数溢出的形状仍完整评价。没有引入浮点/定点近似。已延迟完整评价及变化链评价对象；原生成器的结构 `Chain/SchedulePlan` 和资源保护仍保留，不能称全部对象组装已消除。连续段缓存复用实际节点分类与完整连续段精确重量，变化后重组段边界；状态规则继续原扫描。实际收益和未覆盖成本见第二阶段证据。

## 8. 第三阶段：独立候选的数值并行

### 8.1 选择与前提

首选既有 NumPy 数据＋Numba 编译循环，在候选维度使用原生多线程：每次迭代计算一个独立候选，各自写自己的结果位置。不是给现有 Python 对象循环加线程，也不是在同一条生产时钟里并行相加。先验证串行数值路径，再开启并行。

Numba 支持对适用循环使用 `parallel=True` 和 `prange`；只读共享数组、各自独立输出是本版设计前提。NumPy 的对象数组运算不能因此获得普通数值线程收益；多个线程不能同时修改共享容器或扩容数组。[Numba 并行循环](https://numba.readthedocs.io/en/stable/user/parallel.html)、[NumPy 线程安全](https://numpy.org/doc/2.2/reference/thread_safety.html)

依赖沿当前 `numpy==2.2.6`、`numba==0.65.1`、`llvmlite==0.47.0`，不因读到新版官方文档自动升级。实际线程后端、版本兼容和 Windows 冻结包必须单独验证。

如果第二阶段后仍以 Python/Decimal 精算为主，则数值多线程可能收益有限。多进程或 joblib 是有测量依据后的替代提案，不是同时必建的另一套后端；切换前明确范围和 Windows 验证安排，新依赖须确认。joblib 的进程执行也有数据序列化成本，不能只换调用库就预设更快。[joblib 并行取舍](https://joblib.readthedocs.io/en/latest/user_guide/parallel.html)

### 8.2 首批范围与扩展范围

| 范围 | 并行内容 | 不并行的部分 |
|---|---|---|
| 首批：整链换位 | 同一方案下不同链排列的只读数值检查与必要指标计算 | 主循环枚举、扣费、精算确认、接受及状态更新 |
| 第二批：节点/片段移动交换 | 已有节点构成、描述可独立验证的候选；边检查、变化链数值扫描及时间筛选 | 新桥生成、受控拆单、带预算副作用的修复分支 |
| 跨阶段共用 | 首轮、拆后重放及后置精修中上述适用候选 | 不按大辊期各自独立求解，不合并或删除现有搜索阶段 |

第二批属于本版计划内，但必须等首批正确性及实际收益检查后接入；并非永久只做宽差或整链这一小段。不支持的动作仍按原位置串行执行，不能从候选集合删除。

涉及既有虚拟材移除的描述，只有删除资格与完整变化已经由原逻辑确定、无需新桥搜索或额外扣费时，才可按同一纯数值契约评价；否则是串行边界。并行对象是足够完整的计算任务，不仅是最后九个分数的比较。

### 8.3 批次、顺序与数据所有权

1. 主线程按原顺序生成有限个无副作用描述，绑定相同任务、方案代次、动作保护模式和候选顺序号。
2. 准备只读公共输入及各候选私有临时空间。需要新增连接表项或目录行时在批次外完成；工作线程不写全局连接缓存、日志、预算、数据库、编号或当前方案。
3. 工作线程只做数值计算，返回“已证明不改善 / 需要精算 / 不支持”及必要数据。结果始终绑定原候选身份，不能只返回一个裸分数。
4. 主线程按原顺序消费：前面已拒绝后才处理后面；需要确认的按原精确入口确认。前面首次改善时接受，后方结果即使更好也作废。
5. 更新正式方案后开启新代次，原候选流按既有重建/续访逻辑恢复。不使用旧代次计算结果，不让旧游标缓存决定新顺序。

批次不跨原动作轮转边界，开始试验时以 1/2/4/8 线程及有界批量测量；批量不得超过剩余当前轮转窗口、剩余额度及已证明可纯生成的连续候选范围。具体上限由阶段 3 有界样本固化，不一次生成 40 万份候选。

### 8.4 逻辑额度与投机计算

**40 万仍是原算法逻辑候选检查上限，包括原有桥接等附加扣费，不是给每条线程各 40 万。**主线程在原顺序实际到达候选时扣费；提前数值计算但未被消费的后方结果单列为“作废预计算”。

禁止为了凑批量提前运行会调用候选扣费、生成正式编号、变更枚举游标或创建桥接的操作。碰到这些操作，先消费当前批次，再按原流程串行执行，之后才开始下一批。无需新语义的纯描述可预计算，但预计算不能偷用未来的逻辑预算。

所有随机状态、候选次数、接受后重启位置与 4/64 轮转仍由原主循环管理。加速后的实际完整评价数可以减少，投机数值计算可以增加；两者必须透明披露，不能混称“同样物理工作量”。

### 8.5 取消、异常和运行边界

- 主线程在进入批次、消费每个逻辑候选、精算前后及提交前检查现有取消与截止时间。
- 编译循环按有限批量/工作块返回；不承诺可强杀一个正在运行的 Numba 线程，也不让无限大内核占满收尾窗口。必须实测取消到返回的最大延迟并记录。
- 超时后结果不得提交；正确保留最后已接受方案，沿原收尾和审计流程处理。固定工作量等价不意味着限时运行会探索到同一位置。
- 工作候选的错误按原候选顺序处理；若因前面接受而作废，可保留为作废诊断。运行时整体失败则立即结束该加速试验，不静默改串行后称并行通过。
- 默认执行方式仍为串行；试验使用私有执行参数，不扩展 HTTP 请求、业务规则、策略指纹或 SQLite 字段。线程数不能作为排产目标。
- 不在并发请求之间改共享全局线程配置。线程后端的并发调用能力及现有服务请求隔离须验证；不满足时不启用该方式，不私自改服务并发策略。
- 不叠加“八进程各八线程”。当前线程方案无需为自身增加进程池或复活旧失效工作文件；若另选多进程，再单独设计冻结入口和子进程回收。

## 9. 模块、接口和发布边界

| 层次 | 本版职责 | 禁止越界 |
|---|---|---|
| 规则与精确评价 | 原规则加载、语义、完整评价与审计；供加速路径核验和回落 | 不以性能理由停用规则、改数值或隐藏错误 |
| 私有数值计算 | 数据投影、适用性、紧凑视图、编译内核、纯批次评价 | 不访问服务/数据库/工具/基线文件；不反向导入 `api/app` |
| 搜索上下文与候选入口 | 当前视图、候选描述、调用快速/精确路径、唯一接受 | 不维护第二个可提交当前方案或独立权重系统 |
| 诊断工具 | 同请求对照、影子核验、分阶段计时和计数 | 不复制正式求解流程，不把探针耗时当正常性能 |
| 服务/发布 | 原请求和结果契约；必要运行依赖收集、试验入口及实包验证 | 不改规则保存启用、数据库、前端或自动部署 |

允许新增职责明确的私有计算模块，数量由实际职责决定，不强迫全部塞进一个文件。先复用现有投影、规则计算和 `ChainSummary`；共享计算需要抽取时同步调用方，避免循环依赖。

现有架构只对私有桥接模块放开 NumPy/Numba。扩展数值内核时须精确更新新模块的依赖许可和架构测试，其他核心边界保持；不全局放开任意第三方导入。

Windows 实包验证覆盖首次编译、冷/热请求、线程运行时依赖、并发调用适用性、取消、异常和连续多次求解；已有桥接 NumPy/Numba 打包通过不能替代新增并行内核的验证。实际调用命令由实施接线后记录，不捏造当前尚不存在的 CLI 参数。

## 10. 验证、测量与一分钟目标

### 10.1 正确性与允许差异

| 检查层次 | 通过要求 |
|---|---|
| 数据视图 | 与原模型逐值对应；缺值、动态节点、拆片、期序、重复身份及失效正确 |
| 数值内核 | 与原规则对照正常/边界/不支持/溢出情形；没有未解释的错误提前拒绝 |
| 候选描述 | 有序候选及原扣费位置一致；不只验证最终方案 |
| 按需评价 | 影子核验快速拒绝；所有接受的完整指标、违规、有序资源及精确日期一致 |
| 整次求解 | 相同请求/40 万额度下有序方案、接受轨迹及逻辑序号、来源/谱系、生成上界、停止原因一致 |
| 审计 | 独立无搜索缓存重算；零禁止、零欠重、来源守恒及其余既有条件不放宽 |
| 允许变化 | 实际完整评价、对象组装、缓存、内核调用、预计算与作废、耗时/CPU/内存；如实分列 |

### 10.2 逐阶段测量

每个主要阶段先做集中正确性检查，再保留独立完整运行及重复结果；上一阶段冻结后进入下一阶段，不一次混改后只测最终版。用户要求不必每个小步骤运行测试，实施计划按功能边界安排集中检查。

记录任务准备、数值投影、首次编译、缓存、候选生成、快速判断、精确确认、对象组装、批次协调、实际业务阶段及独立审计的时间。计时桶需说明是否重叠，不把函数累计值重复相加。

数值线程的 CPU 计入同一进程，记录经过时间、进程 CPU、实际线程数及主机处理器信息；若改多进程则另计子进程 CPU，不能只看父进程。输入读取、公共求解和额外报告写出分列，旧 1214.57 秒边界与新工具不同的部分不得混比。

并行先对优化后的串行同批候选测 1/2/4/8 线程，包含准备、编译、等待和作废成本；适用份额过小、线程更多反而慢时不强行采用八线程。完整成对计时不得并发运行相互争抢 CPU 的样本。

### 10.3 一分钟目标的检查提案

在选定验收机器、相同观察设置、同 40 万完整逻辑额度下，对最终选定方式至少运行五个完整样本，报告中位数、最大值、冷/热状态；中位数及最大值均不超过 60 秒才称本专项该环境的一分钟目标达到。首次编译、初始化和收尾不得偷偷从相应冷启动口径排除。

五样本是本专项建议的目标检查方法，不替换历史 20 对/180 秒正式门槛，也不代表已得到性能证明。Windows 与本机 Mac 分别记录；只在热服务请求满足时，结论必须明确仅指热请求，不宣称 EXE 首次启动也满足。

未达一分钟仍可交付经验证的阶段收益，但不得将“功能实现完成”写成“性能目标完成”。不以提前耗尽更少额度、降低质量、关闭审计或改排序达标。

## 12. 术语与证据边界

| 术语 | 通俗说明 |
|---|---|
| 数值计算视图 | 把已验证订单整理为供计算使用的数组；不是另一份业务订单 |
| 轻量候选描述 | 记录“移动哪里、放到哪里”，先不构造完整新方案 |
| 片段摘要 | 保存一段订单影响拼接检查的必要信息，减少重复扫描 |
| 增量评价 | 只重算变化及其传播的影响，不是少执行业务规则 |
| 按需评价 | 能证明不改善时停止继续评分，可能改善时完整确认 |
| 定点整数 | 将可精确表示的数按固定比例放大为整数；仍需检查精度和溢出 |
| 影子对照 | 快速计算之外再用原精确计算核验，用于验证而非性能计时 |
| 方案代次 / 作废预计算 | 当前方案的内部版本；基于旧版本提前算出而不能再使用的结果 |
| 编译内核 / Numba | 把适用的数值循环编译为机器指令运行的计算部分及所用工具 |

当前行为由源码核验、集中测试和各阶段实际记录互证；第三方机制引用官方说明，2026-09-15 核验。文档中的官方示例加速比例不转用为 APSGo 收益，机制可行不等于当前全部 Decimal 评价可直接编译。不得将本机阶段验证当作 Windows 或一分钟性能验收。
