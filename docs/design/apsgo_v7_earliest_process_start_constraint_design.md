## 2. 目标与非目标

目标：

1. 求解前收到每单已经计算好的连镀最早开始时间。
2. 构造、搜索、候选评价和最终审核使用同一生产时间轴，发现并尽量修复提前开工。
3. 最早开工规则启用时，最终回写必须没有提前开工；其他业务违规可保留，但完整性与独立复核必须通过，全部违规、评分和真实时间如实返回。
4. 继续使用统一 NumPy 数值结构和已编译计算内核，不回到逐候选解析日期、构建 Python 订单对象的路径。

非目标：不修改前端最早日期推算公式，不联合求解上下游工序，不引入停机日历、自动空闲、并行机或换辊停机时长；不改九项目标顺序，不增加第十项目标；不提高候选额度或时限。除第 9.2 节明确授权的入口及候选清零过滤调整外，不改候选生成、接受、停止条件，不因允许回写而降低搜索中的其他规则保护。

## 3. 时间概念与当前实现

| 名称 | 本文含义 | 来源 |
|---|---|---|
| 本次排产开始时间 | 整个生产序列的时间原点 | 前端求解弹窗的 `schedule_start_at` |
| 本单最早开始时间 | 本单到当前工序允许开始加工的下界 | 前端已计算的 `earliestDates.coating` |
| 本单计算开始时间 | 按最终生产顺序累加前面所有节点用时后得到的时刻 | 后端统一时间轴 |
| 本单计算完成时间 | 本单计算开始时间加本节点生产用时 | 后端统一时间轴；现有回填字段名包含“计算最晚日期” |
| 订单交货日期 | 希望订单完成的交期边界 | 现有 `due_date`，日期边界沿用当日结束口径 |

“最早开始时间”不是交货日期，也不是本次排产开始时间。**本规则比较开始时刻，不比较完成时刻；即使完成时刻已晚于最早开始时间，只要实际开始过早，仍然违规。**

## 4. 判定公式：连续生产，不自动等待

按最终发布顺序展开所有小辊期及节点，跨小辊期、大辊期均不断开时间累计。设本次开始为 `T0`，节点用时为 `d[i]`，来源订单最早开始为 `R[i]`：

```text
S[0] = T0
S[i] = T0 + sum(d[j] for j < i)
C[i] = S[i] + d[i]
真实节点合格条件：S[i] >= R[i]
提前时长：max(0, R[i] - S[i])
```

禁止改成 `S[i] = max(C[i-1], R[i])`：该公式会自动插入等待，不属于本次业务模型。也不允许把整次开始时间偷偷后移。

例：本次 08:00 开始，A 用时 2 小时、最早 08:00；B 用时 1 小时、最早 11:00。A→B 中 B 在 10:00 开始，提前 1 小时，**虽然 B 在 11:00 完成，仍违规**。若另有已就绪、用时 1 小时且满足连接及资源规则的 C，A→C→B 可以消除问题；没有合适调整时，不得在输出中自动补 1 小时等待。

精度建议沿用权威生产时间轴的整数毫秒。时间原点和外部最早时间精确到秒输入，节点累计可能产生毫秒；相等合格，提前 1 毫秒也违规。现有交期目标按秒进行四舍五入评分的口径不变，不能先把开始时间显示取整再判硬约束。

## 5. 规则定义与九项目标

| 项目 | 设计 |
|---|---|
| 规则名称 / 建议键 | 当前工序最早开工限制 / `earliest_process_start` |
| 建议实现类 | `EarliestProcessStartRule`，沿用现有规则基类与注册方式 |
| 作用范围 | 整个方案；逐个实际排产真实节点判定 |
| 配置参数 | 空参数；规则保存启停状态，订单时间随本次请求传入，不写进规则定义 |
| 禁止违规数 | 每个提前开工的真实节点计 1 条；多个拆分片段分别判定 |
| 禁止严重度 | 建议为该节点提前秒数，所有违规节点求和；详细口径见下文 |
| 最终回写条件 | 完整方案通过数据正确性、无搜索缓存重算及结果映射审核；启用时最早开工违规为零，其他业务违规可保留并回写，详见第 10 节 |
| 停用行为 | 不计本规则的违规、严重度或重点搜索；不把缺失最早时间当作本规则输入错误 |

新规则进入既有前两项目标，当前九项顺序保持：

1. 禁止违规数量。
2. 禁止违规严重度。
3. 欠重小辊期数量。
4. 欠重总缺口。
5. 上月欠交订单全部完成时间。
6. 交期加权等待负担。
7. 相邻小辊期首尾宽差总和。
8. 虚拟材总重量。
9. 非空小辊期数量。

仍按前一项优先于后一项逐级比较，不改成九项加权求和。当前配置声明是实际运行顺序的权威来源，不在新规则内另写一份目标排序。

严重度建议：`提前毫秒 / 1000` 秒。现有严重度使用百万分之一的整数单位，因此本规则对应整数贡献为 `提前毫秒 × 1000`，运算必须检查溢出。违规数量先比较、严重度后比较；仅用于引导修复，不是允许提前的配额。诊断同时给出违规节点数和去重来源订单数，但不得混用两者评分。

## 6. 订单范围、空值与数据质量

| 对象 / 情形 | 处理 |
|---|---|
| 普通真实订单 | 必须满足来源订单最早开始时间 |
| 真实过渡材 | 与普通真实订单相同，不因过渡材身份豁免 |
| 同期拆单、借入拆单片段 | 每片继承同一来源订单下界，按片段实际开始分别检查；原单完成交期仍取最后片段完成时间 |
| 生成型虚拟材 | 没有真实来源最早时间，不执行本规则；其生产用时必须参与累计 |
| 最早时间早于本次开始 | 合法输入，相对偏移允许为负，不截成零 |
| 规则启用但真实订单最早时间缺失 | 建议前置拒绝并列出订单与字段；不默认为零、不用交期或本次开始补值 |
| 日期存在但格式、时区或数值范围非法 | 输入校验失败，不进入搜索 |
| 前端因产品路线未计算连镀日期 | 明确报告“当前工序最早时间缺失”；不得自动拿热轧、酸洗轧日期替代 |

规则启用前应检查实际选单范围是否都属于连镀工序并具有最早时间。是否允许某类真实订单缺省，属于业务例外，需要明确授权；本稿不设置隐藏豁免。

沿用既有真实/生成型虚拟角色识别，不仅凭前端显示名称或订单编号判断；不改变材料分类及来源守恒。

## 7. 请求、配置与响应契约

### 7.1 请求建议

求解地址不变：`POST /api/v1/scheduling/GQGA4/default/month/solve`。

建议新增明确版本 `v7-month-solve-v3`，在每个真实输入订单中增加 `earliest_start_at`。沿用已有 `schedule_start_at`、交期、速度及其他订单字段。示意如下，省略的既有必填字段仍须提供：

```json
{
  "contract_version": "v7-month-solve-v3",
  "schedule_start_at": "2026-06-01T00:00:00+08:00",
  "orders": [
    {
      "source_order_id": "example-order",
      "earliest_start_at": "2026-06-03T08:00:00+08:00"
    }
  ]
}
```

前端把 `earliestDates.coating` 的工厂本地时间转换为显式 `+08:00` 的秒级字符串，不经过浏览器所在时区隐式换算。已有最早日期是本地墙上时间，不得先误当 UTC 再平移 8 小时。

后端在服务边界校验一次时区和格式，再进入共用时间输入模型。不接受“由服务端当前日期猜年份”或“日期缺时刻时猜 00:00”等隐式补全。

版本行为：旧 v1/v2 的旧场景维持既有契约；活动规则启用了新规则但旧客户端没提供对应输入时，返回明确缺失能力/字段诊断，不静默关闭规则。新客户端不能在旧后端报错后去掉字段重试。部署前先完成新后端、前端接线及数据检查，再显式启用规则。

### 7.2 规则管理

沿用已有 `getActiveRules` / `setActiveRules` 查询与保存启用接口及版本校验。增加规则模板、类型注册和数值编译映射；不另建一套配置存储，不在每条订单上存规则开关。

规则本身独立于交期优化：它表达“能否开工”，不是“是否晚交”。实现应以“任一启用规则需要生产时间轴”为触发依据；不应因为关闭某个交期目标就漏掉新硬约束。对当前不支持所需时间输入或数值执行能力的入口，应前置明确拒绝，不退回不检查的旧路径。

### 7.3 结果与诊断

继续使用 `current_process_start_at` 和 `current_process_latest_at` 回填开始、完成时间，不改“最晚日期”列来掩盖提前开工。

在现有规则诊断/交期报告中增加必要信息：来源订单、实际节点、所属大辊期及小辊期、最早开始时间、计算开始时间、提前秒数、规则身份。普通成功结果不新增第二套日期计算接口。

前端已有最早日期列保留，拆单片段继承原单信息。订单列表与导出继续以**当前步骤全部订单、全部列**为准；不能导出另一套独立修正后的时间。通过正确性审核、且没有启用的最早开工违规时，带其他业务违规方案可以成为当前求解步骤数据，并明确提示“已回写，存在业务违规”；仍有提前开工或正确性审核失败的方案只保留诊断，不得回写。

违规明细以独立复核后的完整结果为准。边/节点规则定位到对应订单，链级违规定位小辊期，方案级违规在总体提示中展示；不能只显示现有宽厚温警告而遗漏时间、期约束或虚拟比例等违规。列表警告列承载对应提示，现有完整明细保留；前端不重算、不删除、不把违规数清零。新状态及审核标记见第 10.3 节。

## 8. 统一数值结构与唯一生产时钟

### 8.1 一次标准化

扩展既有时间输入模型与 `NumericOriginals` 原订单数值表，建议增加：

- `earliest_start_ms`：相对 `schedule_start_at` 的有符号 `int64` 毫秒偏移。
- `has_earliest_start`：是否提供有效下界的布尔数组；禁止用零或某个合法负数充当缺失标记。

真实节点通过既有来源索引读取原单下界，拆单无需复制一份可漂移的时间；虚拟节点没有真实来源索引，跳过下界检查。数组连续、只读并属于当前任务，不逐候选构建日期对象、字符串、映射或领域订单。

请求、标准化任务、缓存复用及审核身份必须覆盖新输入与规则启停。相同订单规格但不同最早时间不是相同排程任务；不能复用另一时间输入下的方案评价。仅做物理连接判定的缓存仍只承担物理连接职责。

### 8.2 在现有累计循环中判定

扩展 `_clock_view()`：读取当前 `clock` 作为节点开始偏移，按来源下界判断，再累加该节点时长作为完成偏移。交期评价和本规则读取同一次累计结果；最终报告复用已审核语义，不创建第二条可写时钟。

违规计入方案级汇总，同时保留节点及链定位。不要既记入链缓存又在方案汇总重复累计。数值编译器和明细投影共用同一规则、原因编号与单位转换。

新规则需要的额外工作是每个真实节点读取一次下界并比较；但实际增加的完整耗时还取决于搜索轨迹，不能仅凭比较次数承诺性能不变。

### 8.3 缓存边界

相邻规格是否可连接与绝对开始时间不同：本规则**不加入静态规格连接矩阵**，否则会错误地把依赖前面生产时长的判断固化成两节点关系。

同一条链内容没变，但前面的链顺序、用时或虚拟材变了，链中节点的开始时间就可能改变。因此：

1. 物理边和仅依赖链内容的规则仍复用原缓存。
2. 最早时间和交期评价不能只按链内容复用。
3. 首版沿用当前完整方案原生时间扫描，覆盖所有受影响的后续节点；不新增复杂的局部时间缓存。
4. 同一代次的只读输入可以复用；接受换序后，批次剩余候选及派生的提前开工标记按现有代次失效机制处理。

## 9. 搜索过程：必须能修复，不只是报错

### 9.1 保留总体流程

继续使用现有“规格连接与路径构造 → 首轮局部搜索 → 受控拆单及唯一重放 → 后置结构精修 → 独立审核”流程，不为新规则再建一套求解器。

初始方案仍以快速构造为主。完成后做同一完整评价，允许内部存在提前开工，作为后续修复起点；不能要求每条初始局部链脱离全局时间轴单独合格。允许最终带违规回写不意味着跳过搜索，或直接把未完成审核的初始解作为结果。

### 9.2 修正禁止违规入口

当前后置精修的“存在任何禁止违规就退出”要细分：

- 启用最早开工规则：即使当前方案仍有其他禁止违规，也进入既有结构精修；不能因一条本身超限的窄钢订单而跳过其他订单的提前开工修复。
- 精修候选不再要求其他业务违规一次全部清零。逐条和批量评价共同取消这项绝对清零过滤，继续经过统一候选消费及提交保护：每一条非最早开工规则的禁止违规数量不得超过当前方案，九项质量仍须严格改善。该保护按规则数量判断，不新增逐规则严重度非增条件，不宣称每项严重度都不会增加。
- 停用或不配置最早开工规则：保留原来遇到禁止违规退出、候选禁止违规必须清零的流程。
- 连接构造、受影响链重量检查、期锁、拆单授权、来源守恒、取消、额度及无缓存审核全部保留；本轮不引入新动作，不改候选顺序和扣额含义。

实现时必须检查首轮、拆单、后置精修和公共候选消费的实际调用链，不允许只移除一行入口判断却让下游继续把所有提前候选提前拒绝。含提前开工的候选可以作为内部中间状态，但仍须通过现有完整质量比较及提交条件；不引入无界随机接受。

### 9.3 复用动作，增加问题定位

可用调整包括：将尚未就绪的订单/片段移后，将已经就绪且能连接的订单移前，交换节点/片段，以及在允许范围内调整整条小辊期顺序。优先使用既有规格矩阵定位直接可连接位置；必要时仍按原合法桥接规则修复连接。

只靠原有交期锚点可能漏掉“需要移后”的订单。因此在现有重点候选通道中纳入提前开工节点：按提前时长降序、实际位置及来源身份稳定排序；保留普通扫描通道，不能只处理最早的一个违规。

重点通道扩展仍遵守候选结构归属唯一生成，不先生成两份再去重；复用既有轮转、首改善接受、共享额度和取消规则。新规则关闭时不插入这些重点候选；启用时允许轨迹发生业务上有意的变化，并在对照中单独标注。

每个完整候选都重新评价全方案累计时间。例如把一个提前订单后移，可能使其他订单被提前；不能只检查被移动订单。跨大辊期仅使用原有合法资源动作，不能借本规则取消原订单期约束。

不得新增“为消耗时间而插入虚拟材”的用途、放大虚拟重量或虚构加工时长。原有为合法连接或链重填充产生的虚拟材继续计时，并接受原资源与比例规则检查。

### 9.4 无解与额度耗尽

在有限候选范围内没有找到零违规，只能说明本次未找到全部合规方案，不能宣称数学上无解。若仍含启用的最早开工违规，不能回写；若最早开工合格，仅剩其他业务违规，完整且经可靠复核后可按第 10 节回写。最早时间集中偏晚、可提前排的订单不足，确实可能与“不等待”形成冲突，但不得据此自动放宽规则判定。

停止后保留真实停止原因、最终方案及提前明细；若正确性审核未通过，仍只保留诊断。达到候选或搜索时间上限但完成后续审核，与审核超时、取消、异常不同，后者不能通过允许业务违规回写绕过。是否改开始时间或另行支持等待，由用户决定。

### 9.5 月计划使用订货量

1. APSGoWeb 原单增加独立 `orderQuantity` 字段，导入“订货量”及明确同义表头；`coatingShortage` 和原始列仍保存实际连镀欠交，不改名、不覆盖。新导入的排程重量使用订货量。
2. 已保存步骤若尚无新字段，从其 `originalFields` 中读取明确的订货量列；不读取连镀欠交、通用 `weight` 或含义不明的合同数量作替代。缺少、非有限或非正订货量在求解前提示，禁止静默回退。
3. 求解请求仍通过既有 `orders[].weight` 传递；后端 `_order_timing` 直接用同一重量、宽厚和有效速度推算用时，因此不新增请求字段或第二套用时公式。接口消费者对该字段负责，不能声称其他未修改的客户端也已切换。
4. 拆单回写按来源订单汇总片段重量，核验等于订货量；返回节点 `weight` 使用实际片段重量，原单订货量/欠交量保持各自含义。历史步骤的已有重量和日期不自动重写，须重新求解产生新结果。
5. 订货量会同时影响链重、窄钢重量限制、拆单与生产用时，不是仅拉长日期。原单最早时间、交期、速度、密度和无等待原则不变；不得以延后时钟来伪造改善。真实提前/晚交变化仍需同输入重新求解，不用局部测试代替。

### 10.2 业务合规与结果正确性分别判断

复用 `_numeric_audit.audit_numeric_core_without_search_cache()` 从原始任务、最终节点及规则重建数值任务，独立于搜索缓存重新累计全部规则。应用层继续审核结果映射及请求/规则/方案身份。

| 检查类别 | 示例 | 回写处理 |
|---|---|---|
| 阻止回写的业务违规 | 启用的最早开工规则判定提前，包括普通真实材、真实过渡材和任一拆片；提前 1 毫秒也计入 | 必须清零，否则不回写；即使其他业务规则全部满足，也不能放行 |
| 其他业务规则违规 | 宽度、厚度、温区、链重上下限、连续限制、订单延后期、虚拟比例等正常评价产生的违规 | 允许，保留原等级、原因、严重度、主体及数量；不是把禁止违规重分类为已允许欠重 |
| 输入或配置错误 | 必填值缺失、非法日期/数值、未知规则/期、活动版本冲突 | 仍拒绝；无法可靠计算不属于“已有完整方案但不合规” |
| 结构及来源错误 | 丢单、重复覆盖、重量不守恒、未知来源、伪造/缺失拆单或虚拟谱系、物理属性被错误改写 | 仍拦截；合法拆片不当作重复订单 |
| 独立复核不一致 | 搜索与独立审核的评分、违规、资源或时间不一致；拆单执行记录与同一任务权威授权重放不一致 | 仍拦截，不能把程序错误伪装为业务违规 |

只有**完整结果 + 核心正确性复核通过 + 应用结果映射审核通过 + 启用的最早开工违规为零 + 身份对应 + 无终止性错误**才具备回写资格。不能仅凭 `passed=false` 或错误码中包含“规则”判断可放行；按问题实际来源分类，未知审核错误默认阻止。业务违规保留在规则明细中，不把所有错误诊断一律降为警告。

### 10.3 状态、响应与前端行为（已接线，验证见实施计划）

采用一个新增结果状态 `publishable_with_violations`，含义为“数据可靠、最早开工回写条件满足，但有其他业务违规”。保留已有 `success` 和 `publishable_with_allowed_deviation`（仅既有允许偏差）语义；仅在没有启用的最早开工违规、且存在超出原允许偏差范围的其他业务违规时，使用新状态，不混称普通成功。有提前开工时仍为 `complete_not_publishable`，不得签发正式结果。

| 响应字段 / 状态 | 目标语义 |
|---|---|
| `publishable` | 可以写回当前求解步骤，不表示全部业务合规；必须满足最早开工门槛并具有已签发的完整正式结果 |
| `audit_summary.integrity_passed` | 两层正确性审核完成且通过；是新带违规结果的必要条件 |
| `audit_summary.writeback_blocking_violation_count` | 从核心独立审核派生阻止回写的业务违规数，本次只计启用的最早开工违规；必须为 0 才能回写。规则停用且审核完整时为 0，审核未完成或无可信明细时为 `null`，不能把缺失默认成 0 |
| `business_rules_satisfied` | 从独立复核的全部规则明细派生；无任何业务违规才为真，含已允许欠重也为假；没有可靠完整评价时为 `null`，不能把未检查说成合规 |
| `audit_summary.passed` | 保留原综合审核含义（原先允许的欠重偏差仍可通过）；不能用它代替上面两个独立事实，也不强置为真 |

| `delivery_report`、`latest_dates` | 取同一正式结果与生产时间轴，完整返回当前日期接线所需信息；不自动等待或修正日期 |
| `complete_not_publishable` 等未发布状态 | 含最早开工违规或不具备可靠回写资格时不签发正式结果；保留诊断，不返回可写订单行或正式日期回填 |

前端只在新状态、`publishable=true`、明确的 `integrity_passed=true`、`writeback_blocking_violation_count=0` 及请求/规则/节点/重量/日期身份检查全部满足时，回写带其他违规方案。先验证订单和日期完整，再一次性替换当前步骤；失败保留旧数据。不把 `core_audit.passed=false` 当唯一拒绝条件，也不无条件绕过审核。最早开工未达标时提示“仍有订单早于最早开工时间，未回写”，并展示对应诊断；不能把阻断数量为正或缺失的响应当成可回写。

带违规回写提示“求解完成，存在业务违规，已回写；请查看违规明细”，不新增每次必须人工确认才能保存的流程，不触发真实设备生产。其他状态沿用原回写检查；旧客户端遇到不认识的新状态仍拒绝，不能伪造旧 `success` 以绕过它。升级后端与 APSGoWeb 应配套验证，本次不改 C#。

| 预算耗尽仍违规 | 仍提前则不回写；仅其他违规且正确性通过才可回写；保留停止原因，不宣称无解、不自动等待 |
| 最早开工恰好合格、提前 1 毫秒及多个拆片 | 分别允许进入回写判定、阻止回写、任一片提前即阻止；不按显示秒数取整后豁免 |
| 单项/多项其他业务禁止违规、欠重及混合违规 | 最早开工合格且正确性通过可回写，原违规等级/数量/严重度和九项评分不变 |
| 提前开工与其他业务违规并存 | 仍阻止回写；不能把“其他可违反”错误扩展到提前开工 |
| 业务违规与丢单/重单/守恒或重算错误并存 | 正确性错误优先拦截，不能因同时含业务违规便放行 |
| 审核未运行、取消、异常、收尾超时 | 不回写，不能将缺失标记当作通过 |
| 新状态、旧状态及旧客户端 | 新状态显式校验可靠性及阻断数量为 0 并告警；数量缺失/正值拒绝，旧成功/允许偏差行为不变，旧客户端安全拒绝陌生状态 |
| 新规则停用 | 同输入/种子/额度下原候选顺序及结果无额外变化 |
| 缓存、批量串行和无缓存审核 | 新输入身份、时间、计数和严重度完全一致 |
| 前端提交、回填、当前步骤导出 | 同一时间原点、显式时区、无 8 小时偏移、无第二次日期修正 |

必要测试集中按契约、数值规则与搜索、端到端审核组织，不要求每次小编辑全量测试。真实 GQGA4 对照须补齐并冻结每单最早时间；旧基线缺少该字段不能假填后宣称“同输入”。

真实对照固定原订单物理数据、九项目标顺序、开始时间、种子及预算，分别记录启用前后九项值、提前节点/来源数、总提前秒数、耗时和停止原因。启停最早开工规则可以改变搜索轨迹；本次仅改变回写资格则不能改变搜索行为，两种对照必须区分。新增应用审核耗时单列；若相同时限导致截断点变化，应如实分析，不能隐藏或擅自提高预算。Windows 发布包测试与本地后端验证分别记录。

## 14. 设计决策与后续确认

已确认：开始时间不早于本单当前工序最早时间，仍以原禁止等级参与评分与搜索；不自动等待。用户最新确认“最早开工违规必须清零，其他业务违规允许回写”，取代 v0.3 全部业务违规放行口径；正确性错误仍拦截。

以下已有确认继续保持：

1. 真实单最早时间缺失前置报错，包括路线没有连镀日期的情况，不默认无下界。
2. 新请求版本 `v7-month-solve-v3`、订单字段 `earliest_start_at`；时间使用显式北京时间到秒，内核沿用整数毫秒。
3. 违规按排产真实节点计数，严重度按提前秒数累计，去重原单数仅作统计。
4. 在既有搜索中加入提前开工定位，修正后置精修入口；保留搜索中其他禁止规则保护，最终回写改按第 10 节。

新增状态与审核标记是本次回写语义的落地设计，不引入新目标、独立求解器或规则数据库开关。实施与验证见计划新增阶段 6.1～6.4；进一步修复真实提前订单与现场启用分别需要额外授权。
