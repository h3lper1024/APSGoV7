## 2. 目标与非目标

目标：

1. 求解前收到每单已经计算好的连镀最早开始时间。
2. 构造、搜索、候选评价和最终审核使用同一生产时间轴，发现并尽量修复提前开工。
3. 最终可回写结果中提前开工为零；无法消除时保留诊断，不发布违规方案。
4. 继续使用统一 NumPy 数值结构和已编译计算内核，不回到逐候选解析日期、构建 Python 订单对象的路径。

非目标：不修改前端最早日期推算公式，不联合求解上下游工序，不引入停机日历、自动空闲、并行机或换辊停机时长；不改九项目标顺序，不增加第十项目标；不提高候选额度或时限，不以降低其他硬约束换取新规则通过。

## 3. 时间概念与当前实现

| 名称 | 本文含义 | 来源 |
|---|---|---|
| 本次排产开始时间 | 整个生产序列的时间原点 | 前端求解弹窗的 `schedule_start_at` |
| 本单最早开始时间 | 本单到当前工序允许开始加工的下界 | 前端已计算的 `earliestDates.coating` |
| 本单计算开始时间 | 按最终生产顺序累加前面所有节点用时后得到的时刻 | 后端统一时间轴 |
| 本单计算完成时间 | 本单计算开始时间加本节点生产用时 | 后端统一时间轴；现有回填字段名包含“计算最晚日期” |
| 订单交货日期 | 希望订单完成的交期边界 | 现有 `due_date`，日期边界沿用当日结束口径 |

“最早开始时间”不是交货日期，也不是本次排产开始时间。**本规则比较开始时刻，不比较完成时刻；即使完成时刻已晚于最早开始时间，只要实际开始过早，仍然违规。**

以下是初稿核验基线 `f169ba8` 的代码证据，不代表实施后的当前状态；新字段、规则、修复及接口接线详见实施计划阶段 1～5：

- 前端 [earliestDates.ts](/Users/miles/dev/dev-front/APSGoWeb/src/earliestDates.ts) 已计算各工序最早日期。时间字符串不带时区，以工厂本地时间表达；部分产品路线可能没有连镀日期。
- 前端 [v7.ts](/Users/miles/dev/dev-front/APSGoWeb/src/api/v7.ts) 的 `projectSolveOrder()` 尚未发送最早开始时间；当前求解请求为 `v7-month-solve-v2`。
- 后端 [month_scheduling.py](../../src/apsgo_v7_service/month_scheduling.py) 严格校验订单字段，直接在当前请求中增加未定义字段会被拒绝。
- [_numeric_kernel.py](../../src/apsgo_scheduler/core/_numeric_kernel.py) 的 `_clock_view()` 按全方案生产顺序累加节点用时；目前没有本规则。
- [_numeric_refinement.py](../../src/apsgo_scheduler/core/_numeric_refinement.py) 的 `improve_numeric_refinement()` 当前遇到任何禁止违规都会直接返回；接入新规则必须处理这一入口条件。

## 4. 判定公式：连续生产，不自动等待

按最终发布顺序展开所有小辊期及节点，跨小辊期、大辊期均不断开时间累计。设本次开始为 `T0`，节点用时为 `d[i]`，来源订单最早开始为 `R[i]`：

```text
S[0] = T0
S[i] = T0 + sum(d[j] for j < i)
C[i] = S[i] + d[i]
真实节点合格条件：S[i] >= R[i]
提前时长：max(0, R[i] - S[i])
```

禁止改成 `S[i] = max(C[i-1], R[i])`：该公式会自动插入等待，不属于本次业务模型。也不允许把整次开始时间偷偷后移。

例：本次 08:00 开始，A 用时 2 小时、最早 08:00；B 用时 1 小时、最早 11:00。A→B 中 B 在 10:00 开始，提前 1 小时，**虽然 B 在 11:00 完成，仍违规**。若另有已就绪、用时 1 小时且满足连接及资源规则的 C，A→C→B 可以消除问题；没有合适调整时，不得在输出中自动补 1 小时等待。

精度建议沿用权威生产时间轴的整数毫秒。时间原点和外部最早时间精确到秒输入，节点累计可能产生毫秒；相等合格，提前 1 毫秒也违规。现有交期目标按秒进行四舍五入评分的口径不变，不能先把开始时间显示取整再判硬约束。

## 5. 规则定义与九项目标

| 项目 | 设计 |
|---|---|
| 规则名称 / 建议键 | 当前工序最早开工限制 / `earliest_process_start` |
| 建议实现类 | `EarliestProcessStartRule`，沿用现有规则基类与注册方式 |
| 作用范围 | 整个方案；逐个实际排产真实节点判定 |
| 配置参数 | 空参数；规则保存启停状态，订单时间随本次请求传入，不写进规则定义 |
| 禁止违规数 | 每个提前开工的真实节点计 1 条；多个拆分片段分别判定 |
| 禁止严重度 | 建议为该节点提前秒数，所有违规节点求和；详细口径见下文 |
| 最终发布条件 | 本规则及其他禁止规则全部为零；继续执行覆盖、守恒及既有审核 |
| 停用行为 | 不计本规则的违规、严重度或重点搜索；不把缺失最早时间当作本规则输入错误 |

新规则进入既有前两项目标，当前九项顺序保持：

1. 禁止违规数量。
2. 禁止违规严重度。
3. 欠重小辊期数量。
4. 欠重总缺口。
5. 上月欠交订单全部完成时间。
6. 交期加权等待负担。
7. 相邻小辊期首尾宽差总和。
8. 虚拟材总重量。
9. 非空小辊期数量。

仍按前一项优先于后一项逐级比较，不改成九项加权求和。当前配置声明是实际运行顺序的权威来源，不在新规则内另写一份目标排序。

严重度建议：`提前毫秒 / 1000` 秒。现有严重度使用百万分之一的整数单位，因此本规则对应整数贡献为 `提前毫秒 × 1000`，运算必须检查溢出。违规数量先比较、严重度后比较；仅用于引导修复，不是允许提前的配额。诊断同时给出违规节点数和去重来源订单数，但不得混用两者评分。

## 6. 订单范围、空值与数据质量

| 对象 / 情形 | 处理 |
|---|---|
| 普通真实订单 | 必须满足来源订单最早开始时间 |
| 真实过渡材 | 与普通真实订单相同，不因过渡材身份豁免 |
| 同期拆单、借入拆单片段 | 每片继承同一来源订单下界，按片段实际开始分别检查；原单完成交期仍取最后片段完成时间 |
| 生成型虚拟材 | 没有真实来源最早时间，不执行本规则；其生产用时必须参与累计 |
| 最早时间早于本次开始 | 合法输入，相对偏移允许为负，不截成零 |
| 规则启用但真实订单最早时间缺失 | 建议前置拒绝并列出订单与字段；不默认为零、不用交期或本次开始补值 |
| 日期存在但格式、时区或数值范围非法 | 输入校验失败，不进入搜索 |
| 前端因产品路线未计算连镀日期 | 明确报告“当前工序最早时间缺失”；不得自动拿热轧、酸洗轧日期替代 |

规则启用前应检查实际选单范围是否都属于连镀工序并具有最早时间。是否允许某类真实订单缺省，属于业务例外，需要明确授权；本稿不设置隐藏豁免。

沿用既有真实/生成型虚拟角色识别，不仅凭前端显示名称或订单编号判断；不改变材料分类及来源守恒。

## 7. 请求、配置与响应契约

### 7.1 请求建议

求解地址不变：`POST /api/v1/scheduling/GQGA4/default/month/solve`。

建议新增明确版本 `v7-month-solve-v3`，在每个真实输入订单中增加 `earliest_start_at`。沿用已有 `schedule_start_at`、交期、速度及其他订单字段。示意如下，省略的既有必填字段仍须提供：

```json
{
  "contract_version": "v7-month-solve-v3",
  "schedule_start_at": "2026-06-01T00:00:00+08:00",
  "orders": [
    {
      "source_order_id": "example-order",
      "earliest_start_at": "2026-06-03T08:00:00+08:00"
    }
  ]
}
```

前端把 `earliestDates.coating` 的工厂本地时间转换为显式 `+08:00` 的秒级字符串，不经过浏览器所在时区隐式换算。已有最早日期是本地墙上时间，不得先误当 UTC 再平移 8 小时。

后端在服务边界校验一次时区和格式，再进入共用时间输入模型。不接受“由服务端当前日期猜年份”或“日期缺时刻时猜 00:00”等隐式补全。

版本行为：旧 v1/v2 的旧场景维持既有契约；活动规则启用了新规则但旧客户端没提供对应输入时，返回明确缺失能力/字段诊断，不静默关闭规则。新客户端不能在旧后端报错后去掉字段重试。部署前先完成新后端、前端接线及数据检查，再显式启用规则。

### 7.2 规则管理

沿用已有 `getActiveRules` / `setActiveRules` 查询与保存启用接口及版本校验。增加规则模板、类型注册和数值编译映射；不另建一套配置存储，不在每条订单上存规则开关。

规则本身独立于交期优化：它表达“能否开工”，不是“是否晚交”。实现应以“任一启用规则需要生产时间轴”为触发依据；不应因为关闭某个交期目标就漏掉新硬约束。对当前不支持所需时间输入或数值执行能力的入口，应前置明确拒绝，不退回不检查的旧路径。

### 7.3 结果与诊断

继续使用 `current_process_start_at` 和 `current_process_latest_at` 回填开始、完成时间，不改“最晚日期”列来掩盖提前开工。

在现有规则诊断/交期报告中增加必要信息：来源订单、实际节点、所属大辊期及小辊期、最早开始时间、计算开始时间、提前秒数、规则身份。普通成功结果不新增第二套日期计算接口。

前端已有最早日期列保留，拆单片段继承原单信息。订单列表与导出继续以**当前步骤全部订单、全部列**为准；不能导出另一套独立修正后的时间。不合格诊断方案不得伪装为正式求解步骤数据。

## 8. 统一数值结构与唯一生产时钟

### 8.1 一次标准化

扩展既有时间输入模型与 `NumericOriginals` 原订单数值表，建议增加：

- `earliest_start_ms`：相对 `schedule_start_at` 的有符号 `int64` 毫秒偏移。
- `has_earliest_start`：是否提供有效下界的布尔数组；禁止用零或某个合法负数充当缺失标记。

真实节点通过既有来源索引读取原单下界，拆单无需复制一份可漂移的时间；虚拟节点没有真实来源索引，跳过下界检查。数组连续、只读并属于当前任务，不逐候选构建日期对象、字符串、映射或领域订单。

请求、标准化任务、缓存复用及审核身份必须覆盖新输入与规则启停。相同订单规格但不同最早时间不是相同排程任务；不能复用另一时间输入下的方案评价。仅做物理连接判定的缓存仍只承担物理连接职责。

### 8.2 在现有累计循环中判定

扩展 `_clock_view()`：读取当前 `clock` 作为节点开始偏移，按来源下界判断，再累加该节点时长作为完成偏移。交期评价和本规则读取同一次累计结果；最终报告复用已审核语义，不创建第二条可写时钟。

违规计入方案级汇总，同时保留节点及链定位。不要既记入链缓存又在方案汇总重复累计。数值编译器和明细投影共用同一规则、原因编号与单位转换。

新规则需要的额外工作是每个真实节点读取一次下界并比较；但实际增加的完整耗时还取决于搜索轨迹，不能仅凭比较次数承诺性能不变。

### 8.3 缓存边界

相邻规格是否可连接与绝对开始时间不同：本规则**不加入静态规格连接矩阵**，否则会错误地把依赖前面生产时长的判断固化成两节点关系。

同一条链内容没变，但前面的链顺序、用时或虚拟材变了，链中节点的开始时间就可能改变。因此：

1. 物理边和仅依赖链内容的规则仍复用原缓存。
2. 最早时间和交期评价不能只按链内容复用。
3. 首版沿用当前完整方案原生时间扫描，覆盖所有受影响的后续节点；不新增复杂的局部时间缓存。
4. 同一代次的只读输入可以复用；接受换序后，批次剩余候选及派生的提前开工标记按现有代次失效机制处理。

## 9. 搜索过程：必须能修复，不只是报错

### 9.1 保留总体流程

继续使用现有“规格连接与路径构造 → 首轮局部搜索 → 受控拆单及唯一重放 → 后置结构精修 → 独立审核”流程，不为新规则再建一套求解器。

初始方案仍以快速构造为主。完成后做同一完整评价，允许内部存在提前开工，作为后续修复起点；不能要求每条初始局部链脱离全局时间轴单独合格，也不能把未修复初始解当可发布结果。

### 9.2 修正禁止违规入口

当前后置精修的“存在任何禁止违规就退出”要细分：

- 仅存在本规则的提前开工：允许进入既有结构搜索，优先修复。
- 存在其他禁止违规：保留原处理边界，不因本规则绕过物理、资源、期锁和守恒保护。
- 候选即使降低了提前开工数量，也不能引入原本没有的其他禁止违规来交换收益。

实现时必须检查首轮、拆单、后置精修和公共候选消费的实际调用链，不允许只移除一行入口判断却让下游继续把所有提前候选提前拒绝。含提前开工的候选可以作为内部中间状态，但仍须通过现有完整质量比较及提交条件；不引入无界随机接受。

### 9.3 复用动作，增加问题定位

可用调整包括：将尚未就绪的订单/片段移后，将已经就绪且能连接的订单移前，交换节点/片段，以及在允许范围内调整整条小辊期顺序。优先使用既有规格矩阵定位直接可连接位置；必要时仍按原合法桥接规则修复连接。

只靠原有交期锚点可能漏掉“需要移后”的订单。因此在现有重点候选通道中纳入提前开工节点：按提前时长降序、实际位置及来源身份稳定排序；保留普通扫描通道，不能只处理最早的一个违规。

重点通道扩展仍遵守候选结构归属唯一生成，不先生成两份再去重；复用既有轮转、首改善接受、共享额度和取消规则。新规则关闭时不插入这些重点候选；启用时允许轨迹发生业务上有意的变化，并在对照中单独标注。

每个完整候选都重新评价全方案累计时间。例如把一个提前订单后移，可能使其他订单被提前；不能只检查被移动订单。跨大辊期仅使用原有合法资源动作，不能借本规则取消原订单期约束。

不得新增“为消耗时间而插入虚拟材”的用途、放大虚拟重量或虚构加工时长。原有为合法连接或链重填充产生的虚拟材继续计时，并接受原资源与比例规则检查。

### 9.4 无解与额度耗尽

在有限候选范围内没有找到零违规，只能说明本次未找到可发布方案，不能宣称数学上无解。最早时间集中偏晚、可提前排的订单不足，确实可能与“不等待”形成冲突，但不得据此自动放宽规则。

停止后保留真实停止原因、最好诊断方案及提前明细；建议用户检查本次开始时间和上游数据。是否改开始时间或另行支持等待，由用户决定。

## 10. 最终审核与发布

复用 `_numeric_audit.audit_numeric_core_without_search_cache()` 从原始任务、最终节点及规则重建数值任务，独立于搜索缓存重新累计并检查本规则。

正式发布必须同时满足新规则零违规、其他禁止规则零违规、来源覆盖及重量守恒、现有资源审核。未通过时保留现有不可发布结果语义，不回写前端正式方案，不伪装成输入格式错误或服务异常。

审核需要核验拆单来源继承、真实过渡材、生成型虚拟用时、最终生产链序及时间原点。报告与导出取同一审核结果的时间，不能排序展示后重新算出另一套日期。

## 13. 验证与验收设计

| 场景 | 必须验证的结果 |
|---|---|
| 计算开始恰等于最早时间 | 合格 |
| 提前 1 毫秒；完成晚于最早时间 | 仍违规；计数不因显示取整消失 |
| 下界早于本次开始；日期跨日/月 | 有符号偏移和累计正确，不截断 |
| 中间虚拟材及跨小辊期/大辊期 | 虚拟用时累计；边界不重置时钟 |
| 真实过渡材及每个拆单片段 | 均按来源下界逐节点检查 |
| 日期缺失、路线无当前工序、错误时区 | 前置清晰报错，不猜默认值、不静默关闭 |
| 一个节点或整链换序 | 后续未改链也重检；与手算时间一致 |
| 只有提前开工的初始解 | 能进入修复；可构造小例修到零违规 |
| 修复提前却引入其他禁止违规 | 不得发布，也不能绕过原保护接受 |
| 预算耗尽仍违规 | 诊断保留、不可发布；不宣称无解、不自动等待 |
| 新规则停用 | 同输入/种子/额度下原候选顺序及结果无额外变化 |
| 缓存、批量串行和无缓存审核 | 新输入身份、时间、计数和严重度完全一致 |
| 前端提交、回填、当前步骤导出 | 同一时间原点、显式时区、无 8 小时偏移、无第二次日期修正 |

必要测试集中按契约、数值规则与搜索、端到端审核组织，不要求每次小编辑全量测试。真实 GQGA4 对照须补齐并冻结每单最早时间；旧基线缺少该字段不能假填后宣称“同输入”。

真实对照固定原订单物理数据、九项目标顺序、开始时间、种子及预算，分别记录启用前后九项值、提前节点/来源数、总提前秒数、耗时和停止原因。新规则合法地改变可行方案范围，不能要求启用后排程序列与旧结果相同；也不能提前承诺交期或耗时一定改善。Windows 发布包测试与本地后端验证分别记录。

**本稿没有运行上述测试，没有启用新规则，也没有产生新排程结果。**
