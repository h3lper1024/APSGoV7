### 2.1 本次运行已经观察到的事实

A2 和 FB2 均实际执行。保护检查次数不是全部候选次数；两类拒绝合计 12,219，不应除以 2,000,000 后声称是保护自身的拒绝率。接受拆单为零也不能单凭计数证明拆单阶段从未进入。

日志缺少逐阶段消耗与明确跳过原因，因此只能确认候选总额度耗尽，以及存在后置阶段被前置阶段占用预算的控制风险；不能把全部 200 万次精确归因于整链合并，更不能宣称所有精修邻域已经充分搜索。本设计用阶段进入、退出和覆盖记录补足这一证据缺口。

### 2.2 当前源码的三处顺序阻塞

| 位置 | 固定基线行为 | 风险 |
|---|---|---|
| `_numeric_search.py::_run_numeric_local_search()` | 顺序执行整链、真实节点迁移、虚拟补重、整链调序，共用总预算 | 第一个算子可能占满预算，基础搜索内部也存在后续算子无机会的问题 |
| `_numeric_refinement.py::run_numeric_serial_search()` | 只有 `stop_reason is LOCAL_SEARCH_COMPLETE` 才进入受控拆单和结构精修 | 前置阶段耗尽预算时，后续修复无法进入 |
| `_numeric_search.py::improve_numeric_controlled_split()` | 接受拆单后内部调用 `_run_numeric_local_search()` 回放 | 隐含回放仍可占满剩余预算，侵占后置精修机会 |

不能只删除外层两个 `if LOCAL_SEARCH_COMPLETE`；必须一起处理基础算子额度、拆单回放和外层调度。

### 2.3 当前预算语义必须准确保留

`budget.py::SolveRuntimeBudget` 持有唯一候选计数、搜索截止时间、最终截止时间及取消令牌。`must_stop` 当前将任意非空 `stop_reason` 视为停止；`allows_search()` 调用 `permit(0)`，候选计费调用 `permit(1)`。

特别注意：当前候选计数恰好等于总上限时，`permit(0)` 不会仅因相等就失败；再次申请正数额度才会触发超限。这使最后一个已计费候选仍可检查时间、取消并完成提交。阶段控制不得把比较简单改为 `used >= limit` 后用于所有继续检查，破坏这一边界。

现有精修并非完全没有提前感知。`_numeric_refinement_scan.py::build_scan()` 从已有完整评价中提取 `EARLY_START`，优先排列相关来源；`intra()` 将跨过提前节点的前移动作纳入关键扫描。因此先保障现有精修的执行机会，再评估新增算子的必要性，有利于区分两类改动的收益。

## 3. 目标、非目标与术语

### 3.1 目标

保证适用的后置阶段在全局资源允许时获得明确机会；候选总数不超限、截止时间和收尾窗口不重置；阶段退出不伪装全局停止或收敛；取消、错误、候选身份与正式提交保护继续有效；通过阶段日志区分“未进入、被截断、扫描完成、进入但无改善”。

### 3.2 不在本次范围

不增加全局候选上限或延长总时间，不新增等待、改变订单下界或工时；不修改九项质量及其顺序、其他规则逐项保护、FB2 新增借入就绪和既有借入不恶化条件；不新增拆单授权、桥接策略、第四项组合修复或 A2 路径分段；不改变回写政策，不自动修改 YAML、SQLite、依赖、前端或用户服务。

预算分配会改变各类候选的访问机会，真实最终结果和接受轨迹可能变化；不能承诺与旧调度逐候选一致。最早规则停用时仍保持关闭语义和各阶段既有适用性检查，不因新调度启用本来不适用的规则或动作。

### 3.3 术语

| 名称 | 含义 |
|---|---|
| 全局预算 | 一次任务唯一的候选总账、搜索时限和取消状态 |
| 阶段配额 | 某阶段在全局剩余额度内能够使用的份额，不是新增预算 |
| 时间片 | 某阶段的一段协作式执行时间，到期后在安全检查点让出控制权 |
| 已获准候选 | 已在原计费点成功申请额度、尚未完成全部校验的候选尝试 |
| 完整正式状态 | 当前已接受的任务、方案、评价、代次及资源序列一致的状态；可以存在被允许继续修复的业务违规 |
| 代次 | 方案版本标识；接受新方案后，旧候选或旧扫描覆盖结论不能直接复用 |
| 机动池 | 预留及归还的未消费额度，仍属于同一全局预算 |

## 4. 方案取舍与首版流程

| 方案 | 判断 |
|---|---|
| 只提高总候选上限 | 不解决阶段占用关系，不作为本次方案 |
| 前置耗尽后清空停止原因或给修复新建预算 | 会绕过总账、截止时间或取消语义，禁止 |
| 只给基础搜索一个整体配额 | 能保护外层精修，但基础内部和拆单回放仍可能相互挤占，不完整 |
| 保留阶段顺序，设置分层配额和机动回补 | 作为第一版，改动目的清晰，便于单独验证 |
| 全面动态轮转、在线学习配额或同时增加新算子 | 暂不采用，避免扩大本次范围 |

首版流程：

```text
原初始构造与 A2 调序
  → 建立正式搜索状态，读取剩余全局预算
  → 基础局部搜索：四个算子分别限额
  → 受控拆单扫描
  → 发生拆单时进行有限回放
  → 现有结构精修：获得保留额度
  → 未用额度回补尚未完成且仍适用的工作
  → 原最终审计、结果组装与签发
```

“后置获得机会”以全局时间、取消状态、适用性及足够最小额度为前提；不能承诺已取消或全局资源耗尽时仍执行每个阶段。

## 5. 候选配额及唯一总账

### 5.1 在搜索入口冻结分配基数

令 `L` 为全局候选上限，`C0` 为进入数值搜索时已用计数：

```text
B = max(0, L - C0)
phase_used = global_count_now - global_count_at_phase_entry
```

不清零 `candidate_check_count`，不按原请求上限重复发放已消耗额度。阶段记录起始计数和分配量，正式计费仍只修改全局计数器。

### 5.2 首轮分配建议

以下比例是待实测的初始参数，不是已经验证的最优比例或生产配置值。

| 顶层阶段 | 比例 | B = 2,000,000 时 |
|---|---:|---:|
| 基础局部搜索 | 20% | 400,000 |
| 受控拆单及有限回放 | 10% | 200,000 |
| 结构精修 | 60% | 1,200,000 |
| 机动池 | 10% | 200,000 |

先用整数计算前三份 `B * percent // 100`，剩余全部进入机动池，避免浮点误差或取整增发。保留额是使用上限，不强迫阶段消耗完。

对于极小预算，零额度阶段必须明确记录 `insufficient_budget`，不能为每阶段强行补一份导致超支。存在提前违规且精修适用时，可以从机动池优先申请一个最小计费单位；该单位必须从机动池扣除，仍可能因全局时间或取消而无法执行。

第一版不要求新增请求字段或前端开关。配额集中维护为有名称、可校验的内部调度方案，实际比例及调度版本写入诊断；若以后进入 `SolverPolicy`，再明确请求、指纹和兼容性，不在本次文档提交中改配置。

### 5.3 基础四算子子配额

在基础搜索份额中，首轮按 50% / 25% / 10% / 剩余分配：

| 基础算子 | 基础份额占比 | 基础份额 400,000 时 |
|---|---:|---:|
| 整链合并 | 50% | 200,000 |
| 真实节点迁移 | 25% | 100,000 |
| 虚拟材补重 | 10% | 40,000 |
| 整链顺序调整 | 剩余约 15% | 60,000 |

整链算子到自己的上限后进入节点迁移，不把父阶段直接标记为全局结束。提前完成或不适用的子阶段释放未用额度，但第一轮优先保证后续保留额度，不立即把全部余额返给最前面的整链合并。

### 5.4 拆单扫描与回放共同受限

拆单扫描和拆单后回放必须拆成可独立调度的步骤，二者合计不超过该顶层阶段份额。内部具体比例由后续实施计划固定并记录，不声称已有最优分法；必须预留回放份额，不能让扫描无条件消耗父阶段全部额度。

没有实际接受拆单则跳过回放。接受过拆单但扫描被阶段配额截断时，保留待回放标志，仍可在预留额度内整理。第一版每次受控拆单阶段至多触发一次受限回放；回放中的基础算子也有子配额，不递归再启动拆单，不重置全局预算，不把一个回放切片当多次完整回放。

### 5.5 守恒与回收

```text
sum(顶层阶段实际消费，包括各次回补) = C_final - C0
C_final <= L
未消费的保留额度 + 当前未分配余额 <= L - C_now
```

子阶段消费包含在父阶段中，不能将父子计数相加后再与总账比较。已经计费但拒绝、被取消或因错误未提交的工作不退款；只能归还未消费额度。重新分配不修改已用计数，也不能重复释放同一份保留额。

## 6. 全局终止与阶段退出分离

继续传递同一个 `SolveRuntimeBudget`。建议在其上增加阶段作用域或向编排函数传递轻量阶段控制对象；后者引用原预算而不是复制总账。现有代码有预算类型检查，不能随意传入接口不兼容的替身或重新调用 `from_policy()`。

下列名称是拟增加的阶段内部语义，不宣称已存在于 `SearchStopReason`：

| 阶段结果 | 含义 | 全局处理 |
|---|---|---|
| `scan_complete` | 当前代次完成该阶段约定的扫描 | 进入下一阶段，不等于全局收敛 |
| `candidate_slice_exhausted` | 本阶段没有新候选额度 | 让出控制权，保存可恢复位置 |
| `time_slice_exhausted` | 本阶段时间片到期 | 安全退出，未授权新工作不再启动 |
| `not_applicable` | 既有适用条件不满足 | 记录跳过，不扩大规则范围 |
| `insufficient_budget` | 无可分配最小额度 | 记录跳过或等待回补 |
| `global_stop` | 真正的全局终止 | 不再进入后续搜索阶段 |

阶段额度或时间片耗尽不能写成全局 `CANDIDATE_LIMIT_REACHED`、`SEARCH_TIME_LIMIT_REACHED`，更不能写成 `USER_CANCELLED` 或数值 `CANCELLED` 错误。用户取消、全局截止、输入或系统错误按原链路传播，绝不通过换阶段清除。

新版编排中，算子不再用 `budget.stop_reason = LOCAL_SEARCH_COMPLETE` 互相传话；自然扫描完成通过阶段结果返回。全局终止由预算及最终编排统一负责。外部停止原因若需新增枚举，必须在实施计划中列明 `contracts.py`、签发和序列化的兼容修改，不能直接返回未定义字符串。

## 7. 阶段进入条件与完成语义

### 7.1 基础搜索

每个算子独立获取子额度和退出结果。阶段中断时仅保留已正式接受的 `state`；质量不改善的候选继续拒绝。一个算子配额用完不阻止兄弟算子获得其预留份额。

### 7.2 受控拆单

入口为：全局未终止、正式状态完整、拆单规则适用、有可分配预算。资格扫描自身也受时间与取消检查，不能为了确认存在候选先无限扫描。

不再依赖基础搜索自然收敛，也不要求提前节点清零。业务违规不等同于状态损坏。来源守恒、拆单授权、目标期间锁、连接修复、完整质量比较及 FB2 保护全部保留。

### 7.3 拆单后回放

由编排层依据是否实际接受拆单、待回放状态和剩余份额决定进入，不由拆单函数暗中启动无限基础搜索。若全局停止，保留已接受完整状态进入原收尾，不能为完成回放而继续计费。

### 7.4 结构精修

入口为：全局未终止、正式状态完整、自身适用且获得预算。删除对前置 `LOCAL_SEARCH_COMPLETE` 的控制依赖，但保留精修自身规则检查。

固定基线中，最早开工规则未启用且方案含禁止违规时，精修会跳过；启用时可进入并依靠原接受保护避免增加其他禁止项。本次不把这两种情况一律放开，也不能重新引入“有任何其他禁止违规就禁止提前修复”的旧问题。

现有关键与普通动作族交替策略、候选顺序、首次清理和完整质量比较尽量保持。初版不同时新增第四项组合修复动作，不把“进入精修”当作“必能消除提前”。

### 7.5 机动回补与全局结束

先履行适用阶段的保留机会，再使用机动池。仍有提前且精修因阶段配额中止时，优先继续精修；其次处理待回放、未完成的合法拆单和其他未完成扫描。优先级及额度领取顺序必须确定，不能依赖无序容器或随机时钟值。

同代次已完整扫描且没有改善的工作不无条件重跑。后续接受新方案后，旧代次完成记录失效；是否重新执行依据新代次和剩余全局预算判断。

只在当前代次所有约定且适用的搜索工作完成、没有待恢复截断工作时，才可给出与覆盖范围相符的完成结论。仅把四个阶段各调用一次，不能宣称全局局部最优。首版优先继续消费可用机动份额，直到真实全局终止或约定扫描完成；不得为方便退出而伪造候选耗尽或收敛。

恢复时需保证进展：继续同代次游标，或者按新代次重建。零额度、零进展或已失效状态不能无限反复入队，必须记录原因并结束该次调度尝试。

## 8. 已计费候选的完成边界

### 8.1 分开“申请新工作”和“完成已获准工作”

| 操作 | 检查内容 |
|---|---|
| 枚举下一段候选 / 启动新尝试 | 全局停止、阶段额度、阶段时间片、当前代次 |
| 原计费点申请候选检查 | 原全局上限、父子阶段份额、时间和取消；成功只计费一次 |
| 完成已获准的候选评价、FB2 检查、物化和提交 | 全局时间、取消、错误、身份及原接受条件继续检查；不能仅因阶段计数刚好达到上限拒绝完成 |
| 需要另一次原规则计费的桥接或变体尝试 | 必须重新申请，不能借用上一次授权免费执行 |

阶段额度为 100 时，第 100 次若已成功计费，可以完成当前授权尝试；不能启动第 101 次。阶段软时间片到期后，已获准的有界尝试可以完成，但真正的全局截止或取消必须立即按原检查点生效。

当前消费、桥接、物化和 `NumericSearchState.commit()` 都会检查预算，必须沿整条链区分边界。不能把 `allows_search()` 全局替换为阶段 `used < limit`；也不能让“正在处理”成为无限嵌套桥接的免计费通行证。

### 8.2 原计费位置保持

本次不重新定义一次候选检查，不把原本不计费的枚举继续标记当真实候选扣额，不给 FB2 消费与提交复核再加一笔额度。提前过滤、完整评价、批量消费和变体原有计费位置必须逐一列入实施清单，防止重复收费或漏收费。

配额关闭时，原 `SolveRuntimeBudget` 的基本行为保持；开启阶段范围后，所有已有正数额度申请都必须受父子配额约束，不能只限制最外层 `for` 循环。

## 9. 时间片与收尾窗口

时间分配基于数值搜索入口的剩余搜索时间：

```text
remaining_search_time = max(0, search_deadline_monotonic - clock())
phase_deadline = min(search_deadline_monotonic, phase_enter_time + granted_time)
```

不使用 `final_deadline_monotonic` 作为搜索时间分配基数，不重设两个截止时间，不动 `finalization_reserve_seconds`。可先采用与候选配额相同的顶层比例，并记录实际配置；子阶段及回放同样受父时间片限制。

候选配额和时间片谁先用尽，谁限制新工作。枚举大量组合但很少生成候选时仍有时间检查；枚举器已有有界继续点应复用，不能只在成功生成候选后检查。

时间片是协作式、非抢占的。一个正在进行的有界计算单元可能越过阶段软截止，实际超出必须记录，并从后续可用搜索时间中扣除，不能通过补足各阶段原时间份额延长全局截止。是否能给出具体最大超出值取决于实际检查粒度，未经测量不得承诺固定毫秒上限。

候选配额主导时有较强可重复性；墙钟时间片命中会受机器负载影响，不能承诺跨机器接受轨迹完全一致。测试应使用可控时钟，真实诊断记录配额、阶段用时、退出原因与模式版本。

## 10. 批量候选、工作区与阶段切换

精修批次同时受原批大小、全局剩余额度和当前阶段可用份额约束。仅限制最终消费而无限预计算，会继续占用其他阶段时间，不能视为阶段预算已经落实。

描述预取或原生预计算不等于候选已获得正式计费授权。实际消费仍在原计费点申请；未消费、已失效或因阶段结束丢弃的结果不记作接受，也不记作正式 FB2 拒绝。其真实计算用时和丢弃数量应记录，不能冒充零成本。

阶段切换必须在完整正式状态上发生：释放私有工作区，关闭枚举生成器，丢弃未消费候选及失效预计算；不发布半成品，不回滚此前完整接受的动作。清理失败按真实错误处理，不能将异常降格为正常阶段退出。

回补同代次工作可保留紧凑的扫描游标和动作族进度，不保存跨代次候选数组。其他阶段接受新方案后，按新任务、方案指纹和代次重建；候选的链身份、位置、资源序列及评价必须重新绑定。

不能每次恢复都从前几个已拒绝组合重新开始。若现有某算子暂不支持恢复，应在实施计划明确补齐游标或采用有限单次调用，不能写成已经具备完整可续扫能力。

## 11. 建议控制对象与编排接口

以下为设计名称，不是现有仓库接口，实际落点在实施时按现有风格统一。

| 对象 / 结果 | 建议包含的信息 |
|---|---|
| 阶段额度记录 | `phase_name`、`parent_phase`、入口全局计数、候选份额、时间份额、阶段软截止 |
| 阶段进度 | 当前任务 / 方案身份、代次、算子游标、是否有待回放或已计费尝试 |
| 阶段结果 | 内部退出原因、是否完成约定扫描、实际消费、接受数、前后代次及全局停止原因 |
| 分配器 | 入口剩余总量、未兑现保留额、可回补余额、确定性的领取与回收记录 |

编排示意：

```python
# 仅为接口示意；不代表上述函数已经实现。
state = create_search_state(...)
allocator = create_stage_allocator_from_remaining(budget)

for phase in planned_phases:
    if global_search_has_stopped(budget):
        record_remaining_phases_skipped("global_stop")
        break
    if not phase.is_applicable(state):
        record_phase_skipped(phase, "not_applicable")
        continue
    grant = allocator.allocate(phase)
    if grant.is_empty:
        record_phase_skipped(phase, "insufficient_budget")
        continue
    with budget.phase_scope(phase.name, grant) as control:
        outcome = phase.run(state, budget, control)
    record_phase_summary(phase, outcome, state)
    allocator.release_unused_once(control)
    if outcome.global_stop:
        break

run_pending_work_with_remaining_allowance(state, budget, allocator)
finalize_current_complete_state(state, budget)
```

全局额度“正好已用完但最后一个候选在途”与“可以启动新阶段”是不同状态；编排不能用一次普通 `permit(0)` 就认定有新候选可分配。完成在途工作后再决定全局结束，不再申请虚假候选来制造停止原因。

## 13. 阶段诊断设计

建议新增 `numeric_search_phase_summary`，同时记录真正进入和未进入的阶段；已有初始就绪、借入拒绝与精修动作族汇总继续保留，不重复计分。

| 字段组 | 建议内容 |
|---|---|
| 身份与模式 | 请求 ID、调度版本、阶段和父阶段、进入/退出方案指纹与代次 |
| 执行机会 | `entered`、跳过原因、分配候选份额、时间片、是否回补 |
| 实际工作 | 全局计数起止、阶段候选消费、完整评价、接受数、实际耗时、软截止超出 |
| 质量变化 | 前后提前节点数 / 原单数 / 提前总毫秒、其他禁止数、欠重、虚拟重量及完整质量键 |
| 阶段结束 | 内部退出原因、扫描覆盖状态、是否待恢复、全局剩余量及真实全局停止原因 |
| 批量与清理 | 未消费 / 失效批次丢弃数，清理是否完成 |

提前指标复用绑定当前方案的已有完整评价，不另建生产时钟。中断没有合法后评价时不得填造改善值，应标记未完成并保留最后正式状态指标。

对全局停止后未进入的阶段，明确输出 `entered=false` 和原因；诊断缺失不能继续充当“应该没有执行”的唯一证据。异常退出也应尽量记录已有汇总，但不能吞掉原异常。

顶层阶段消费可求和校验总账；子阶段明细标明包含关系。阶段完成记录绑定代次，不将旧代次的“无改善”当成新代次的结论。

## 14. 新增功能测试与验收边界

本次只写设计，没有执行下表测试。后续使用已有依赖、合成状态、可控时钟和明确的边界替身验证新增功能；不得把替身测试描述成真实求解器或全量回归通过。

| 测试场景 | 应满足的行为 |
|---|---|
| 前置阶段持续产生拒绝候选 | 到阶段上限让出，后续适用阶段仍能进入 |
| 基础整链算子耗尽子额度 | 节点迁移、补重和调序的保留机会不被吞掉 |
| 第 N 个已计费候选改善 | 完成必要校验并提交；第 N+1 个不得获准 |
| 第 N 个候选还需新增桥接尝试 | 无剩余额度时不能免费继续，保留原正式状态 |
| 正好达到全局上限 | 已获准尝试可完成；不能启动后续新候选或阶段 |
| 阶段软时间片到期 | 安全让出，不伪造全局超时或取消 |
| 枚举很多但没有候选 | 仍能在有界时间检查点退出 |
| 全局时间耗尽或用户取消 | 不得通过换阶段清零停止原因后继续 |
| 最终收尾窗口 | 原两个截止时间不变，不用收尾预留运行搜索 |
| 阶段提前结束、不适用及极小预算 | 未用额度仅回收一次，零份额不增发，不忙循环 |
| 拆单接受与有限回放 | 回放受父额度约束，无拆单不回放，不侵占精修保留额 |
| 批量预计算与中途接受 | 未消费和旧代次结果正确丢弃，不重复计费或记拒绝 |
| 回补扫描 | 同代次续扫；新代次重建，不反复扫描同一被拒前缀 |
| 有其他禁止违规且启用最早规则 | 精修适用性和原其他规则保护同时保持 |
| 全部约定阶段走过但部分被截断 | 不误报当前代次完整扫描或局部最优 |
| 诊断及父子计数 | 进入/跳过均可追溯，顶层消费之和等于全局差值 |

控制流验收首先证明“没有超预算、修复获得机会、最后已计费候选不被误杀、取消不复活”，不把提前数量必须下降作为这些单元测试的替代。

用户本地真实对照应固定同一输入、规则快照、开始时间、下界、重量口径和全局预算，先只改变调度。分别观察初始质量、各阶段机会与消费、最终提前和其他质量，不同时提高上限、关闭 FB2 或加入新算子，否则无法归因。

## 15. 风险、兼容性与约束

保留额度只解决执行机会，不保证现有候选能通过 FB2，也不保证消除全部提前。若精修获得份额仍大量因既有借入恶化被拒绝，下一步研究定向组合修复，不自动放松保护。

20/10/60/10 及基础子份额均是首轮验证起点。配额过小可能减少普通合并收益，过大仍可能挤占修复；后续依赖阶段诊断调整，而不是把示例数字视为最优。不得为提升表面提前指标引入等待、额外耗时虚拟材或改变日期。

真实运行未完成的逐阶段归因仍有不确定性。本设计不声称旧精修一定能解决当前 1,600 余个提前，也不因数据数月级时间错位直接认定数学无解。

共享 `budget.py` 会影响直接调用者；传统路径不在本次改造范围，必须保证未进入阶段范围时仍遵守原接口。搜索调度造成的轨迹变化与业务规则语义改变要分开说明，不能承诺不变的结果指纹。

阶段软退出、原生取消状态和系统错误必须区分。所有临时状态应在完整候选边界清理，不发布半成品，不使用独立预算对象绕过原权限和终止机制。
