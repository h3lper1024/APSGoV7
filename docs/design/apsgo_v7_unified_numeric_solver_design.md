## 2. 为什么需要统一实现

当前已有数值任务、数值方案和编译评价内核，并非从零重写。主要问题是候选在不同阶段的处理方式不同：

| 当前入口 | 已核实的实现方式 | 需要解决的问题 |
|---|---|---|
| [`_numeric_search.py`](../../src/apsgo_scheduler/core/_numeric_search.py) 的 `apply_numeric_candidate()`、`_try_prepared_candidate()` | `_layout()` 将整个方案展开为 Python 链序列，部分候选先构造完整方案再评价 | 首轮拒绝候选也承担全布局和正式方案构造 |
| [`_numeric_refinement.py`](../../src/apsgo_scheduler/core/_numeric_refinement.py) 的 `_try_overlay_candidate()` | 先评价变化链覆盖，接受时才构造完整方案 | 已有延迟物化能力，但未成为各搜索阶段共同入口 |
| 同文件的 `_prepare_repaired_parts()` | 修改链使用元组和列表，桥接过程中创建资源工作区及完整候选包装 | 数值评价之前仍有高频 Python 准备工作 |
| [`_numeric_resources.py`](../../src/apsgo_scheduler/core/_numeric_resources.py) 的 `extend_resource_workspace()` | 有 128 项缓存，未命中时扩展任务、重绑定规则和评分 | 追加少量私有资源仍可能复制全部基础列并计算正式身份 |
| [`_numeric_batch.py`](../../src/apsgo_scheduler/core/_numeric_batch.py) 的 `pack_numeric_candidates()` | 接收已准备的候选，再打包链和私有资源数组 | 批量入口过晚，形成另一道表示转换 |
| [`_numeric_kernel.py`](../../src/apsgo_scheduler/core/_numeric_kernel.py) | 单候选和批量串行共用实际编译评价内核 | 这部分应复用；不能再为统一改造重写第二套评分公式 |

正式接受已经统一归 `NumericSearchState.commit()`；分散的是接受前的候选准备、数据访问和资源处理，不是存在多个互不相认的正式提交者。

三种选择的取舍：

| 方案 | 结果 | 本设计选择 |
|---|---|---|
| 仅规定统一字段格式，各阶段分别实现 | 数组相同，但链编辑、私有资源和候选处理仍可能重复或转换 | 不采用 |
| 将所有阶段合成一个巨型函数 | 容易混淆初始构造、拆单、首改善等不同控制语义 | 不采用 |
| 公共数值计算层＋独立阶段控制 | 同一操作复用同一实现，阶段保留算法顺序 | 采用 |

## 3. 整体架构：一个计算层，两侧边界

### 3.1 职责分层

| 层次 | 负责什么 | 不负责什么 |
|---|---|---|
| 输入与输出边界 | 请求校验、规则加载、单位转换、文本编码；最终对象、CSV、诊断及审核报告 | 不在每个候选中重新解析业务对象 |
| Python 阶段控制 | 调用阶段、选择动作族、申请有界描述批次、管理额度/取消、按序消费、决定接受与停止 | 不逐节点复制链、遍历原型组合或解释规则 |
| **公共数值计算层** | 数值数据访问、图和位置索引、结构描述生成、链编辑、连接修复、资源派生、完整评价 | 不自行改阶段顺序，不直接发布当前解，不操作 HTTP、SQLite 或前端 |
| 正式状态发布边界 | 接受后确认资源编号、生成正式方案与身份，更新代次和缓存 | 拒绝候选不得进入此边界 |
| 独立审核边界 | 从原输入及正式接受事实重建，检查规则、来源、期锁和守恒 | 不直接信任候选缓存及其评分 |

高频数据使用 NumPy 原生数值数组；有序搜索、链编辑及不规则组合循环使用这些数组上的 Numba 编译函数。不能为了形式上的向量化构造庞大的全组合数组，也不能以“仍然有循环”为由认定没有数值化。

对象、字典和 Decimal 可以存在于输入、输出、错误解释及低频控制边界。只承载数组引用的轻量包装也可以存在。禁止的是候选内反复创建节点业务对象、全链元组、规则结果字典及完整正式方案；不追求消除整个 Python 程序中的所有对象。

### 3.2 公共计算层的组成

| 公共能力 | 唯一职责 | 使用者 |
|---|---|---|
| 数据与数值标准 | 字段列、单位、有效掩码、索引域、规则数值表 | 全流程 |
| 图与位置索引 | 有序邻接、匹配队列/栈、节点位置、链首尾和结构归属 | 构造及搜索 |
| 链结构操作 | 读取片段、拼接、移动、交换、切链、换序，输出变化链 | 初始构造及所有结构动作 |
| 连接与修复 | 边可行性、直接连接、单材/双材桥接、适用的修复变体 | 首轮、填充、拆单、精修、回收 |
| 私有资源处理 | 虚拟材和拆片字段派生、来源/期锁/重量工时管理 | 需要动态资源的所有动作 |
| 候选计算 | 组合链操作与修复，执行阶段原有检查，调用评价内核 | 所有搜索候选；不强套初始构造 |
| 规则与评分 | 链、资源、交期及九级目标的权威数值运算 | 候选、接受复核与独立审核 |

共同能力不是为每个阶段提供一套包装后仍调用旧实现。阶段代码必须直接使用同一实现；初始构造共享链写入和规则原语，但保留自己的构造算法，不伪装成“当前解与候选解比较”。

## 4. 一套权威数据模型

### 4.1 数据容器

| 数据 | 数值表达 | 所有权与生命周期 |
|---|---|---|
| 任务基础列 | 按字段分列的整数/布尔数组，原订单、原型、已接受动态节点及来源索引 | 任务建立或正式接受资源时产生版本，计算期间只读 |
| 规则数值表 | 规则类型、作用域、参数、字段依赖和目标投影的数组 | 按规则和数值标准编译；不随普通候选重复编译 |
| 当前方案 | 节点行号扁平数组、链偏移、链身份、所属期及方案代次 | 唯一正式状态，候选不能原地修改 |
| 当前方案索引 | 链长、首尾、原单位置、结构拥有者、重点前缀、链事实及交期摘要 | 绑定任务版本和方案代次；接受后更新或失效 |
| 结构描述 | 动作码、来源/目标链、位置/区间、方向、结构拥有者、修复变体码 | 按原顺序生成；不携带完整候选对象 |
| 候选工作区 | 链引用顺序、变化链节点缓冲及偏移、私有资源列、拆分组和扩展事件 | 单次尝试私有；拒绝、取消或旧代次作废时释放有效区间 |
| 候选输出 | 状态码、九级键、链事实、资源/交期汇总及错误位置 | 纯数值结果；明细仅在接受和审核时生成 |

不同字段保持合适类型，不塞进一张混合型二维矩阵，不使用 `dtype=object`。类型标识、用途和动作使用整数码；文本仅在边界查表，编码值不能替代原先的业务排序规则。

### 4.2 行号、版本与字段完整性

节点、原订单、原型、拆分组和链具有不同索引域，接口必须注明所用域。基础行号稳定；候选新增行号为“当前基础行数＋候选私有行偏移”。批次实际缓冲位置另有偏移表，不能把物理地址或线程完成顺序用作正式身份。

私有资源必须提供全部已启用规则实际依赖的字段及派生列，包括角色、来源、期、牌号编码、温区、表面命中、同规格分组和工时等；不得仅数值化宽厚重而在规则计算时回查节点对象。未启用规则不额外强制原输入字段。

基础数组只读，私有区只允许所属尝试写入。每个描述携带当前任务版本和方案代次；正式状态变化后旧描述、旧视图和旧输出不能继续提交。

## 5. 统一方案读取与链操作

### 5.1 正式方案与候选使用相同读取接口

正式方案使用现有“节点行号＋链偏移”的结构。候选使用“正式方案＋变化链”：未变化链引用原片段，变化链写入私有连续缓冲，链换序只改变引用顺序，新增/删除链用链映射和有效数量表达。

公共读取函数根据链映射取得实际节点序列。边、链规则、资源和时钟内核都使用这一读取约定；正式方案是没有覆盖变化的特例。允许数值内核按顺序扫描全方案，但不先将所有链还原成 Python 元组，也不为了评价拒绝候选复制所有未变节点。

变化链内的必要复制可以保留；目标不是零拷贝口号，而是不再为局部变化重建整个方案。最终接口仍要求完整正式方案时，只在接受边界合并一次。

### 5.2 链操作公共函数

| 操作 | 输入 | 输出及约束 |
|---|---|---|
| 取片段 / 反向读取 | 链引用、起止位置、方向 | 数值范围或方向标记；不先产生节点元组 |
| 拼接 / 插入 / 删除 | 有序片段引用及插入节点行 | 写入受影响链缓冲，输出链偏移和长度 |
| 移动 / 交换 | 来源与目标位置、片段范围 | 同时返回所有受影响链，不分次发布 |
| 切链 / 合链 | 切点或有序链引用 | 新链映射、所属期和稳定身份的待确认记录 |
| 整链换序 | 链引用排列 | 改变顺序而不复制链内节点 |

各动作使用公共原语组合业务候选，不要求把所有动作硬编码成一种操作。原语只执行结构变化，不私自增加资源、改变期锁或接受新解。

## 6. 统一修复与私有资源实现

### 6.1 连接和桥接

保留原语义：先判断直接连接；不满足时依原原型顺序搜索单虚拟材并按原平滑指标择优；单材无可行方案时再按原顺序搜索双材，保持严格更优才替换和同分先到。修复变体仍遵守各动作原来的尝试条件与顺序。

所有阶段调用同一个桥接函数。边判定、虚拟字段派生及适用链检查读取公共规则表，不能在构造、首轮、拆单和精修中各维护一份宽度、厚度或温区公式。当前原型快速掩码与通用边判定的表达需逐项对照后收敛为同源原语；快路径不能遗漏规则。

### 6.2 资源工作区

候选中的虚拟材和拆片直接写入私有字段列，不创建 `NumericDynamicNode` 业务对象，不反复 `np.concatenate` 基础任务的全部列，不生成正式任务/规则/方案指纹。

原型扫描只计算候选参数；真正选中的资源才写入该尝试私有区。拆片同时记录父单、片段序号、重量、工时、目标期和用途；分隔材与归还链仍在同一尝试内处理。拒绝候选不留下正式资源或序号空洞。

记录资源扩展事件的先后及分组边界，使接受时可重现当前逐步追加的正式编号、谱系和祖先身份。不能为了少算指纹把原分步追加合并后悄悄改变公开身份；纯物理缓冲重排不构成业务编号变更理由。

### 6.3 容量管理

使用“容量＋有效长度”的连续缓冲；按有界候选批次分配，不按全部 40 万次额度预分配。容量不足返回数值状态，由外层扩容或缩批后重算同一尝试，不多扣候选额度、不推进随机数和来源游标。

达到安全上限仍无法容纳时明确终止并定位，不删候选、不静默降精度、不改用另一求解器。扩容后旧视图作废；候选间不共享可写尾部。历史 32 MiB 仅为旧批量缓冲估算，不是整个进程内存限制，新结构须重新记录实际内存范围。

## 7. 统一候选计算入口

### 7.1 公共入口及职责

下列为设计接口名称，用于固定责任，不是本轮新增的代码：

| 接口 | 输入与输出 | 调用边界 |
|---|---|---|
| `generate_candidate_descriptors` | 当前数值状态、动作/通道与游标 → 有界描述数组、新游标 | 动作的数值生成实现可以分开，描述协议和结构唯一归属共用 |
| `compute_candidate_attempt` | 共享基础状态、一个描述、修复变体、原阶段检查策略、私有工作区 → 数值候选结果 | **所有搜索阶段的唯一候选计算入口**；内部调用公共链操作、修复、资源和评价 |
| `evaluate_numeric_view` | 统一方案视图、规则表、资源视图 → 完整数值汇总 | 复用现有权威评价公式；候选及正式复核使用同一来源 |
| `consume_candidate_result` | 原序候选结果、当前状态、预算 → 拒绝/接受/停止 | Python 主控；维持原计费、首改善及错误生效时机 |
| `publish_accepted_candidate` | 通过复核的候选私有变化 → 新正式状态 | 主控唯一发布边界，沿用现有 `NumericSearchState.commit()` 职责 |

公共入口不能只是分发到各阶段原有的全布局实现。首轮和精修都必须以第 4～6 节的数据及操作完成一次候选，现有两条准备路径最终退出新数值语义的生产调用。

### 7.2 一次尝试的执行语义

候选计算内部依次执行结构编辑、适用修复、私有资源派生、原阶段事务检查和完整数值评价，返回固定数值结果。哪些禁止类型须直接拒绝、哪些中间工艺偏差参与评分，沿用原阶段政策并显式传入，不能新增全流程零违规的提前拦截。

两类拆单构造过程中的临时布局可以尚未达到完整候选条件；完成后统一执行来源、资格、片段目标期等保护，再进入评价与发布。共享原语不能把正式候选期锁错误地提前套在临时拆分布局上。

拆单保留原“准备成功后、期锁和评价前”的扣额点。公共候选入口内部的同一准备步骤可返回未评价的私有结果，主控扣额后再从该结果续算；不是另建拆单候选算法。续算核对描述、策略、规则/评分身份和工作区代次，未评价结果不能消费或发布；容量重试不扣额，准备失败不扣额，扣额后的期锁拒绝不增加完整评价次数。

初始构造没有“是否改善当前解”的语义，调用公共链写入、资源和规则原语即可，不使用候选接受接口，不新增候选额度消费。

### 7.3 接受与拒绝

拒绝路径只清理私有有效区，不创建完整正式方案、节点业务对象或评价明细。主控严格按原顺序消费九级键，接受首个严格改善候选，同分不新增隐藏裁决。

接受前核验版本和代次；接受时确认资源扩展顺序及编号、生成正式链序和方案、用同内核复核汇总并生成所需明细，最后一次性发布新状态和缓存版本。失败不得留下部分发布。其余旧代次预计算结果立即作废。

## 8. 顺序、额度和停止边界

| 边界 | 必须保持的行为 |
|---|---|
| 结构归属 | 每个节点、区间、链或结构对直接拥有候选；不按每个订单重复展开链动作后再去重 |
| 搜索顺序 | 原阶段、动作、位置、原型、修复变体及稳定同分顺序不变；保留每原单 4 次推进与重点/常规各 64 次轮转 |
| 随机性 | 保留原随机源、种子、调用顺序与数量；不能直接用 NumPy 随机生成器替换原打散机制 |
| 额度 | 描述不等于一次尝试；两种修复各保留原执行条件和扣额点，预取/容量重试/未消费后缀不额外扣额 |
| 错误 | 预计算的后续候选错误到原序消费时才生效，不能抢先中止前序可接受候选；内存安全失败和全局取消按停止契约处理 |
| 取消与时间 | 图遍历、深层位置扫描及修复使用有界工作段和数值续算游标，主控可检查停止；续算不得重复候选或重计费 |
| 行为对照 | 同输入、规则、数值标准、工作量且不触发时间截断时，候选/接受轨迹及结果一致；同墙钟时限下可能完成更多候选，另验证停止语义 |

逻辑尝试次数、完整评价次数、预计算次数、丢弃次数分别统计。不得以“数组化”“批量化”或“并行化”为由改额度含义、候选集合或接受策略。

## 9. 规则、数值标准和缓存共用

### 9.1 复用已实现的权威公式

现有 `_numeric_kernel.py` 保留为规则、链事实、资源、交期和九级评分的唯一计算来源，改造其数据访问，使其直接读取基础列与私有尾部、正式方案与变化链。不能另建“快速评分”“并行评分”或阶段专用近似规则。

当前 `_numeric_rules.py` 的对外保护包装可以保留；经统一内部契约确认合法的数组，不再每次转元组、建集合又转回数组。必要校验仍由输入边界、结构描述和候选事务承担，不能以消除包装为由取消校验。

明细按需从相同原语生成。最终独立审核从原始请求、启用规则和接受资源事实重新建列、编译并全量评价，不复用候选缓存；输入/输出对象转换在此是合理边界。

### 9.2 数值标准不重新决策

| 内容 | 继承的约定 |
|---|---|
| 物理量与重量 | 按任务及字段选择精确十进制倍率，覆盖订单、原型、规则参数；不先转浮点，不提前舍入原重量 |
| 缺失与类别 | 使用有效掩码和明确类别码；缺失与零不同，不能用整数码大小改变业务排序 |
| 时间 | 整数毫秒累计，原小时工时只转换一次；原始正工时量化为零须前置报错；交期为当天 24 点 |
| 四舍五入 | 已约定量化点均用 `ROUND_HALF_UP`；评分时间按已确认秒精度；不用半偶舍入，不新增其他舍入点 |
| 拆分 | 片重精确守恒；按稳定片段序号累计分配父单毫秒，末端总和守恒；合法派生零毫秒片段仍计算来源覆盖 |
| 严重度与容差 | 继承现有整数公式与配置工艺容差，不恢复内部 `1e-9`/`1e-6` 隐藏宽限 |
| 安全范围 | 输入与动态扩展均证明 `int64` 单值和中间运算安全，超界定位失败，不截断或回退浮点 |

九级目标顺序保持：①禁止违规数，②禁止严重度，③欠重链数，④欠重总缺口，⑤上月已欠交订单全部完成时间，⑥旧欠等待与本月延期累计加权负担，⑦相邻链首尾宽差，⑧虚拟材重量，⑨非空链数。全部最小化、严格逐级比较；宽差包含跨大辊期边界。

完整公式及已确认业务含义继续引用原设计第 4、8、9、15 节和现有测试，不在本设计重新解释交期或修改目标。

### 9.3 索引和缓存的唯一归属

| 层级 | 可保留的数据 | 有效性边界 |
|---|---|---|
| 任务 / 规则 | 静态边判定、原型派生列、规则数值表及身份编码模板 | 输入、规则、数值标准及相关字段不变 |
| 当前方案代次 | 节点位置、结构归属、链排序/首尾/前缀、未变链事实和交期摘要 | 绑定代次；接受后只迁移核验为未变化的部分 |
| 候选尝试 | 变化链、私有节点、局部资源与评价结果 | 单次尝试私有；不能被其他候选缓存命中 |

沿用可信追加祖先与未变链核验语义，规则、所属期和节点内容均纳入有效性判断；不能只凭链号复用。各阶段不再维护重复的资源或位置台账。

拒绝候选不通过生成正式 SHA-256 才查缓存；采用受控任务版本、方案代次、稳定链引用及变化标记管理内部复用。正式指纹仍按原算法在接受/输出边界生成。现有 128 项任务扩展缓存不能成为继续全任务复制的依赖；新私有资源机制接通后，只保留实际仍有收益的有界缓存。

## 10. 各阶段如何接入统一实现

| 阶段 | 保留的阶段算法 | 必须调用的公共实现 | 不得残留的专用热路径 |
|---|---|---|---|
| 任务建立 | 原输入校验、期序和规则选择 | 数据列、单位、编码和规则编译 | 搜索过程中回查业务对象取数 |
| 连接图 | 原节点排序、随机打散、有序边生成 | 公共边判定；邻接节点数组和偏移 | Python 邻接列表构造后再整体转数组 |
| 路径覆盖 | 原广度优先分层、深度优先增广次序 | 数值匹配/距离、数组队列/栈及邻接游标 | 带 Python 迭代器的节点栈；替换路径算法 |
| 初始链 | 原种子、拼接和截链条件 | 公共链写入、连接及适用规则原语 | 每次追加转节点元组，或为加速添加构造约束 |
| 首轮局部搜索 | 原整链调整、真实节点移动、虚拟填充、整链调序次序 | 描述生成及统一候选计算入口 | `_layout()` 全链展开，评价前生成完整正式候选 |
| 受控拆单 | 同期间与未来借入归还原次序、资格和原子边界 | 公共拆片/分隔材派生、变化链及候选入口 | 临时节点业务对象，拆分候选单独扩展全任务 |
| 拆后唯一重放 | 原来要求的一次首轮重放 | 同一个已统一的首轮入口 | 备用对象版首轮或额外重放轮次 |
| 后置结构精修 | 原动作集合、优先通道及 4/64 节奏 | 同一描述协议、链操作、修复和候选入口 | 自己的一套候选对象、布局打包和资源工作区 |
| 连接材回收 | 原扫描顺序、保护分隔材及调用位置 | 公共链编辑、桥接和完整候选计算 | 专用近似分数或绕过来源/期锁检查 |
| 审核与输出 | 独立双审计和对外结果格式 | 同一数值标准及权威规则原语 | 将搜索缓存当独立审核结论 |

连接图保留压缩稀疏行形式，即“每个节点一段有序邻居数组＋偏移”，不因此新增 SciPy 依赖。图遍历有状态，不能为了统一候选接口而改成候选评分问题。

各阶段可能包含自己的数值算法函数；只要数据和公共业务运算来自统一计算层，就是职责划分，不是重复实现。判定分散的标准是“同一链编辑、资源派生或规则公式是否出现多份”，不是代码是否放在多个文件。

## 11. 模块组织建议

本设计不建立新的通用插件框架或独立微服务，仍在现有 `apsgo_scheduler.core` 内运行。保留 `_numeric_*` 模块体系，按下表收敛职责，不为目录整齐先大规模移动代码。

| 模块 | 统一后的职责 |
|---|---|
| `_numeric_units.py`、`_numeric_state.py` | 权威单位与数据；补齐正式状态、变化链、私有资源和描述协议 |
| `_numeric_chain_ops.py`（拟新增） | 共用数值链读取和结构操作，不携带阶段策略 |
| `_numeric_resources.py` | 共用桥接与动态资源数值原语；正式资源物化限于发布边界 |
| `_numeric_candidate_kernel.py`（拟新增） | 公共单次候选计算：链编辑、修复、阶段检查、资源和评价的组合；不发布当前解 |
| `_numeric_kernel.py` | 保留唯一规则与完整评价公式，共用方案/资源访问协议 |
| `_numeric_rules.py`、`_numeric_evaluation.py` | 编译与边界校验、数值结果转明细；不在内部热路径反复打包 |
| `_numeric_construction.py` | 构图、路径覆盖和初始构造的专有数值算法，调用公共原语 |
| `_numeric_search.py`、`_numeric_refinement.py` | 阶段控制及动作生成组织，统一调用公共计算入口；算法专有枚举在数值函数中运行 |
| `_numeric_batch.py` | 组织同一候选协议的有界批次，管理私有区偏移，不再接收一组 Python 完整候选重新打包 |
| `_numeric_solver.py`、`_numeric_boundary.py`、`_numeric_audit.py` | 端到端入口、输出映射与独立审核 |

两个拟新增模块分别承载已明确的公共职责，不是先创建空壳。实施时若现有模块足以承载，可调整物理文件归属，但不得改变唯一入口和依赖边界：阶段依赖候选计算，候选计算依赖链/资源/规则原语，公共原语不能反向调用阶段控制。

当前 [`solver.py`](../../src/apsgo_scheduler/core/solver.py) 仍按显式数值语义身份选择新路径，历史标准入口不是数值计算失败后的备用求解器。本设计统一新数值语义内部，不自动修改 SQLite 活动规则、正式 YAML、API、C# 或删除仍有调用方的历史公开入口；最终退役须另外确认迁移范围。新数值路径内部则不允许长期保留旧的对象候选路径。

## 12. 串行、批量与并行共用一个实现

**先实现整个数值串行流程的统一，再进行并行试点。**不能先只改精修修复函数，再把其他阶段仍各自准备候选的状态称为系统改造完成。

单候选、批量串行和后续候选并行都调用第 7 节同一个计算入口。批次从数值描述开始，直接分配私有区、计算并输出，不先建立完整候选对象。共享基础列只读，各候选输出和尾部互不重叠；主控始终保有原序消费和首改善接受权。

描述间可独立时才并行；同一描述内有依赖的修复尝试依原条件推进，或仅对已证明独立的尝试预计算。不得假设所有修复变体都可以无条件并行；后缀结果和错误遵守第 8 节的消费契约。

统一串行接通后，优先评估后置结构候选的修复、构造与评价整体作为并行试点。首轮/拆单使用共用串行实现，不因此自动并行化其依赖链；不引入多种子择优或线程竞争接受。

对比当前代码、新统一串行和同内核并行 1/2/4/8 线程。计时包含描述生成、修复、资源、评价、作废计算、接受和审核；没有端到端收益就采用已验证的串行。保留现有 NumPy/Numba 依赖，不因本设计引入 joblib、Dask 或 SciPy。

## 14. 实施依赖、风险与停止条件

设计上的依赖顺序为：冻结全流程同标准基线及覆盖清单；建立公共数据/链/资源原语和候选入口；各阶段接通并退出旧内部准备路径；完成完整串行一致性和耗时对照；再开展批量及并行收益验证。按模块分次实现可以，最终验收不能留下未登记的阶段例外。

| 风险 / 触发条件 | 处理方式 |
|---|---|
| 同标准候选、接受或最终结果出现差异 | 停止该接线的验收，定位第一分歧；不能笼统归因为 NumPy |
