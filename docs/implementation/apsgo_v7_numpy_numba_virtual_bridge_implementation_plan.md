## 4. 逐阶段实施步骤

### 4.1 阶段 0：基线、依赖和测量口径

1. 确认第 1 节授权，核对实际提交、工作树和文件归属；记录 `d55dadb` 完整基线身份。新文档提交不会改变此生产基线。
2. 在新干净导出执行原残留检查，复用 `tools/profile_solver_search.py` 的 `check/full`；冻结两份现场请求和正式质量请求。必要的工具修改先测试，新旧侧用同一工具。
3. 重新取得一份完整 Python 基线：初始/首轮/最终方案、完整有序评价、采纳轨迹、资源、拆单、双审计和实际缓存统计。首轮参考 64226/2263/34，完整参考 200000/3697/54、质量 `(0,0,0,0,11726,660,23)`；不一致先找首差异，不改期望。
4. 仅获授权后，在指定 Conda 环境检查并安装选定兼容依赖。优先保留 NumPy 2.2.6；按官方兼容表及实际平台二进制包锁定 NumPy、Numba、llvmlite，记录包来源、版本和 Python/平台。同时冻结适配的 `pyinstaller-hooks-contrib` 版本，阶段5以构建脚本一处私有确切版本常量负责安装与校验，保留单行 `requirements-build.txt` 职责。不凭另一平台可导入推断 Windows 可用。
5. 用本项独立小探针验证数组、缺失掩码、分支、严格浮点顺序及 `nopython_signatures`；测首次编译、同进程再次调用和重启成本。探针不是生产桥接，不把微型函数编译耗时代替最终内核冷启动。
6. 核对现发布 hooks 与依赖版本、既有源码/缓存禁入约束。能进行 Windows 技术冒烟时提前验证，不能时保留待验；若已证明依赖/冷启动不可行，暂停，不继续生产接线。
7. 冻结候选块大小初值64及比较豁免叶子清单：只有计时、真实代码身份、缓存实际统计及新增内部执行统计可变，业务内容不豁免。记录未触墙钟前提。

交付 `stage_00_baseline/`：源码/工具/输入/环境身份、实际基线、版本可行性和首次编译观察，独立提交。该阶段不改变原桥接运行路径。

### 4.2 阶段 1：依赖声明和数值适配

1. 修改项目依赖；架构测试只给 `_bridge_numeric.py` 一条精确例外，其他核心导入 NumPy/Numba 仍失败。不直接从其他模块导入 llvmlite。
2. 新增私有模块，准备原型目录、缺失掩码、当前锚点投影及有序规则参数。每条数值边都有虚拟端点，不建立不会使用的类别编码；真实直接边仍走原规则。原业务对象仍留在 Python，所有规则值作为参数进入内核。
3. 仅支持设计四种具体边规则，每类至多一个实例；精确类型、规则集/边缓存/工厂行为也校验。不支持、重复、自定义规则及不安全投影返回“不适用”，不能静默丢一条规则。
4. 按需准备、有界分段，保持温区取原左右锚点的语义；不预生成试探 Node 或常驻二维/三维大表。未被访问的非法字段不得提前变成业务错误。
5. 验证数组形状、索引、缺失/零值、参数顺序、目录稳定性，以及不同规则/原型/请求之间不串用。此阶段不改正式 `bridge()` 路径。

交付 `stage_01_numeric_inputs/`：适配测试、架构门禁、实际依赖版本和保留的 Python 基线。

### 4.3 阶段 2：判边和顺序选桥

1. 实现严格 float64、`fastmath=False`、不并行、启用边界检查的最小内核；复用同一判边函数，不为单桥和双桥复制四种公式。
2. 规则按原启用顺序全部执行，保留缺失与异常分支；中间溢出返回“需要原处理”，不是“不连接”。数值状态不暴露到公开接口。
3. 单桥扫完全部目录才决定是否进入双桥；双桥按外层第一原型、内层第二原型，有界分块，保留两位置相同原型及同分首个。
4. 平滑度保持原表达式和双桥中间边重复计分；不改成预排序、Top-K、随机抽样或先找到就返回。只返回索引、分数和完成/回退状态。
5. 对原规则公开判定和原 Python 桥接做差分；验证真实编译签名、内核实际执行、测试未全部回退。工具里的原实现只做参照，不再复制一个生产算法。

交付 `stage_02_numeric_kernels/`：第 5 节对应差分矩阵、首个差异（无差异也记录）、编译与块成本；生产入口仍未接线。

### 4.4 阶段 3：接入唯一桥接入口

1. 保留现入口参数验证、直接连接及有效虚拟数量上限；在确实需要虚拟搜索时才导入/准备/编译。直接连接成功和有效上限为零不触发原型准备或 JIT。
2. 从原方法提取虚拟搜索部分作为 Python 回退，不另复制直接边逻辑。快路径不适用时回退；依赖/编译/程序错误沿用系统错误，不宽泛捕获成“没有桥”。
3. 数值准备和每块前后、阶段转换、物化及返回前检查原预算。首次编译仍计入原请求搜索时间，编译后立即查预算；绝不重置时钟/额度。
4. 只有完整选桥结束且仍可搜索，才调用原 `materialize()` 创建胜出的一至两个节点。停止、取消、异常或候选失败不推进正式编号、不留下半个候选。
5. 保留旧自定义规则精确测试的17次查询/49次轮询/4、13、13缓存；新增实际快路径的可控停止、全字段结果、编号/温区与后续候选一致性测试。
6. 验证整链、移单、两类拆单后唯一重放、宽差等所有 `_boundary_join` 使用者，无需逐调用者接线。完整评价/缓存、原采纳流程和最终审计保持。
7. 按设计第7.2节在 Python 外层接入每工厂至多三条执行证明日志：首次数值调用前一次 `start`，单桥/双桥各首次完整成功数值扫描后一次 `ready`。测试实际签名和模式、不支持/取消不伪报成功、无额外判边/预算查询、日志失败不改变结果；内核不打印。help/规则读写不触发数值调用或编译。

交付 `stage_03_bridge_integration/`：聚焦/累计、实际快路径命中、回退、生命周期和错误诊断记录。尚不能宣称 Windows 或完整性能通过。

### 4.5 阶段 4：完整等价、冷/热与质量

1. 同一主输入、观察工具、明确源码/依赖版本下，完整比较初始/首轮/最终有序方案、评价、轨迹、计数、资源、停止原因及双审计。缓存实际统计单列，不能整份删除运行清单。
2. 无分析器运行5对独立冷进程，交替旧→新、新→旧；记录进程启动到退出及原公开求解内部经过/CPU/阶段时间。Numba 首次编译真实包含在每个新进程样本内。
3. 同进程另记录第一次和第二次完整请求，核验第二次仅复用编译代码，不复用上次订单/规则数据；随后重启再次验证冷调用。冷热样本分表，不混合计算中位数。
4. 单独做首轮函数分析/调用计数，观察 Node 物化、语义身份编码、块数、实际快路径/回退、编译及剩余热点；Numba 内部不能仅凭 cProfile 推断细分耗时，可由外侧小探针测块成本。不得在生产逐候选刷日志。
5. 原正式180/10输入按原质量门跑完整求解；最新310/10输入独立运行并标注实际截断，不将其当同工作量一致性证明。固定工作量一侧若触时限，停止成对结论，不偷偷增加正式配置。
6. 测量时不并行跑累计测试，电脑保持唤醒；休眠或明显干扰时保留整组另行完整复测，不挑样/补齐，不重跑已完成样本冒充补充。
7. 全流程未稳定改善、冷调用明显变差或业务存在差异时，记录并暂停收口，不降低质量门、不把热内核倍数写成已达成收益。

交付 `stage_04_comparison/`：所有样本索引、逐项差分、冷/热成本、CPU、创建/编码次数和正式质量。5对专项不替代原20对性能门。
