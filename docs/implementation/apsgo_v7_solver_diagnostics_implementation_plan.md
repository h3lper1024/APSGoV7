## 3. 日志与文件口径

### 3.1 每行时间及耗时

- **每一行控制台与文件日志**均打印本机日期、时间、毫秒与时区偏移，包含 Uvicorn 启停、规则 GET/POST、求解、警告及异常堆栈的各物理行。换行消息也要补时间前缀。
- 日志时间用于定位发生时刻；耗时使用单调计时器计算，单位为秒，避免调整系统时间导致负耗时。
- 配置读取发生在 Uvicorn 启动之前；配置或启动失败使用独立的带时间控制台日志，避免受已有根日志格式影响。加载成功后由 Uvicorn 一次安装正式处理器。
- 求解请求从进入路由开始计时。请求相关日志携带 `elapsed_seconds`（从该请求开始的累计耗时）；阶段结束行另带 `stage_seconds`（本阶段耗时）。服务启停等无请求日志不伪造请求耗时。
- 最终总耗时统计到本次响应内容与诊断收尾完成，不声称包含网络发送或 C# 回写耗时。客户端断开时单独记录断开及后台工作线程实际结束。
- 同一格式用于控制台和文件；日志内容中的外部换行、控制字符应转义，防止伪装成其他记录。异常堆栈保留定位信息。

示例仅说明字段与格式，数值不是实测：

```text
2026-09-08 15:26:31.428+0800 INFO month_solve_started request_id=... order_count=531 elapsed_seconds=0.002
2026-09-08 15:26:33.561+0800 INFO solver_stage_finished request_id=... stage=initial_solution stage_name=初始方案构造 stage_seconds=0.321 elapsed_seconds=2.135
2026-09-08 15:26:34.007+0800 INFO solver_move_accepted request_id=... sequence=1 action_name=... quality_before=... quality_after=... elapsed_seconds=2.581
2026-09-08 15:30:11.608+0800 WARNING month_solve_finished request_id=... status=complete_not_publishable publishable=false stop_reason=... elapsed_seconds=220.182 diagnostic_directory=...
```

### 3.2 打印哪些内容

| 时点 | 日志内容 |
|---|---|
| 服务启动 | 监听地址、端口、诊断是否开启、成功启用的输出目录；可用的构建/版本身份 |
| 规则查询或保存 | 保留现有操作、活动版本、指纹和结果码；使用统一时间格式 |
| 求解开始 / 输入绑定完成 | 请求标识、订单/计划期数量、预期与实际规则版本、规则/字典/最终请求指纹、种子和本次预算、补齐统计 |
| 算法阶段开始 / 结束 | 英文阶段键及中文名称；阶段完成、截断或异常状态；已有链数、质量值、检查及采纳计数、阶段与累计耗时 |
| 结构调整被采纳 | 序号、动作名称、涉及链/来源订单、调整前后质量值、当前候选检查数、累计耗时；不能在候选提交前记录为已采纳 |
| 求解结束 | 求解状态、停止原因、可发布性、双审计结果/失败码、带目标名称的质量值、违规和问题计数、候选/完整评价/采纳/拆单计数、总耗时、诊断目录 |
| 不可发布或异常 | 逐条输出最终禁止违规的规则、原因码、对象和中文说明，以及其他失败问题；相同诊断避免重复打印；保留异常类型和堆栈 |

初始方案构造完成时，记录已有初始评价和链数。后续阶段跳过、提前退出或超时，不得打印成正常完成。阶段与采纳日志在运行中输出，不等求解结束后才批量打印。

日志只记录上述摘要和失败定位，不打印整份订单/规则 JSON，也不逐条打印最多 200000 次候选检查。阶段内部受控拆单后的原搜索重放，标明所属阶段及重放事实，不能重复累计外层耗时。

`core_solve` 总耗时已包含核心细阶段，阶段字典不能简单求和作为请求总耗时；累计时间始终从请求入口独立测量。`complete_not_publishable` 也可能源于收尾超时或其他审计失败，不能统一记录为“违反规则”。

### 3.3 每次求解的文件

启用落盘后，目录结构为 `diagnostics/runs/<request_id>/<运行时间_唯一后缀>/`。同一请求标识再次提交时建立新目录，不覆盖或混入上一轮。目录名只使用服务端规范化标识和生成的后缀，不使用订单号或外部任意路径。

| 文件 | 内容与写入时点 |
|---|---|
| `request.json` | 请求解析通过且获得求解执行权后，保存实际收到的 JSON 正文，保留原订单相对顺序 |
| `prepared_request.json` | 一次绑定完成后立即保存：补齐后的订单、权威期序、规则和评分声明、虚拟原型、策略、准备报告、活动版本与各项指纹；这是实际交给算法的输入 |
| `solve.log` | 本次请求的阶段与采纳日志，使用同一时间格式实时追加；包含初始构造与后续调整的摘要，便于单独发回排查 |
| `response.json` | 实际生成的 HTTP 响应正文；不可发布时仍保持公开响应的空 `rows` 语义。没有生成响应时不伪造该文件 |
| `diagnostic_summary.json` | 状态、停止原因、版本/指纹、策略身份、问题、双审计、运行计数与耗时；存在候选时还保存候选完整计划、质量、各链评价和全部违规，明确其是否获准发布 |
| `candidate_rows.csv` | 存在完整候选时生成，按原方案链序及链内顺序展开，供人工查看；标明“诊断候选”及实际发布状态 |

“中间数据”首版固定为绑定后的输入、初始评价摘要、各阶段摘要和采纳记录；不保存每个拒绝候选或每次调整后的全量方案副本。初始评价、阶段摘要复用当时已算出的值，不为落盘增加完整评价。

数据细节：

- 优先从 `diagnostic_candidate.plan/search_evaluation` 取候选，正式发布评价单独标注。候选搜索评价不能冒充最终无缓存审计结果；没有候选时写明 `candidate=null`，不生成虚假的 CSV 行。
- 非发布 `SchedulingResult` 没有完整的独立审计评价；此时保存搜索评价、审计报告和审计产生的 `issues`，不能承诺从结果对象还原独立审计的全量质量与违规列表。
- CSV 至少包含计划期、小辊期标识及序号、节点序号、订单/节点标识、重量、宽厚、温区、牌号、材料角色与拆单来源；使用既有行转换和谱系字段。完整违规以 JSON 为准，不依赖面向正式发布的告警投影才能生成诊断行。
- JSON 保留数值精度，复用 `dumps_exact_json`；不先转为浮点数。代码、文档、日志与 JSON 使用 UTF-8 无 BOM。CSV 供 Excel 通过“数据导入”按 UTF-8 打开，订单号指定文本；文本字段防止被解释为公式，原值仍在 JSON 保留。
- `prepared_request.json` 保存本次用到的规则、原型及补齐结果，字典保留指纹和准备报告即可；不为本专项再导出整个 SQLite 库或第二份字典。
- 原始请求、准备输入和阶段日志逐步写入；最终文件逐个用同目录临时文件写完再替换。整个运行目录不声称具备跨文件事务，最后的摘要应记录已写文件及写入失败；进程被强杀时允许保留不完整记录。
- 单文件写入、序列化或 CSV 投影失败只影响诊断，明确记录 `diagnostic_write_failed` 和文件名，其余能写的文件继续保存；不改变求解状态、候选采纳、HTTP 错误语义或发布判定。日志处理器异常也不能传播回搜索。
- 客户端断开后，后台工作线程仍按原取消机制结束；本次诊断记录保持到实际退出，再关闭文件。解析前错误和拒绝执行的 429 请求至少有带时间的错误日志，不为任意非法请求保存全量正文。
- 当前成功响应在求解工作线程返回后序列化；实施时将响应构造和本次诊断收尾纳入该工作线程的生命周期，完成后再向 HTTP 层交付响应内容。响应序列化失败继续使用原 HTTP 错误映射，不能作为“诊断写盘失败”被吞掉；仅诊断文件的序列化和写入错误允许隔离。

## 4. 配置、发布及最小改动范围

计划在现有 YAML 新增一个可选块：

```yaml
diagnostics:
  enabled: true
  output_directory: ../diagnostics
```

新模板显式启用。旧 YAML 没有该块时，继续输出带时间的控制台日志，文件落盘关闭；`enabled: false` 同样关闭文件落盘，不取消控制台诊断摘要。块存在时严格校验布尔值、非空目录和未知键。

目录相对 **YAML 所在目录** 解析，Windows 发布包中对应 `<发布根目录>\diagnostics`；不依赖启动盘符、当前工作目录或 PyInstaller 内部目录。已有现场 YAML 不被升级脚本覆盖，升级时由部署人员补入配置块。

共享文件 `diagnostics/service.log` 采用标准库 `RotatingFileHandler`（按文件大小轮换日志），固定 10 MiB、保留 3 个历史文件。逐请求目录先人工归档清理，不增加定时清理或保留策略配置。显式启用但启动时无法创建目录，应先用带时间的控制台错误清楚报告并停止启动；运行途中写盘失败按第 3.3 节隔离。

| 改动位置 | 计划修改 |
|---|---|
| `src/apsgo_v7_service/configuration.py`、`config/apsgo_v7_service.yaml` | 可选诊断配置及配置文件相对目录 |
| 新增 `src/apsgo_v7_service/diagnostics.py` | 集中实现标准日志配置、单次运行文件与已有值对象的输出；普通函数和必要标准处理器即可 |
| `src/apsgo_v7_service/app.py`、`scheduling.py` | 请求计时、绑定输入、结果及失败分支接线；后台线程退出前完成其诊断收尾 |
| `src/apsgo_v7_service/month_scheduling.py` | 复用既有只读行转换即可支持诊断候选，不必修改该文件；公开响应原样保持 |
| `src/apsgo_scheduler/core/solver.py`、`neighborhoods.py` 及实际拆单/审计捕获点、应用入口 | 阶段、异常与正式采纳日志；共用一个标准库安全日志小函数，不在核心直接写文件 |
| `.gitignore`、`release/README.md`、必要的 `README.md` 使用说明 | 添加根 `/diagnostics/` 忽略、现场启用方法和人工定位步骤；保留用户已有修改 |
| `tests/service`、相关 `tests/core` 和 `tests/release` | 复用现有夹具，覆盖不可发布、时间、文件、并发取消与打包路径 |

Uvicorn 和算法日志应共用同一组处理器配置，明确路由算法包日志，避免只配置 `uvicorn` 而丢失核心日志。通过 `uvicorn.run(log_config=...)` 接入；不在启动前临时添加随后会被覆盖的文件处理器。单次请求信息使用标准库上下文机制关联到实际工作线程，完成后释放，不以全局“当前请求”变量串接。

构建脚本已复制整个 YAML，无需新增依赖或专门的数据收集步骤。日志和运行目录不进入干净发布包；在发布临时副本启动后才生成，包级校验仍区分原始发布文件与现场运行产物。

## 8. 追加实施：进程 CPU 时间统计

### 8.1 目标、依据与边界

用户要求借鉴 V3 探针，补充“进程实际消耗的 CPU 时间”，辅助判断 Windows 求解慢在计算消耗，还是存在等待或运行环境限制。**本轮只补文档，阶段 5、6 均未实施；不预先认定根因为 CPU 核数或虚拟机。**

本次核对 V3 提交 `e5bdcdfd3dd1ed880037d28159bfe8b6bef5d15f`：`/Users/miles/dev/dev-py/apsgo-v3/profiling.py` 的 `CpuTimer` 已用两个标准库时钟计时，`stages/stage3_resource.py` 在写阶段产物前取指标，`workflow.py` 的外层耗时则覆盖整个阶段调用。这说明计时思路可借鉴，但统计范围不能不加区分地照搬。

- 复用 V7 现有请求上下文、阶段开始/结束日志和 `diagnostic_summary.json`；不引入 V3 运行时依赖，不另建 `ProfileCollector`、`profile.jsonl`、采样线程或监控框架。
- 不使用函数级剖析工具 `cProfile` 作为本次常驻探针；它用于进一步定位具体函数，不与正常运行耗时混为一谈。
- 不增加逐候选日志、规则评价、候选检查或新的计数器；不改算法、预算、取消检查次数、规则、评分、HTTP 响应、运行身份或指纹。
- 不改变 YAML、数据库、C# 或发布脚本；CPU 信息是服务层观测数据，不进入核心结果契约。关闭文件落盘仍保留控制台 CPU 信息，不增加单独的 CPU 开关。

计时语义依据：[Python 3.10 `time` 文档](https://docs.python.org/3.10/library/time.html#time.process_time)与 [PEP 418](https://peps.python.org/pep-0418/)。`process_time()` 返回当前进程的用户态与内核态 CPU 时间之和，不包含休眠；与包含等待的 `perf_counter()` 分别计算起止差值，不能交叉相减。

### 8.2 字段与计算口径

设 `E` 为本次请求开始以来的经过时间，`C` 为同一区间的进程 CPU 时间。以下都是累计指标，不是瞬时采样百分比。

| 字段 | 含义与公式 | 输出位置 |
|---|---|---|
| `elapsed_seconds` | 既有累计经过时间 `E`，保留原含义 | 原有日志与摘要 |
| `process_cpu_seconds` | 新增累计进程 CPU 时间 `C` | 求解相关日志与摘要 |
| `cpu_core_equivalent` | 平均使用核数 `C / E`；`E <= 0` 时为 `null` | 请求结束日志与摘要 |
| `cpu_count` | 当前系统报告的逻辑处理器数量；读取失败或未知为 `null`，不猜成 1 | 请求开始/结束日志与摘要 |
| `machine_cpu_percent_estimate` | `C / E / cpu_count * 100`；缺少有效分母时为 `null` | 请求结束日志与摘要 |

CPU 数量每次请求读取一次并复用，不逐候选或逐日志读取。逻辑处理器数量来自 [`os.cpu_count()`](https://docs.python.org/3.10/library/os.html#os.cpu_count)，不代表进程实际获准使用的配额；虚拟机内的数量也不能当作宿主机物理核数。整机百分比只是按该数量换算的估计，不保证与任务管理器某个瞬间显示一致。

比值使用未舍入的差值计算；新增 CPU 时间和比值输出保留六位小数，既有经过时间与业务数值精度不变。摘要沿用已有精确 JSON 输出；未知值写 JSON `null`、日志 `-`，不输出 NaN/Infinity 或以 0 冒充采样成功。摘要保留原有字段与 `schema_version=1`，只追加上表诊断字段；历史摘要缺少新字段表示“未采集”，不等于消耗为零。

进程 CPU 时间包含同一进程的其他线程，例如同时发生的规则查询；不能称为求解线程独占耗时，也不包含子进程。多线程累计 CPU 时间可以超过经过时间，平均使用核数不得强行限制为 1。本次不新增 V3 的 `non_cpu_wait_seconds`：“经过时间减 CPU 时间”不能准确表示 I/O 等待，更不能直接证明虚拟机限额。

### 8.3 计时与日志接线

1. **请求起点**：在 `app.py::solve_month_schedule()` 现有 `started = perf_counter()` 旁记录 CPU 起点，读正文、解析与后续处理均在同一请求区间内。不能等到创建 `RunDiagnostics` 或进入核心搜索时才启动 CPU 时钟；原搜索预算计时器完全不动。
2. **共用计算**：在现有诊断模块内用一个普通小函数计算成对时钟差值，显式请求日志、格式化器和摘要复用；同次采样的 CPU 与经过时间来自同一区间。不增加计时器继承体系，不接受来自另一阶段的耗时作为比值分母。
3. **运行中日志**：`TimestampFormatter` 给已有请求上下文的阶段、采纳、警告和结束日志补累计 `process_cpu_seconds`，不新增日志事件；显式日志已提供成对数值时不重复覆盖。控制台与文件可因格式化时点不同产生微小差值，不要求不同处理器的样本逐字相同。
4. **阶段分析**：用同次运行、同一日志来源中某阶段开始/结束行的累计 CPU 差值观察该区间消耗。阶段平均使用核数采用这同一对日志的 `Δprocess_cpu_seconds / Δelapsed_seconds`；原 `stage_seconds` 的采样边界可能不同，只作对照，不能自动替代分母。重复的搜索重放按本次开始/结束区间配对，不把同名阶段合并；缺少配对时标记缺失，不猜测。既有 `stage_seconds` 仍为阶段经过时间，不把累计 CPU 误写为阶段 CPU；首版不增加阶段 CPU 汇总表。外层核心求解与其内部阶段重叠，不能简单相加。
5. **摘要与最终日志**：沿用 `finish()` 保存响应/候选、`close()` 关闭单次日志后再生成摘要的顺序。摘要里的两个时钟在生成摘要时一起采样，包含此前的响应构造、文件写入和日志关闭，但不包含摘要自身完整序列化/写盘；之后的全局 `month_solve_worker_finished` 再采样，反映截至该结束记录的收尾消耗。这条日志不重新写回已关闭的 `solve.log`，也不为让数值相等而改写摘要。两者都不声称包含 HTTP 网络传输、C# 回写或整个操作系统线程的退出时间。
6. **失败与取消**：正常、不可发布、绑定/输入失败、版本冲突、响应构造失败均沿用原处理路径。解析前错误、413/415/503/429 等尚未创建运行目录的请求，通过 `_log_month_solve()` 的显式入口补 CPU 数值，不能只依赖上下文格式化器；仍不落全量请求正文。工作线程已启动后客户端取消，计时继续到该工作线程实际收尾，不在断开时提前冻结。工作线程未启动则不伪造工作线程结束、候选或摘要。
7. **隔离**：无请求上下文的服务启动、规则读写日志只保留原时间信息，不借用其他求解的起点。重复请求使用各自起点，不引入全局“当前请求”。CPU 采样或诊断输出失败只影响观测，保留原日志和业务结果，未知 CPU 标记为缺失；错误报告不能递归触发同一失败采样。

示例仅用于说明两个计时指标，数值不是实测：

```text
2026-09-08 18:00:00.000+0800 INFO solver_stage_started stage=local_search elapsed_seconds=20.000000 process_cpu_seconds=18.000000
2026-09-08 18:08:20.000+0800 INFO solver_stage_finished stage=local_search stage_seconds=500.000000 elapsed_seconds=520.000000 process_cpu_seconds=508.000000
```

该区间 CPU 消耗约为 `508 - 18 = 490` 秒，经过时间约 500 秒，平均相当于使用 0.98 个核；这是定位线索，不是“已找到慢因”或“已优化性能”的结论。
