## 6. 各阶段实施要点

### 阶段 0：冻结原始输入与接入基线

1. 重新核验两个 Git 工作区、V3 源库、实际 YAML 目标库和 C# 用户修改，记录摘要。
2. 只读核验 GQGA4 全部 230 条及来源字段，保存行数、分类、源库摘要和规范化摘要；不在仓库复制整份字典。原表 GQGA5 不进入本期迁移范围。
3. 用 V3 原生产加载/拼接代码与冻结 `optimization_problem.json` 作逐单对照，只验证输入，不开始搜索。期望 531/531 一致、529 命中/2 缺失、软钢 525/硬钢 4/空 2。
4. 确认 GQGA4 命令接收的是哪一步的记录；记录原始真实材、过去生成虚拟材、同合同多行和已有拆片处理方式。若实际输入超出核心“原始真实订单一来源一行”契约，停止该依赖步骤并提出具体映射决策，不默认删除。
5. 保存 HTTP JSON 金样和前端来源映射方案；现有完整解只用于回归对照，不能当在线输入来源。
6. 只读核验 C# 实际业务库 `Warnings` 列容量，确认可容纳设计第 9 节元数据和告警；无法核验则单独保留该门禁，字段不足需明确扩容决策，不截断。

### 阶段 1：建立字典快照与纯拼接

- 用标准库 dataclass、不可变映射和现有 `fingerprint()`；输入映射不变异原订单。
- 校验规范化重复、非法分类、空键、启停、来源字段；两个大小写牌号正常命中。
- 纯函数测试使用最小内联样本；生产代码不读取 tests、V3 路径或仓内字典副本。230 行一致性留给显式迁移及阶段 8 验证。
- 拼接覆盖普通材/实际过渡材、缺失、已有值冲突、非文本；准备报告统计按原始订单。
- 缺失统一为 `None`，与旧冻结空值一致。不得为了使问题指纹“看起来相同”删除必要属性；逐项对照并解释差异。

### 阶段 2：实现数据库升级与快照生命周期

- 在临时副本实现 v1→v2 原子升级；包含 schema 签名、版本记录读取和不可变触发器，不关闭原历史保护后任意回填。
- 迁移命令专用打开并完整校验 v1，不经过普通 v2 `open/initialize`；同一个 `BEGIN IMMEDIATE` 覆盖 schema、快照、新版本、激活与回读，`user_version=2` 最后写。新建/迁入 v2 均通过统一严格签名校验。
- 新库初始化必须由显式命令传入只读 V3 SQLite 源库，并同事务创建规则、原型、字典；已有库普通初始化只验证，不替用户覆盖活动规则。
- 迁移复制目标库当前活动规则、虚拟原型、备注和页面快照，创建新业务版本并重编译；验证非默认规则及原型逐字段保留。字典指纹相同不代表规则版本指纹相同。
- 页面保存在并发检查之后继承活动字典；不能在事务外预读再复制到另一版本。
- 规则保存 `request_hash` 仍表示用户规则请求，不把当前可变字典塞入旧哈希公式；幂等先判断旧操作，不因当前字典改变而误判相同请求内容不同。
- 迁移重试以操作 UUID、预期活动版本和冻结字典指纹共同核对。普通规则保存不能复用迁移操作身份伪装成同一操作。
- 迁移先把 V3 源通过 SQLite Backup API 固化成临时一致性快照，再从该快照读取和计算
  `source_database_sha256`；主文件裸哈希仅作外部文件证据，不能代替包含 WAL 已提交内容的导入身份。
- 迁移固定审计主体由普通规则保存入口保留并拒绝。事务失败后重试只允许复用严格 schema v1
  且三张规则表全量内容与当前目标一致的既有备份；不匹配备份拒绝且不覆盖，复制后验证失败清理不完整文件。
- v2 重入先查原迁移操作；一致返回原版本及当前活动状态，不重新激活；不匹配冲突，无同操作则拒绝重复迁移。覆盖“迁移成功→规则再保存→原 UUID 重试”。
- 恢复历史规则采用历史规则/原型 + 当前有效字典的新版本；旧历史版本缺字典可以读取，但不能直接启动新的字典准备求解。
- 当前 schema/HTTP 测试写死“版本 1、三表、版本 2 不支持、仅两条路由”；随实际实施更新为真实 v1 历史夹具、当前 v2 合法夹具、未来版本拒绝和三条实际路由。缺字典的旧测试助手不能冒充合法新版本，不通过删除一致性断言消除失败。

### 阶段 3：绑定求解输入与数据准备报告

- 增加内部完整活动快照读取，复用已有规则验证；同一数据库事务读取活动指针、字典和原型，公开规则 GET 不新增整份字典字段。
- 在 `bind_gqga4_scheduling_task()` 中统一补齐，不仅 HTTP 路径补齐。
- 绑定对象和返回对象保留字典身份、准备报告及关联指纹；核心请求含补齐属性，核心运行清单不接数据库主键。
- 使用两版本快照隔离测试：任务 A 绑定后保存版本 B，A 全过程仍使用 A；后续任务读取 B。
- 绑定完成后禁止数据库访问，再执行小型真实求解；覆盖规范化、缓存和最终无缓存审计。

### 阶段 4：实现月计划请求与结果转换

- 只实现设计的 GQGA4 请求契约，JSON 小数使用现有精确编码；外部语义请求、字典补齐前服务输入和绑定后核心请求三层身份分别记录，缺字段定位清楚。
- 原始 `weight` 来自连镀欠交；权威期序由前端预设大辊号传入；默认 4 期不能写入核心。
- 服务端按已有三条件判定材料角色；表面等级空值通过，空值打断连续段语义不变。
- 结果只从 release 读取，复制发布链序、节点序、来源期/分配期、类别和谱系。非发布结果返回空 rows，保留诊断。
- 权威 `violations` 与流程 `issues` 分开输出，保留原 scope 和主体；覆盖允许欠重的链级违规、节点/边/方案级序列化，逐行投影不能增加权威计数。
- 行级宽/厚/温告警及链首欠重提示由权威违规映射，C# 不重算；完整违规仍在顶层保留，不以行投影替代。
- 核心禁止空链和空计划；覆盖无产出计划期不生成占位行、非发布结果空 rows、跨期借入、同期间拆片、未来借入拆分归还、虚拟材和欠重可发布的序列化测试；不能将诊断候选签发为结果。
- 完整结果行使用冻结字段集合，拆单与虚拟谱系展开全部现有字段。正式 release 仅允许无违规或欠重允许偏差；宽、厚、温告警仅通过纯投影测试验证定位，禁止违规不能伪装为可发布结果。

### 阶段 5：接入 HTTP 与 YAML 求解策略

- 新增求解路由并复用当前 FastAPI 宿主；现有规则路径、方法、数据格式保持。
- 6 项求解策略在 YAML `monthly_solve` 中配置，使用核心 `SolverPolicy` 二次校验；新增映射与严格加载器、初始化器、服务测试同时落地。
- 通过同一只读事务核对 `expected_active_version_id`；409 不运行搜索。
- 单进程单求解，异步 HTTP 等待线程结果；用户断开设置取消标志，不把线程取消误称为已终止求解；占用仅在求解退出后释放。
- 测试 429 忙、取消、输入超限、无字典、损坏、已有规则保存并发和完整 rows 返回。真实接口验证不复用用户已启动的服务进程。
- 按路由区分求解 8 MiB/413/415 与旧规则 256 KiB/既有错误响应，测试 Content-Length 和流式超限；不得修改共享常量连带放宽规则接口。
- 公共入口 `failed/input_invalid` 统一映射 422，保留原输入诊断；其他正常返回状态仍为 200。新增测试证明没有再实现一套启用规则必填检查。

### 阶段 6：建立 C# V7 专属配置和客户端

- 先保存用户改动摘要，精确抽取现有 `PipelineV7ApiBaseUrl` 读取到新 V7 配置类。
- 新增路由/超时键，保留用户实际地址；不给 V3 类改基地址，不统一两个后端。
- 请求/响应 DTO 使用与 Python 相同的字段和小数口径；请求 ID 必须核对，所有 rows 完整接收。
- 用 Python 产生的固定 JSON 在 C# 解析，C# 请求 JSON 回送 Python 解析；包括 null 分类、小数、中文及所有求解状态。
- API 请求异步，方法保留取消令牌和超时，网络不自动重试；当前页面不新增用户取消按钮，失败提示带任务身份和字段定位。
- 每次 POST 前调用既有规则 GET 取得活动版本，不能从配置规则步骤记录猜版本；GET/POST 间变化返回 409，由用户重新发起，不自动重跑。

### 阶段 7：接入 C# 求解服务和原子回写

- 参考原 GQGA4 的版本定位、整批取数、连镀重量、预设大辊号解析与原始属性取值；业务流程不依赖 V3 服务类。
- 先创建全部内存结果记录并核验来源覆盖、重量守恒、输出期序、拆片/虚拟属性，之后才打开短写事务。
- 原命令按选择确定版本后读取该版本/产线的全部“配置规则”步骤记录；不得缩成只排选中行。正重量输入虚拟材或重复来源明确提示，不静默过滤。
- 使用现有 SqlSugar 的 `BeginTran/CommitTran/RollbackTran`，原步骤结果删除和新结果插入在同一事务；核对插入数等于全部记录数，错误必须回滚，事务内不联网。
- 真实单克隆来源属性，`SoftOrHard` 不在请求发送，只校验响应的软钢/硬钢/null 值域及拆片一致性后写入；虚拟单使用原型结果和现有 GQGA4 需求写入方法。
- `RollingStrictAnalysisRuleChecker` 当前不处理 GQGA4，保持不变；现有图表读取 V7 诊断映射的 `Warnings`，不新增本地规则复算。
- 以 `Warnings` 同级 `V7Metadata` 保存精简身份，核验各行和响应一致及数据库无截断；仅 GQGA4 汇总复用 `HasWarningMessages()`，测试纯元数据为零报警、有告警才计数、四类提示正确映射，其他产线行为不变。
- `CalcRollPosCommandGQGA4DeliveryTime` 继续作为独立下一步，使用 `CalcDay.Date` 和原连镀小时公式；本期不把它移入求解器。
- 验证用户仍手动查询排程结果；取消/失败不前进、不删除旧结果。
- GQGA4 命令显式设置 `RunInBackground => true`，以 `ChangesSchedRecords` 仅在事务提交成功后置 true；参考已有配置规则命令，避免提示后正常 return 被框架当成求解成功。页面不增加主动取消入口，不把内部取消令牌误报为已有按钮功能。

## 9. 数据库恢复与失败处理

1. 迁移前记录目标绝对路径、schema、活动版本、规则和字典摘要及备份文件；用 SQLite backup API 或 `.backup` 取得完整一致性快照，验证 `integrity_check` 和活动规则可读。
2. 源库只读，行数、规范化内容哈希和来源摘要可重复验证，不在仓库落字典副本。服务启动/请求不执行迁移写入；迁移用明确命令、操作 UUID 和预期版本。
3. 事务中失败回滚 schema 和新版本，旧活动版本不变。迁移成功但部署失败时先停目标服务，再从备份恢复目标库及匹配的旧包，正确处理 WAL/SHM；禁止服务运行中覆盖数据库文件。
4. 恢复先在临时库演练，记录准确命令和验证结果；实施记录未填写恢复命令前，不标记真实迁移具备回退能力。
5. 前端写回失败在本地事务内回滚；Python 求解接口本身不写 C# 业务数据库，不需要用后端规则库备份恢复排程结果。
