## 2. 已定口径与实施前置条件

### 2.1 按本轮沟通实施的业务口径

- 显式传入生产开始时间，交期截止按当地当天 24 点，不能用订单最早交期或程序执行时间替代。
- 起排时已到期为旧欠单，未到期为可争取准交订单；同一次任务中分类不变。
- 在原前四项目标之后增加“新增晚交订单重量”和“累计等待与延期负担”，原宽差、虚拟重量、链数顺延为第 7～9 项。
- 以原订单本次待排吨位为权重，拆片最后完成才算原订单完成，虚拟材只占用时间。
- 交期只贡献目标和诊断，不成为禁止发布违规；工艺、来源、拆单、期序和预算边界保留。
- 复用既有构造/动作/评价/审计，允许交期改善而宽差变大的合法候选，不新建求解框架。
- 测试集中在关键逻辑块和收口，不在每个小步骤后重复跑测试。

精确公式、等号、缺失值和特殊订单处理统一引用设计第 4～6 节，实施时不能再口头换成“按月份优先”或“只要在本大辊期就算准交”。

### 2.2 阶段 0 必须明确的输入

1. 真实 GQGA4 原始请求与速度、交期来源；原始 Excel 只作源数据，不覆写。现有诊断输入缺字段时做明确关联，不能顺手重排或修正订单。
2. 所有可生成虚拟原型的有效速度与来源；没有工艺值时暂停真实时间基线，不猜值。可以独立开展公式/合成验证，不能用合成工时关闭现场门禁。
3. 首个需要适配的月计划客户端：Web 或 C#。当前可读两者以核对契约，但后续外部仓库写入须获得明确范围，不能默认同时改两套。
4. 同一冻结开始时间、实际种子、候选上限、时限和规则副本。六月样本采用 `2026-06-01T00:00:00+08:00`，其他输入必须重新明确。

技术提案为 v2 求解 / 日期契约与版本化原型速度，详情见设计第 6、13 节。正式规则激活和客户端切换另外确认，不由持续开发授权自动涵盖。阶段 0 当前已核验的来源、哈希和未决项见[前置核对记录](evidence/apsgo_v7_delivery_objective_optimization/stage_00_precheck/README.md)。

### 4.2 阶段 0：冻结计时输入、对照口径和接口选择

1. 重查分支/提交/工作树，记录输入、规则、原型、计时数据、策略和工具身份。用户数据库改动仅记录现状，不提交。
2. 冻结旧七级参考版本及其实际完整输出；已有明确版本的有效输出可复用，不为阶段编号重复跑一份相同基线。
3. 核对原订单速度来源；登记虚拟速度。补齐字段需能通过来源身份关联，不能仅按表格行号拼接。
4. 固定 v1/v2 兼容矩阵、时间单位和秒边界、首个客户端、计划使用的规则副本。真实库切换不在此阶段执行。
5. 冻结真实对照的质量/预算口径和输出目录；交期数值统一采用严格新口径，不引用旧零虚拟用时结果作门槛。

交付：输入索引、文件身份、未决项和可复现命令。此阶段做资料 / 契约检查，不要求跑业务测试集；输入缺失时如实记录，不能填假值关闭。

### 4.3 阶段 1：建立计时输入、归一化与工时共用逻辑

1. 加入可选原始计时块，建立原订单/原型映射；不用 `Node.rule_attributes` 承载每单不同的预计日期。
2. 共用严格工时纯函数，按设计第 4 节处理速度优先级、时区、截止 24 点及未舍入工时。服务层原始速度在进入核心前转为精确工时。
3. 构造只读相对截止小时、原订单重量与单位工时，校验全部映射和字段；拆片和虚拟节点时间从权威原始身份派生。
4. 统一版本化指纹投影，检查 `normalize_input()`、请求绑定、`contract_audit.py` 中直接枚举 dataclass 的路径，不能只在单个入口去掉 None 字段。
5. 一起编写必要用例，集中在阶段 2 执行；此阶段提交可以标“实现已提交，验证待阶段 2”，不伪造通过数量。

完成标准：旧请求不需要计时块，新计时输入可严格归一化；调用和身份闭合。未到测试检查点不部署、不对外宣称可用。

### 4.4 阶段 2：两个交期指标与九级评价

1. 新增一个方案级 `DeliveryDuePerformanceRule`，一次扫描计算两个目标，只输出贡献，不创建禁止违规。
2. 扫描使用生产链序和全部节点时长，按原订单最后拆片聚合；原始来源重量与节点重量分工明确。
3. 复用质量声明加载和汇总；新两项必须按名称定位，不把下标 4/5 写死在多个消费者。
4. 核对新规则不会导致未变链评价整体回退；方案级交期每候选重算，最终无缓存入口保持。
5. 集中执行第 5 节“计时与评分”验证，涵盖阶段 1～2；失败先修复，再进入搜索。

交付：可独立评价的九级目标、必要单测、实际命令和结果。无需在此运行完整 GQGA4 搜索或 Windows 构建。

### 4.5 阶段 3：结构搜索和交期候选接受

1. 初始完整方案接入九级评价，但不将规格拓扑改成纯交期排序。
2. 在既有动作生成中优先枚举临期/新增晚交节点和旧欠单；记录确定性同分顺序，不增加新的权重学习系统。
3. 整链、节点、连续段及切链候选沿用原连接与资源检查。交期启用时不以宽差下降作必要预筛；完整候选严格比较九级。
4. 对整链/精修放宽“前置目标必须全部相同”的旧宽差限定：前四项仍与当前方案一致，但不要求两个交期目标也相同；同时保留原动作工艺/资源条件，完整九级必须严格改善。交期未启用保持原行为。
5. 保留原阶段顺序、同一预算、受控拆单至多一次回放；交期单独启用也能进入顺序精修。
6. 用例与代码一起准备，集中在阶段 4 验证；不得因时间不足提前宣称搜索效果提升。

完成标准：所有涉及顺序的候选和拆后回放进入统一目标评价，没有仅改总评分却被前置宽差判断挡住的路径。

### 4.6 阶段 4：独立审计与交期明细

1. 从原始问题重建计时，独立核验源身份、每个节点时长、原订单最后完成以及两项目标；不依赖搜索累计值。
2. 核心/应用结果绑定计时身份，生成逐节点相对时间、逐原订单贡献与交期汇总，未发布结果仍不能回写生产行。
3. 为后续服务输出提供一份统一明细，不在接口层写第二套评分函数。
4. 集中执行第 5 节“搜索与审计”验证，覆盖阶段 3～4，故意篡改起点/拆片/排序的反例必须失败。

交付：正确候选可采纳、错误候选被拒绝、无缓存审计能识别污染；不要求此阶段跑 HTTP 或每个动作单独跑真实全量数据。
