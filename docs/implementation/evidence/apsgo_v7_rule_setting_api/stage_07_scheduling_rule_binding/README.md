## 2. 实现结果

1. `SchedulingTaskInput` 只包含请求身份、订单、计划期和求解策略，不包含规则集或虚拟材料原型。
2. `bind_gqga4_scheduling_task()` 在一次一致性读取中取得并完整校验活动版本，然后首次构造不可变 `SchedulingRequest`。
3. `BoundSchedulingTask` 分别保存数据库活动版本主键、规则指纹、请求指纹和绑定指纹；数据库主键不冒充 `RuleSetSpec.version` 业务版本号。
4. `solve_gqga4_scheduling_task()` 绑定后只调用一次既有 `solve_request()`；搜索、最终审计和结果签发只使用请求内存快照。
5. `BoundSchedulingResult` 保留同一绑定身份并校验结果运行清单中的请求和规则指纹，不给核心请求或结果契约增加数据库字段。

当前仓库没有生产排程 HTTP 请求组装器，因此本阶段完成的是服务层正式绑定入口，不声称现有月计划排程流量已经接入。

## 3. 自动化覆盖

- 任务运行中启用新版本：在途任务保留旧快照，后来启动的任务取得新快照。
- 活动快照读取或完整校验失败：不启动求解，也不回退到测试文件、V3 配置或历史版本。
- 任务身份错误：在访问规则数据库前拒绝。
- 数据库活动版本主键与规则业务版本号不同：两者仍分别记录并正确校验。
- 绑定完成后禁用 `RuleStore.open()`：小样本仍成功求解，证明搜索链不访问规则仓储。
