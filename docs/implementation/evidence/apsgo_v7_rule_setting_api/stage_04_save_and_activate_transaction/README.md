# V7 规则设置接口：阶段 4 保存并启用事务验证

## 1. 结论

阶段 4 已建立 GQGA4 月计划规则的框架无关应用服务：

- 一次保存在一个 SQLite `BEGIN IMMEDIATE` 事务内完成新版本、17 条规则、虚拟材料原型和页面快照写入，然后条件切换活动版本。
- 幂等查找早于基础活动版本检查；丢失响应后用同一操作标识和同一内容重试不会增加版本。
- 历史保存记录被后续版本替代后，幂等重放只返回原保存版本标识和当前活动视图，不重新启用旧版本。
- 查询与保存都在返回前完整回读并校验编译快照、逐条规则、原型、页面快照、摘要及审计字段；损坏数据不会部分返回。
- 编译、任一数据库写入、活动版本条件更新、回读或响应序列化失败均整体回滚。

本阶段不包含 HTTP 路由、正式数据库初始化、求解请求绑定或 C# 页面改造。

## 3. 事务顺序

1. 在事务外使用 GQGA4 固定模板规范化规则、原型和备注，计算不含保存操作标识的请求摘要。
2. 开启写事务，读取 `GQGA4/default/month` 当前活动版本。
3. 先查找同一 `save_operation_id`：同摘要返回幂等结果，不同摘要拒绝。
4. 新操作再比较 `expected_active_version_id`，过期编辑不写库。
5. 使用下一个规则集版本号调用既有 GQGA4 编译入口，再写入版本、17 条规则与两份快照。
6. 以原活动版本为条件切换指针；未更新一行时抛出存储冲突并回滚。
7. 在事务内重新读取并校验完整活动视图，同时验证响应可序列化；成功后提交。

`editor_snapshot_json` 只保存规范化后的 `rules`、`virtual_prototypes` 和 `remark`。基础版本另由 `based_on_version_id` 保存，保存操作标识另由 `save_operation_id` 保存；不把二者复制到页面快照，也不为非 HTTP 的初始版本伪造公开 POST 请求。

## 4. 并发、幂等与回滚证据

| 场景 | 验证结果 |
|---|---|
| 两个不同保存操作真实重叠 | 第一个连接持有写锁时第二个请求不完成；锁释放后第一个创建版本 2，第二个收到活动版本冲突，库中仅有版本 1、2 和 34 条规则。 |
| 同一保存操作真实重叠 | 第一个连接提交后，第二个按幂等记录返回同一保存版本，仍只有一个新版本。 |
| 操作标识相同但规则、原型顺序、备注或基础版本不同 | 稳定返回操作内容冲突，不增加版本或规则行。 |
| 第 8 条规则写入失败 | 前 7 条与新版本一起回滚，原活动版本不变。 |
| 真实条件更新未命中 | 存储层抛出冲突，服务在完整回滚后转换为活动版本冲突。 |
| 响应序列化失败 | 错误在提交前触发，所有新记录和活动指针回滚，同一请求可安全重试。 |

## 5. 回读一致性证据

参数化反例分别损坏以下内容，公开查询均统一拒绝为 `stored_snapshot_inconsistent`：

- 编译 JSON 结构、经合法签名的业务身份或版本号、数据库指纹。
- 规则数量、连续顺序或逐条内容。
- 原型数量、规范序列化、合法 JSON 中的极端指数数值。
- 页面快照、请求摘要或未规范化备注。

另有正向用例验证 `Decimal("1e10000")` 这类超大但有限的十进制值可从保存响应与后续 GET 精确回读；不会为了拦截损坏快照而损失合法数值精度。摘要用例同时证明规则启停、原型内容、原型顺序、备注和基础版本均参与摘要，仅 `save_operation_id` 被排除。
