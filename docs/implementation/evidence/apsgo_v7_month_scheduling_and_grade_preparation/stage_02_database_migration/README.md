## 2. 实现结果

1. `RuleStore` 当前 schema 升为 v2：规则版本增加字典指纹，新增按规则版本所属的字典明细表，
   并保留更新、删除和向活动/历史版本追加的数据库级禁止保护。
2. 普通打开只接受严格 v2；迁移命令使用专用入口验证严格 v1 或 v2。schema 增量、字典、新规则
   版本、活动指针和最终 `user_version=2` 在同一个 `BEGIN IMMEDIATE` 事务内完成。
3. 新库初始化必须显式提供已核验的 V3 SQLite 源；源不合法时不创建目标目录或数据库。已有
   有效 v2 库可不再依赖 V3，重复初始化只读验证且不覆盖活动版本。
4. 页面保存并启用在并发检查后，从操作前活动版本复制完整字典；保存请求摘要公式不含字典。
   同一操作重放不复制字典，也不把已经被替代的版本重新激活。
5. 历史恢复读取历史规则、虚拟原型和备注，但新版本继承恢复操作前的活动字典；迁移前无字典
   的历史规则仍可作为恢复来源，不能直接作为活动求解快照。
6. 迁移先用 SQLite Backup API 固化 V3 临时一致性快照，再从同一快照读取、校验并计算
   `source_database_sha256`；因此 WAL 中已提交内容和记录的来源身份不会分离。GQGA4 必须恰好
   230 条、全部启用、规范化牌号唯一，并通过所有业务和来源字段校验。
7. 迁移操作以 UUID、原活动版本、保留的迁移审计主体和字典指纹核对重放；普通规则保存不能
   使用该主体伪装迁移。一致时返回原保存版本及其当前活动状态，不再建版本、建备份或重新激活。
8. 事务失败后保留可恢复备份；相同参数重试只复用严格 schema v1 且三张规则表全量内容与
   当前目标相同的备份。不匹配的同名文件拒绝且不覆盖，复制后验证失败会清理不完整文件。

本阶段复用现有规则版本记录承担迁移审计，没有增加单独的迁移日志表；现有不可变版本、操作
UUID、执行主体、来源版本和字典指纹已经覆盖本期重试与追溯需求。
