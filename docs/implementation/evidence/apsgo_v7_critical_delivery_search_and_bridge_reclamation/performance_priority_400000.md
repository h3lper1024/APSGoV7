## 3. 内部函数的有界诊断

为了避免再次等待 20 分钟完整求解，从组合 40 万次保存的精修入口恢复方案，仅运行前 2000 次额度的实际精修代码；冷建边缓存及评价复用状态，使用标准库 `cProfile`。不修改正式请求或源代码，结果不用于替换完整排程。生产源码与 `735cc14` 一致。

原始记录：`diagnostics/critical_delivery_search_and_bridge_reclamation/performance_400000_20260915_02/prefix.prof`；回读摘要为同目录 `profile_analysis.json`，包括源测量和二进制摘要的 SHA-256。探针记录 794 次完整评价、15 次接受；2001 次候选扣费调用包含最后一次额度拒绝。采样运行不是完整阶段测量，不能把其比例直接乘以 802 秒当作精确贡献。

| 降序 | 计算项 / 代码位置 | 样本累计时间 / 秒 | 优化方向（尚未实施） |
|---|---|---:|---|
| 1 | 交期全方案重算，`delivery_timing.py:evaluate_delivery` | 5.06 | 预计算节点工时及交期阈值，复用未变前缀，只重算受影响区间和必要后缀；原单拆片以最后完成为准，仍保留原精度累计、秒级评分 |
| 2 | 直接连接插入位置排序，`width_optimization.py:_direct_insertion_slots` | 3.19 | 复用同一方案下的节点与目标链可插位置；在产生提案前确定重点/常规归属，减少生成后才丢弃的重复扫描，保留候选并集和顺序 |
| 3 | 受影响链的规则重评，`rule_set.py:evaluate_complete_chain` | 2.47 | 已有未变链复用不能重复算作新优化；针对真正变化的链研究边界/连续段摘要复用，保留全部规则语义 |
| 4 | 资源和重量全量汇总，`resource_facts.py:derive_evaluation_resource_view` | 1.83 | 真实重量、原单集合及未变链贡献复用；虚拟增删、借用归属和拆单仅对变化部分更新，发布前全量复核 |
| 5 | 候选节点完整性检查，`neighborhoods.py:_width_candidate_nodes_valid` | 1.44 | 当前每个候选遍历旧节点及新方案；针对同一不可变节点/链复用已验证事实，变化节点和连接材继续核验，不取消入口校验或最终审计 |

这些是各函数的累计时间，含被调用函数；不是互斥桶，不能简单求和。样本的完整候选评价总入口约 11.99 秒，包含上表若干项；`sum_weights()` 合计约 5.23 秒，分散在交期守恒、资源及链重计算中，也不能作为额外 5.23 秒再次相加。单样本有约 2.75 秒首次数值内核编译成本，后置阶段通常已经编译过；实际 `_scan_block` 累计约 0.023 秒，不能据首次编译将继续改桥接内核排为第一优先级。

这里有一条跨阶段优先项：**整链换位使用专门的精确增量评价**。它不改变链内节点，但目前仍进入通用完整候选、资源与交期扫描。首轮已经花约 137 秒，拆后重放和后置精修也使用相同评分。先优化共用交期/资源计算及整链换位路径，能同时覆盖前三个阶段；并不是再增加一种算子。

## 4. 一分钟目标的约束

在当前 Mac、同输入及同 40 万次条件下，从 1214.57 秒到 60 秒需要约 20.24 倍提速，削减约 95.06% 的经过时间；平均约 329 次检查/秒需提升到约 6667 次/秒（只是全流程归一化指标，检查代价并不相等）。仅把耗时最大的精修阶段完全消除，其他部分仍约 412 秒，说明必须跨阶段减少共用计算。

不能目前承诺单靠某个库、缓存或多进程即可达到一分钟。先做无损的重复计算削减：交期增量/整链换位 → 直接插入位置复用 → 资源与受影响链/节点校验增量。数值化或并行应针对优化后仍然热的独立计算另行测试，不能以更少候选、不同顺序、关闭审计或放宽规则冒充同质量提速。若这些措施仍不足，再单独讨论是否允许改变搜索策略与质量取舍。

本机计时不等于 Windows 实包时间；后续性能目标还须在实际验收机器上复测，并区分冷启动与已启动服务请求。本次只列候选优化点，不开启大改造。
