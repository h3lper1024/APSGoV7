## 2. 关键控制边界

1. 候选描述来自同一只读方案代次；拒绝候选继续复用当前方案和既有候选私有变化链、资源及评价工作区。
2. 动作族来源游标只在描述实际消费后推进。批次预取不能把下一轮搜索起点越过已接受候选。
3. 主线程严格按原顺序消费；首个改善被接受后，同批剩余描述属于旧方案代次，立即作废，不扣逻辑候选额度。
4. 取消、时间或额度停止发生在消费前时，未消费描述不调用候选入口、不提交方案、资源或正式编号，并分别记录已准备、已消费、拒绝、接受、旧代次、取消和停止数量。
5. 动态桥接以及一个结构配方内部的第二修复变体继续使用原串行候选事务。本阶段没有把它们伪装成可并行工作，也没有改变其额外候选计费。

## 6. 阶段 6.2：完整候选评价线程适用性试验

阶段 6.2 先执行收益筛查，再决定是否把线程接入生产搜索。筛查没有修改生产源码，也没有增加第二套评分器：从同一冻结请求的一次 150000 次上限运行中，截取 `evaluate_numeric_overlay_candidate()` 实际收到的前 256 组只读输入；随后对完全相同的 256 组输入分别用 1、2、4、8 个 Python 工作线程调用**同一个完整评价函数**。每档先预热一次，再独立运行 5 次；每次结果均逐项与串行基线比较，规则结果、违规、资源、交期和九级评分全部一致。

本机为 macOS arm64、Python 3.10.18，操作系统报告 12 个逻辑处理器；Numba 默认及配置线程数均为 12。原始试验摘要保存于 `diagnostics/numpy_numeric_search_and_calculation/stage6_exact_evaluator_thread_probe_256_01.json`。

| 工作线程 | 经过时间中位数 | 相对 1 线程 | CPU 时间中位数 | 相对 1 线程 |
|---:|---:|---:|---:|---:|
| 1 | 0.369328 秒 | 基准 | 0.373803 秒 | 基准 |
| 2 | 0.376141 秒 | 慢 1.84% | 0.386019 秒 | 多 3.27% |
| 4 | 0.382813 秒 | 慢 3.65% | 0.414506 秒 | 多 10.89% |
| 8 | 0.396968 秒 | 慢 7.48% | 0.448850 秒 | 多 20.08% |

结论如下：

1. 当前权威完整评价入口及其核心 `_evaluate_numeric_candidate()` 都是普通 Python 函数，不是 Numba 编译内核；内部仍需建立 Python 规则结果、违规和指标对象。Numba 线程不能直接把该调用变成候选维度的 `prange` 循环。
2. 直接并发执行同一个完整评价函数没有收益，线程越多，经过时间和 CPU 时间越高。这里测到的是完整评价调用，不是只占很小比例的交期边界子函数。
3. 若为了使用 Numba `prange` 另写一份只返回九级评分的平行评价器，会重新形成两套规则/评分实现和新的等价风险，不符合本专项“一个权威数值口径”的边界；本阶段不这样做。
4. 因 2/4/8 线程档均未超过 1 线程，按计划的收益门槛不进入完整 40 万次多线程运行，也不把试验线程池留在生产路径。阶段 6.1 的 8 条有序描述批次继续串行消费，规则、九级评分、候选顺序、逻辑额度、资源编号和外部接口均不变。

生产源码和阶段 6.1 测试文件的工作树哈希与 `HEAD` 完全一致；因此线程失败、旧代次、取消、正式编号和投机额度没有新增生产分支需要回归。阶段 6.1 已通过的共享树及精确树 3869 项结果继续适用于当前源码，本节不重复累计测试，也不把独立性能探针冒充功能测试。

## 7. 结论与下一步

阶段 6.1 的正确性门已关闭：批次边界、来源游标、首改善、逻辑额度、取消和旧方案描述作废均保持串行语义。阶段 6.2 又确认当前完整评价入口不适合直接用线程并行：2/4/8 线程均慢于 1 线程，并增加 CPU 消耗。

因此阶段 6 采用当前数值串行实现，不接入候选线程，不运行没有收益依据的 40 万次多线程组。下一项进入阶段 7.1，清理历史上不再可达的旧上下界/对象精算接线并完成最终文档、质量和性能边界收口；一分钟目标仍未达到，不能标记为通过。
