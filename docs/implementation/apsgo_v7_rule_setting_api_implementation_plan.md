## 2. 实施目标

按已确认接口契约完成 GQGA4 月计划规则页面与 V7 的首期适配：

```http
GET /api/v1/rule-sets/GQGA4/default/month/getActiveRules
POST /api/v1/rule-sets/GQGA4/default/month/setActiveRules
```

最终形成以下闭环：

1. 页面一次 GET 读取当前活动规则。
2. 页面一次 POST 保存完整可编辑快照并立即启用。
3. 后端逐条保存规则，同时生成经过 V7 权威加载器验证的完整 `RuleSetSpec` JSON。
4. 数据库事务原子切换活动版本，并处理并发编辑和网络重试。
5. 新排程任务只在启动时读取一次完整编译快照，搜索过程中不访问规则数据库。

## 3. 实施边界

### 3.1 本计划包含

- V7 规则管理接口数据契约。
- GQGA4 固定规则模板和完整配置编译。

- 查询当前活动规则、保存并立即启用的应用服务和 HTTP 路由。
- 初始 GQGA4 正式规则版本导入。
- 排程请求启动时的活动规则快照绑定。
- C# GQGA4 规则页面的查询、保存、错误处理和按钮流程改造。
- 契约、事务、并发、幂等、页面及求解绑定验收。

### 3.2 本计划不包含

- V3 规则接口、DSL 或数据库兼容。
- 草稿、单独启用、审批、定时生效、历史版本删除或回滚页面。
- 任意新增 Python 规则类型、规则表达式编辑器或通用多产线规则设计器。
- 月计划排程接口地址、参数或返回模型的适配。
- 求解算法、搜索动作、评分顺序或 GQGA4 质量门槛调整。
- 重新执行链间宽差专项的 20 对性能验收；本专项没有改变搜索算法。

## 4. 实施原则

1. **现有 V7 契约是唯一规则语义来源**：复用 `RuleSetSpec`、指纹计算和 `load_rule_set()`，不另写第二套业务校验器。
2. **逐条记录用于管理，完整快照用于求解**：求解器不能查询 17 行后临时组装。
3. **一次保存一个事务**：版本、规则行、虚拟原型、编译 JSON和活动指针同成同败。
4. **服务端控制固定元数据**：C# 只提交规则标识、启停和参数，不控制类型、范围、顺序、评分与指纹。
5. **完整集合替换**：POST 必须包含全部固定规则；缺失不解释为停用。
6. **失败关闭**：快照损坏、指纹不符或加载失败时拒绝启用/求解，不回退 V3 或测试文件。
7. **最少新结构**：只实现 GQGA4 当前需要的一套宿主和数据库接入，不为未确认的框架创建通用适配层。
8. **每个功能阶段独立提交**：提交信息使用中文并以 `#feat` 或 `#fix` 开头；不使用 `git add .` 或 `git add -A`。

## 10. 阶段 2：实现 GQGA4 完整规则编译

5. 复用现有指纹函数和 `load_rule_set()`，序列化回读后再次复算与加载。
6. 独立校验虚拟材料原型，但不把它们放入 `RuleSetSpec.rules`。

### 10.2 测试

## 12. 阶段 4：实现保存并启用事务

### 12.1 实现

应用服务严格按以下顺序执行：

1. 规范化请求并计算 `request_hash`。
2. 开始事务并锁定规则集。
3. 先检查 `save_operation_id` 的幂等记录。
4. 再核对 `expected_active_version_id`。
5. 调用阶段 2 的唯一编译入口。
6. 写版本、17 条规则、虚拟原型和编译快照。
7. 以旧版本为条件切换活动版本。
8. 提交并返回完整活动视图。

GET 服务从活动版本读取规则行与编译快照，核对规则数量、顺序、指纹和业务身份后组装响应；发现内部不一致时返回服务器错误，不把损坏数据发给页面。

### 12.2 测试

- 正常保存创建一个版本并立即成为活动版本。
- 两个并发编辑者中只有第一个成功，第二个返回版本冲突。
- 成功响应丢失后，同操作标识、同内容重试不创建版本，并返回原保存版本与当前活动视图。
- 原保存版本后来已被替代时，重放不重新启用旧版本，并明确返回 `saved_version_is_active=false`。
- 同操作标识、不同内容返回冲突。
- 幂等重放优先于旧 `expected_active_version_id` 检查。
- 任一编译、写入或条件更新失败不改变活动版本。

### 12.3 验收

- 并发与幂等使用真实事务测试验证。
- 不存在“规则行已更新但完整快照或活动指针未更新”的可见状态。
- 服务端操作者来自进程身份、时间来自服务器；请求体不接受可信操作者字段。

## 13. 阶段 5：接入两条 HTTP 路由

### 13.1 实现

- 精确注册 `GET /api/v1/rule-sets/GQGA4/default/month/getActiveRules`。
- 精确注册 `POST /api/v1/rule-sets/GQGA4/default/month/setActiveRules`。
- 服务首期只绑定回环地址；接入请求大小限制、日志和统一异常处理，不虚构不存在的登录鉴权。
- 将应用诊断稳定映射为 `400/404/409/422/500/503`。
- 返回 JSON 字段和大小写严格遵守详细设计；不额外发布草稿、启用或 V3 兼容路由。

### 13.2 测试

- 路由方法和路径的契约测试。
- GET 无请求体并返回完整活动版本。
- POST 仅接受 JSON，对缺失、重复、未知规则返回字段级 `422`。
- 并发与操作标识冲突返回 `409`。
- 非回环启动被拒绝，内部错误不泄露堆栈或数据库信息。
- OpenAPI 或宿主路由表中不存在本专项未设计的写接口。

### 13.3 验收

- 用真实 HTTP 测试客户端完成 GET → 修改一个参数 → POST → GET 闭环。
- 响应中的新版本、指纹和逐条规则与数据库活动版本一致。

- 数据库编译快照通过指纹复算和 `load_rule_set()`。
- 第二次执行不新增版本、不改变活动指针。
- 初始化产物不依赖 `/Users/...` 等本机路径。

## 15. 阶段 7：绑定排程任务规则快照

### 15.1 实现

1. 在真实排程请求组装入口按产线、工序和场景读取一次活动版本。
2. 解析完整 `RuleSetSpec` 和虚拟原型，复算指纹并权威加载。

4. 在任务记录、公开结果或审计元数据的既有适当位置保存活动版本与指纹。
5. 搜索阶段只使用请求快照；禁止从规则仓储读取。

### 15.2 测试

- 任务 A 启动后启用新版本，任务 A 保持旧指纹，任务 B 使用新指纹。
- 活动快照损坏、指纹不符、规则加载失败时拒绝启动。
- 不存在测试文件、V3 配置或上一个历史版本的隐式回退。
- 搜索调用链中规则仓储读取次数为零。

### 15.3 验收

- 使用数据库初始版本完成一次固定种子的 GQGA4 全流程求解。
- 零禁止、零欠重、来源覆盖与双审计等现有质量门保持通过。
- 只记录单次功能回归耗时，不把它称为新的 20 对性能验收或算法性能改善。

## 16. 阶段 8：建立 C# V7 规则客户端

### 16.1 实现

- 新建 V7 专用客户端和最少 DTO，只包含两个接口需要的字段。

### 16.2 测试与验收

- POST 请求不包含服务端所有字段。

## 17. 阶段 9：改造 GQGA4 页面加载

### 17.1 实现

- 用一次 `getActiveRules` 替换 V3 目录、当前规则、表单规范和预览加载链。
- 按 `rule_id` 填充现有控件，缓存完整可编辑规则集合、虚拟原型和活动版本。
- 缺少页面所需固定规则时禁止保存并显示配置错误。
- 页面无控件的规则保留原启停与参数，不在保存时重建默认值。
- 查询失败不显示为成功，也不使用硬编码默认规则覆盖数据库。

### 17.2 测试与验收

- 页面打开只发一个规则 GET 请求。
- 17 条规则中可见和不可见项均进入缓存，停用规则状态正确。
- 逆宽、厚度、温度、链重、虚拟材料和固定规则控件映射正确。
- 虚拟材料规格进入 `virtual_prototypes`，不伪装成规则。

## 18. 阶段 10：改造保存并启用流程

### 18.1 实现

- 以缓存的完整规则集合为底，只覆盖用户修改控件对应字段。
- 每次点击生成操作标识，提交一次 `setActiveRules`。
- 删除 GQGA4 页面保存草稿、单独启用、规则预览和目录依赖代码及按钮。
- 成功后使用响应完整刷新页面基线。
- `409` 和 `422` 保留当前编辑值；取消只恢复最近成功快照。
- 网络结果不确定时复用原操作标识重试，不盲目生成新操作。
- 幂等重放表明原保存版本已被替代时，提示用户并刷新为当前活动版本，不重新提交旧值。

### 18.2 测试与验收

- 保存只产生一个 POST，不再产生草稿和启用的串行请求。
- 修改一个可见参数后，不可见规则、固定评分和允许偏差保持不变。
- 并发冲突不覆盖他人版本，页面可重新加载后人工处理。
- 原保存版本已被后续版本替代时，幂等重试不会让页面误认旧版本仍活动。
- 字段错误能定位到对应控件；无法定位的错误有完整总提示。
- 其他 V3 页面编译与基础操作不受影响。

## 22. 回退方案

- C# 页面回退：回退 C# 专项提交；不删除已建立的 V7 历史版本。
- HTTP/服务回退：回退应用部署，保留数据库表和版本数据；禁止通过修改历史行伪造回退。
- 规则内容回退：本期没有页面接口。如生产应急需要恢复旧配置，应通过受控运维命令“复制旧版本内容并编译为新版本”，保留新审计记录。
- 数据库迁移回退：只在确认表内无生产数据时执行删除表的回退迁移；已有数据时保留结构并回退应用。
- 求解绑定失败时不回退到 V3 或测试 JSON；停止新任务并修复活动版本或服务。

任何生产回退前先确认精确目标和备份状态，不使用破坏性通配命令。

## 23. 风险与控制

| 风险 | 后果 | 控制措施 |
|---|---|---|
| 页面只回传可见规则 | 隐藏规则丢失或被误停用 | GET/POST 都使用完整集合，服务端要求恰好 17 个规则标识。 |
| 两人并发覆盖 | 后保存者静默覆盖 | `expected_active_version_id` + 条件更新 + `409`。 |
| 网络重试重复建版本 | 多版本、审计混乱 | `save_operation_id` + `request_hash`，幂等检查优先。 |
| JSON 小数经 `float` 漂移 | 指纹不同、规则阈值变化 | HTTP 入口直接使用 `Decimal`，规范化序列化和回读复算。 |
| 逐条记录与编译快照不一致 | 页面和求解看到不同规则 | 同事务写入，GET/启动回读校验，求解只信编译快照。 |
| 活动配置损坏仍启动 | 排程结果不可审计 | 指纹与加载失败立即拒绝，无文件/V3 回退。 |
| 新 V7 客户端破坏其他页面 | 无关规则页面不可用 | 新建专项客户端，保留 `PipelineV3ApiClient`。 |
| 先实现通用多产线平台 | 工期和复杂度失控 | 本期固定 GQGA4 模板，只保留产线/工序/场景身份。 |
| macOS 静态检查冒充页面完成 | 运行期或 Designer 问题遗漏 | Windows 构建和页面手测列为完成条件。 |

## 24. 实施暂停条件

用户已要求后续按计划持续推进，不在每个小阶段重复等待确认。仅在以下情况暂停：

1. 现场存在多个可能的 HTTP 宿主或数据库，无法用代码证据确定唯一目标。
2. 必须改变已确认的接口方法、地址、完整集合语义或保存即启用语义。
3. 必须改变数据库现有表或生产数据，且迁移影响超出本计划三类逻辑表。
4. 发现 C# 页面基础业务功能与本文映射冲突，需要产品决策。
5. 发现用户未提交改动与本阶段目标文件直接冲突。
6. 需要生产凭据、生产写操作或破坏性数据操作的新授权。

普通实现细节、命名微调和本阶段测试修复不构成暂停理由。
