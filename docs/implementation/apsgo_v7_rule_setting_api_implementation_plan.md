## 2. 实施目标

按已确认接口契约完成 GQGA4 月计划规则页面与 V7 的首期适配：

```http
GET /api/v1/rule-sets/GQGA4/default/month/getActiveRules
POST /api/v1/rule-sets/GQGA4/default/month/setActiveRules
```

最终形成以下闭环：

1. 页面一次 GET 读取当前活动规则。
2. 页面一次 POST 保存完整可编辑快照并立即启用。
3. 后端逐条保存规则，同时生成经过 V7 权威加载器验证的完整 `RuleSetSpec` JSON。
4. 数据库事务原子切换活动版本，并处理并发编辑和网络重试。
5. 新排程任务只在启动时读取一次完整编译快照，搜索过程中不访问规则数据库。

## 3. 实施边界

### 3.1 本计划包含

- V7 规则管理接口数据契约。
- GQGA4 固定规则模板和完整配置编译。
- 规则集、不可变版本、逐条规则的数据库持久化。
- 查询当前活动规则、保存并立即启用的应用服务和 HTTP 路由。
- 初始 GQGA4 正式规则版本导入。
- 排程请求启动时的活动规则快照绑定。
- V7 服务数据库路径、SQLite 超时和监听端点的统一文件配置。
- C# GQGA4 规则页面的查询、保存、错误处理和按钮流程改造。
- 契约、事务、并发、幂等、页面及求解绑定验收。

### 3.2 本计划不包含

- V3 规则接口、DSL 或数据库兼容。
- 草稿、单独启用、审批、定时生效、历史版本删除或回滚页面。
- 任意新增 Python 规则类型、规则表达式编辑器或通用多产线规则设计器。
- 月计划排程接口地址、参数或返回模型的适配。
- 求解算法、搜索动作、评分顺序或 GQGA4 质量门槛调整。
- 重新执行链间宽差专项的 20 对性能验收；本专项没有改变搜索算法。

## 4. 实施原则

1. **现有 V7 契约是唯一规则语义来源**：复用 `RuleSetSpec`、指纹计算和 `load_rule_set()`，不另写第二套业务校验器。
2. **逐条记录用于管理，完整快照用于求解**：求解器不能查询 17 行后临时组装。
3. **一次保存一个事务**：版本、规则行、虚拟原型、编译 JSON和活动指针同成同败。
4. **服务端控制固定元数据**：C# 只提交规则标识、启停和参数，不控制类型、范围、顺序、评分与指纹。
5. **完整集合替换**：POST 必须包含全部固定规则；缺失不解释为停用。
6. **失败关闭**：快照损坏、指纹不符或加载失败时拒绝启用/求解，不回退 V3 或测试文件。
7. **最少新结构**：只实现 GQGA4 当前需要的一套宿主和数据库接入，不为未确认的框架创建通用适配层。
8. **每个功能阶段独立提交**：提交信息使用中文并以 `#feat` 或 `#fix` 开头；不使用 `git add .` 或 `git add -A`。
9. **配置失败关闭**：服务和初始化器只接受完整、严格校验的四项运行配置，不从环境变量或代码默认值静默补齐缺项。

## 9. 阶段 1：建立规则管理接口契约

### 9.1 实现

- 定义 GET 完整活动版本响应。
- 定义 POST 完整保存请求和成功响应。
- 定义可定位错误、并发版本、操作标识、原保存版本和当前活动版本的幂等重放字段。

- 不把 HTTP 框架、数据库实体或 C# 请求/响应类型混入 V7 核心契约。

### 9.2 测试

- 合法完整请求往返不丢字段或数值精度。
- 布尔值、正整数、UUID、规则数组和原型数组的边界失败可定位。
- `20.0` 与 `20.00` 等价且不经过 `float`；通用契约暂时保留规则参数 `20` 与 `20.0` 的类型差异，阶段 2 再按固定模板归一。
- 虚拟材料原型等已有明确字段类型的数值允许将 `20` 与 `20.0` 归一为同一 `Decimal`。
- 顶层、规则项和虚拟材料原型的未知字段严格拒绝，并提供可定位字段路径；规则参数和原型属性内部按各自声明处理。
- 规则参数以 `parameters` 根对象为第 0 层，任一值距根最多 64 层；验证 64 层通过、65 层稳定返回字段级错误，不泄漏递归异常。

### 9.3 验收

- 数据结构能表达设计文档中的全部请求、响应和错误字段。
- 契约层不导入 Web 或数据库依赖。
- 既有 V7 公开请求测试保持通过。

### 9.4 实际实施结果

## 10. 阶段 2：实现 GQGA4 完整规则编译

### 10.1 实现

1. 在 `apsgo_v7_service` 从正式 GQGA4 规则定义建立固定模板，包含 17 个规则标识、类型、名称、范围、版本和顺序；`apsgo_scheduler.app` 的编译器保持产线无关。
2. 接受客户端完整的 `rule_id + enabled + parameters` 集合，拒绝缺失、重复和未知标识。
3. 注入现有固定七级评分定义与允许最终偏差。
4. 将数据库 `version_no` 的无前导零十进制文本作为新 `RuleSetSpec.version`，构造 `RuleSetSpec`。
5. 复用现有指纹函数和 `load_rule_set()`，序列化回读后再次复算与加载。
6. 独立校验虚拟材料原型，但不把它们放入 `RuleSetSpec.rules`。
7. 共用同一模板提供两个有序纯步骤：先将编辑输入归一为稳定页面快照，再结合服务端分配的 `version_no` 编译完整规则集。保存、初始化和求解回读都复用这两个步骤，不建设第二套模板或校验器。
8. 后续幂等摘要只能基于归一快照，不得基于原始请求文本或阶段 1 尚未类型化的数据对象。

### 10.2 测试

- 正式样本编译为 17 条、16 条启用、1 条指定停用和 7 项评分。
- 每个规则的允许参数变更均能通过或返回现有 V7 诊断。

## 11. 阶段 3：建立规则版本存储

### 11.1 实现

- 使用标准库 `sqlite3` 建立 `v7_rule_set`、`v7_rule_set_version`、`v7_rule_definition` schema 和向前初始化。
- 建立规则集业务身份、版本号、保存操作标识、版本内规则标识和顺序的唯一约束。
- 保存完整编译 JSON、指纹、虚拟原型、页面快照、基础版本和可信审计字段。
- 建立当前活动版本指针；历史版本记录不可更新。
- 使用单个 SQLite 连接和 `BEGIN IMMEDIATE` 实现最小存储操作，不建设通用仓储接口或第二种数据库后端。
- 将启动初始化与普通打开分离：初始化入口负责建表和向前检查，普通请求只验证并打开已经存在的 schema，不重复申请初始化写锁。
- 每个 `RuleStore` 连接只在创建它的线程内使用；后续 HTTP 适配不得把一个连接对象跨线程池共享。

### 11.2 测试

- 同一业务身份不能重复建立规则集。
- 同一规则集的版本号和保存操作标识不能重复。
- 同一版本不能出现重复规则标识或重复顺序。
- 新版本写入失败、规则行写入失败或活动指针切换失败均回滚。
- 历史版本更新被应用服务和数据库约束共同阻止。

### 11.3 验收

- 迁移可在临时数据库从空库升级成功。
- 关键唯一约束由真实数据库测试证明，不只靠模拟对象。
- 本阶段不提供反向迁移或自动删表函数；空的临时验收库在关闭连接后删除数据库文件并验证可重新初始化。已有数据的生产回退保留结构并依靠部署备份恢复，不由应用删除历史。

### 11.4 实际实施结果

- 新增一个具体的 `RuleStore`，每个实例只持有一个标准库 SQLite 连接；连接采用自动提交模式，读事务显式 `BEGIN`，写事务显式 `BEGIN IMMEDIATE`，提交失败或任意异常均回滚。初始化与普通打开分离，普通打开不创建数据库、不执行迁移或争抢写锁。没有增加 ORM、连接池、WAL、缓存或第二种数据库实现。

- 版本同时保留 `created_by/created_at` 与 `activated_by/activated_at` 两组服务端审计字段；[历史信息] 本阶段当时固定默认数据库路径及唯一覆盖环境变量，运行时数据库文件被 Git 忽略。阶段 12 只替换运行配置入口，不改变本阶段存储或 Git 忽略语义。

## 12. 阶段 4：实现保存并启用事务

### 12.1 实现

应用服务严格按以下顺序执行：

1. 调用阶段 2 的模板归一步骤取得规范化页面快照，再用现有 `fingerprint()`（内部为稳定编码与 SHA-256）计算 `request_hash`。摘要包含规则集路径身份、`expected_active_version_id`、固定顺序规则、保持用户顺序的虚拟材料原型及去除首尾空白后的 `remark`；`save_operation_id` 不进入摘要。
2. 开始事务并锁定规则集。
3. 先检查 `save_operation_id` 的幂等记录。
4. 再核对 `expected_active_version_id`。
5. 调用阶段 2 的带版本完整编译步骤。
6. 写版本、17 条规则、虚拟原型和编译快照。
7. 以旧版本为条件切换活动版本。
8. 提交并返回完整活动视图。

GET 服务从活动版本读取规则行与编译快照，核对数据库版本号、规则集业务身份、指纹、规则数量和连续顺序 `1..17` 均与编译快照一致后组装响应；发现内部不一致时返回服务器错误，不把损坏数据发给页面。

### 12.2 测试

- 正常保存创建一个版本并立即成为活动版本。
- 两个并发编辑者中只有第一个成功，第二个返回版本冲突。
- 成功响应丢失后，同操作标识、同内容重试不创建版本，并返回原保存版本与当前活动视图。
- 原保存版本后来已被替代时，重放不重新启用旧版本，并明确返回 `saved_version_is_active=false`。
- 同操作标识、不同内容返回冲突。
- 幂等重放优先于旧 `expected_active_version_id` 检查。
- 任一编译、写入或条件更新失败不改变活动版本。

### 12.3 验收

- 并发与幂等使用真实事务测试验证。
- 不存在“规则行已更新但完整快照或活动指针未更新”的可见状态。
- 服务端操作者来自进程身份、时间来自服务器；请求体不接受可信操作者字段。

### 12.4 实际实施结果

- 新增两个框架无关应用服务入口：查询当前启用规则，以及保存完整页面快照并立即启用。每次调用自行打开当前线程的 SQLite 连接，不增加仓储接口、ORM、连接池或缓存。
- 请求在事务外按 GQGA4 模板规范化，摘要按固定 17 条规则顺序、原型顺序、基础活动版本和规范化备注计算，不包含保存操作标识。同一操作先幂等回放，再检查当前活动版本。
- 新保存在一个 `BEGIN IMMEDIATE` 事务中完成版本、17 条规则、原型与页面快照写入、条件活动指针切换、完整回读和响应序列化。编译、数据库写入、条件切换、回读或序列化任一失败均不留下新版本。
- 幂等回放在原版本已被替代后只返回当前活动视图，不重新启用历史版本。活动版本回读会核对业务身份、版本、指纹、逐条规则、原型、页面快照、请求摘要和备注规范化。
- 用真实文件型 SQLite 及两个独立连接验证写锁重叠：不同操作的后到请求返回活动版本冲突，同一操作的后到请求进行幂等回放，两者都只产生一个新版本。
- 阶段 4 专项测试 35 项、事务服务/存储/架构聚焦 128 项、共享树累计 3098 项通过；最终干净导出结果由阶段证据与本项提交记录固定。
- 本阶段不包含 HTTP 路由、正式数据库初始化、求解请求绑定或 C# 改动；下一阶段只接入两条已确认的 HTTP 路由及错误映射。

### 20.2 配置契约与命令

```yaml

```

## 24. 回退方案

- C# 页面回退：回退 C# 专项提交；不删除已建立的 V7 历史版本。
- HTTP/服务回退：回退应用部署，保留数据库表和版本数据；禁止通过修改历史行伪造回退。
- 运行配置回退：恢复上一个已验证的受跟踪配置和匹配代码；先离线校验其精确数据库路径及监听端点，再重启服务。不得通过重新设置 `APSGO_V7_RULE_DB_PATH` 绕过配置文件。
- 规则内容回退：本期没有页面接口。生产应急恢复旧配置时，先确认数据库备份、来源版本和当前活动版本，再使用下述受控命令；该命令复制旧版本内容、重新编译并创建新版本，不修改或重新激活历史行：

```bash
apsgo-v7-restore-gqga4-rule-version \
  --database-path <既有数据库绝对路径> \
  --source-version-id <来源版本主键> \
  --save-operation-id <本次恢复的UUID> \
  --expected-active-version-id <操作前确认的活动版本主键>
```

恢复命令不使用隐式默认数据库，也不创建文件。响应不确定时必须原样重跑同一条命令；若原恢复结果已被后续版本替代，命令返回非零退出码且不会重新激活旧结果。活动版本已变化时不得把参数改成新值强行覆盖，应先重新核对来源、当前活动配置及变更责任人，再决定是否发起一个新的恢复操作。
- 数据库迁移回退：只在确认表内无生产数据时执行删除表的回退迁移；已有数据时保留结构并回退应用。
- 求解绑定失败时不回退到 V3 或测试 JSON；停止新任务并修复活动版本或服务。

任何生产回退前先确认精确目标和备份状态，不使用破坏性通配命令。

## 25. 风险与控制

| 风险 | 后果 | 控制措施 |
|---|---|---|
| 页面只回传可见规则 | 隐藏规则丢失或被误停用 | GET/POST 都使用完整集合，服务端要求恰好 17 个规则标识。 |
| 两人并发覆盖 | 后保存者静默覆盖 | `expected_active_version_id` + 条件更新 + `409`。 |
| 网络重试重复建版本 | 多版本、审计混乱 | `save_operation_id` + `request_hash`，幂等检查优先。 |
| JSON 小数经 `float` 漂移 | 指纹不同、规则阈值变化 | HTTP 入口直接使用 `Decimal`，规范化序列化和回读复算。 |
| 逐条记录与编译快照不一致 | 页面和求解看到不同规则 | 同事务写入，GET/启动回读校验，求解只信编译快照。 |
| 活动配置损坏仍启动 | 排程结果不可审计 | 指纹与加载失败立即拒绝，无文件/V3 回退。 |
| 新 V7 客户端破坏其他页面 | 无关规则页面不可用 | 新建专项客户端，保留 `PipelineV3ApiClient`。 |
| 先实现通用多产线平台 | 工期和复杂度失控 | 本期固定 GQGA4 模板，只保留产线/工序/场景身份。 |
| macOS 静态检查冒充页面完成 | 运行期或 Designer 问题遗漏 | Windows 构建和页面手测列为完成条件。 |
| 相对数据库路径按当前目录解析 | 从不同目录启动时误连或新建错误数据库 | 始终以配置文件所在目录解析并在启动时冻结为绝对路径。 |
| 配置缺项或未知项被静默默认 | 实际运行参数与审计预期不一致 | 要求四项键精确匹配并在任何数据库或 Uvicorn 操作前失败。 |
